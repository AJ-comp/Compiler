PARSER DESIGN NOTES 2026.10.12 · 한국어

ANTLR4의 LL과 장림의 LR
규칙을 선택하는 시점이 다릅니다

같은 x y를 읽어도, 먼저 규칙을 고르고 읽을 수 있고 공통 부분을 읽은 뒤 규칙을 구별할 수도 있습니다. 이 작은 차이가 언제 추가 lookahead가 필요한지를 바꿉니다.

이 문서의 중심 질문
ANTLR4가 다음 토큰까지 미리 보는 문법을, 장림은 왜 기존 LALR(1) 테이블만으로 처리할 수 있을까요?

01 · 읽는 순서

LL은 대안을 고르고, LR은 공통 부분을 읽으며 판단을 미룰 수 있습니다

LL과 LR은 모두 토큰을 왼쪽에서 오른쪽으로 읽습니다. LL의 두 번째 L은 문장에 남은 가장 왼쪽 비단말부터 전개한다는 뜻이고, LR의 R은 가장 오른쪽 비단말부터 전개하는 유도를 역순으로 복원한다는 뜻입니다. LR의 R도 입력을 오른쪽부터 읽는다는 뜻으로 해석하면 방향이 헷갈립니다.

ANTLR4 · LL / ALL(*)

어느 규칙을 실행할지 먼저 고릅니다

규칙에 들어가서 여러 대안 중 하나를 실행해야 할 때, 앞으로 올 입력을 살펴 대안을 선택합니다. 선택한 대안의 토큰과 하위 규칙을 실제로 읽어 갑니다.

ANTLR4는 Adaptive LL(*) 예측을 사용합니다. 선택이 쉬운 곳은 다음 토큰 하나를 확인하는 코드로 처리합니다.

Janglim · LALR(1)

읽은 부분이 어느 규칙을 이루는지 판단합니다

현재 상태와 다음 토큰으로 테이블을 조회합니다. 공통 토큰은 Shift하고, 규칙의 오른쪽이 완성되면 Reduce합니다. 아직 구별되지 않은 규칙들은 한 LR 상태의 아이템으로 함께 기록될 수 있습니다.

왜 이렇게 하나요? 공통 부분을 읽는 동안 같은 액션을 실행할 수 있다면, 구별되는 토큰이 나올 때까지 규칙 선택을 늦출 수 있기 때문입니다.

02 · 같은 문법으로 비교하기

x y와 x z: 장림이 추가 예측 없이 처리하는 이유

S : 'x' 'y'
  | 'x' 'z' ;

여기서 두 대안은 모두 x로 시작합니다. ANTLR4가 이 대안 중 하나를 고르려면 x 다음의 y 또는 z까지 봅니다. 장림은 우선 공통인 x를 Shift합니다. 그 결과 한 상태 안에 다음 두 LR 아이템이 함께 남습니다.

S → x · y
S → x · z

·는 현재 읽은 위치입니다. 두 아이템은 한 상태가 기억하는 문법 정보입니다. 실제 실행한 액션은 x에 대한 Shift 하나이고, 실제 파서 스택도 하나입니다. 다음 토큰이 y면 y를 Shift하고, z면 z를 Shift하면 됩니다.

왜 ε Reduce 충돌도, 추가 예측도 없을까요?
현재 상태에서 두 대안 모두 같은 x Shift 액션을 요구합니다. 다음 상태에서도 y와 z는 서로 다른 테이블 칸으로 구별됩니다. 매 순간 실행할 액션을 하나로 정할 수 있으므로 기존 LALR(1) 테이블로 충분합니다.

읽는 순서를 단계별로 보기

미리 살펴본 토큰실제로 읽은 토큰

이 문법의 동작을 풀어 쓴 설명용 단계입니다. 각 열의 순서를 비교합니다. 처리 시간은 별도로 측정해야 합니다. 입력 토큰 수는 x와 y 또는 z를 세며, EOF는 입력 종료 표시입니다.

입력 x y의 전체 읽기 순서

이 비교는 위 문법을 그대로 정의한 경우의 읽는 순서입니다. ANTLR 문법을 s : 'x' ('y' | 'z');처럼 공통 부분 밖으로 묶으면, ANTLR도 x를 읽은 뒤 y와 z를 선택할 수 있습니다. 문법을 어떻게 작성했는지도 선택 시점에 영향을 줍니다.

03 · 용어를 구별하는 이유

선택지가 있다는 것과 테이블 액션이 충돌한다는 것은 다릅니다

대안 선택 지점

어느 규칙을 실행할지 고르는 곳입니다. |로 나뉜 대안, 선택 구간 ?의 실행·건너뛰기, 반복 *·+의 계속·종료 판단 등이 여기에 들어갑니다.

장림에서 말하는 LR 충돌

같은 상태와 같은 다음 토큰으로 조회한 테이블 칸에 액션 후보가 여러 개 있는 상황입니다. 대표적으로 Shift/Reduce 충돌과 Reduce/Reduce 충돌을 구별합니다.

S : 'x' 'a'
  | 'y' 'b' ;

이 문법도 대안 선택 지점이 있습니다. 하지만 첫 토큰이 x면 첫 번째 대안, y면 두 번째 대안이므로 쉽게 고릅니다. ANTLR4는 이런 선택에 LA(1)을 확인하는 간단한 코드를 생성할 수 있습니다. 추가로 여러 토큰을 살펴봐야 하는 선택에는 adaptivePredict를 사용합니다.

왜 ANTLR의 선택 지점을 장림의 모든 LR 충돌과 같은 것으로 보면 헷갈릴까요? 앞의 x y | x z 문법처럼, LL에서 대안을 고르려고 미리 봐야 하는 문법을 LR은 충돌 없이 처리할 수 있기 때문입니다. 두 방식은 판단을 내리는 위치가 달라서 선택 지점과 충돌 지점이 일대일로 대응하지 않습니다.

이 예제에서 장림의 추가 예측이 줄어드는 이유는 설명할 수 있습니다. 전체 언어 문법에서 이런 경우가 차지하는 비중이나 성능 차이는 해당 문법으로 측정해야 합니다.

04 · 얼마나 미리 볼까요?

고정 k와 필요한 만큼 살펴보는 예측

LALR의 LA는 Look-Ahead입니다. LALR(1)은 현재 상태와 다음 토큰 한 개로 액션을 조회합니다. 여기서 LALR은 LR 상태와 lookahead 정보를 구성하는 특정 테이블 생성 방식의 이름입니다.

방식lookahead를 정하는 방법판단 위치
LALR(1)최대 한 토큰을 사용하는 테이블현재 상태 + 다음 토큰
LALR(k)테이블 생성 시 고정값 k를 정함현재 상태 + 최대 k개 토큰의 조합
ANTLR4의 ALL(*)입력에서 필요한 길이만큼 예측대안 선택 지점
장림의 추가 예측 설계기존 LALR(1) 셀의 후보를 후속 입력으로 비교조건절의 ε Reduce와 Shift가 겹치는 지점

왜 유한한 입력을 보는 것과 고정 k는 다를까요? 한 입력에서는 두 토큰으로 구별되고, 다른 입력에서는 천 토큰 뒤에 구별점이 있을 수 있습니다. 각 입력에서 실제로 읽는 양은 유한하며, 예측하는 길이는 그 입력의 구별점에 따라 달라집니다.

후보 A가 기다리는 구별점: b b b … b c
후보 B가 기다리는 구별점: b b b … b d

이 갈림길을 구별하려면 b들이 끝난 뒤의 c 또는 d까지 살펴봐야 합니다. ANTLR4는 k를 고정하지 않고 필요한 길이만큼 예측하며, 최악에는 남은 입력 전체를 볼 수 있습니다. 예측이 길어지면 시간과 메모리 사용량도 함께 고려해야 합니다.

끝까지 봐도 두 규칙이 같은 입력을 허용한다면?
추가 토큰으로 구별할 정보가 없으므로 모호성을 처리할 정책이 필요합니다. ANTLR4는 남은 대안 중 먼저 적힌 대안을 선택합니다. 장림의 추가 예측 설계에서도 명시적인 우선순위 또는 모호성 진단 정책을 정해야 합니다.

05 · 조건절이 들어오면

조건절의 ε Reduce가 공통 Shift와 겹치는 경우

조건절 내부 변환 · 설계안 
S : 'x' {Allow()}? 'y'
  | 'x' 'y' 'z' ;

조건절은 입력 토큰을 소비하지 않고 C# 검사 함수의 결과로 진행 가능 여부를 판단합니다. 논의 중인 변환 설계에서는 조건절을 검사 함수가 연결된 빈 규칙으로 표현합니다.

S → x GuardAllow y
S → x y z
GuardAllow → ε  [C# 검사 함수: Allow]

x를 읽고 다음 토큰 y를 볼 때, 첫 번째 대안은 먼저 GuardAllow를 ε Reduce해야 하고 두 번째 대안은 바로 y를 Shift할 수 있습니다. 두 액션이 같은 칸에 들어가므로 Shift/Reduce 충돌입니다.

같은 셀의 후보하는 일입력 소비
조건절의 ε ReduceAllow 검사 후 빈 규칙을 Reduce하고 Goto0개
Shift(y)현재 y를 읽고 다음 상태로 이동1개

왜 단순히 “true면 ε Reduce, false면 Shift”로 정하지 않을까요? Allow()가 true인 상태에서 입력이 x y z라면 첫 번째 대안으로 확정하게 됩니다. 첫 번째 규칙이 x y에서 끝나므로 남은 z 때문에 실패합니다. 두 번째 규칙은 이 입력을 받을 수 있는데, 일찍 확정하면서 그 가능성을 버린 겁니다.

조건을 이 경로가 허용되는가라는 검사로 쓰려면, 조건 통과와 최종 경로 선택을 구별해야 합니다. 조건에 경로 선택의 우선권까지 부여하려면 그 의미를 충돌 해결 정책으로 명시할 수 있습니다.

같은 예제를 ANTLR4가 처리하는 결과

ANTLR4 문법에서는 소문자 파서 규칙 s와 전체 입력 종료를 확인하는 start : s EOF;를 사용합니다. ANTLR 4.13.2와 Java 21로 다음 결과를 재현했습니다.

전체 입력Allow선택 경로결과조건 호출
x y EOFtrue첫 번째성공1회
x y EOFfalse첫 번째조건 실패1회
x y z EOFtrue두 번째성공0회
x y z EOFfalse두 번째성공0회

이 예제의 조건은 토큰 'x' 뒤에 있습니다. ANTLR4의 최초 대안 예측에서는 이 조건을 건너뛰고 입력의 문법 모양으로 대안을 구별합니다. 첫 번째 대안을 선택한 뒤 실제로 x를 읽었을 때 Allow()를 실행합니다. 두 번째 대안을 선택하면 첫 번째 대안의 조건은 실행되지 않습니다. ANTLR4의 조건 가시성 설명

위 호출 횟수는 ANTLR4의 해당 문법에서 측정한 값입니다. 장림의 추가 예측에서 C# 조건을 평가하는 시점과 호출 규약도 설계 항목으로 함께 정합니다.

06 · 기존 LR 구조를 살리는 보강

예측은 후보를 비교하고, 실제 파서는 한 액션을 실행합니다

장림의 추가 예측 · 설계안

이번에 논의한 적용 범위는 조건절이 붙은 ε Reduce와 Shift가 충돌하는 경우입니다. 기존 LALR(1) 테이블을 바탕으로, 이 셀에서 추가 예측기가 액션 하나를 고르게 합니다.

01 / 충돌 확인조건절 ε Reduce + Shift

어느 액션을 선택할지 기존 셀만으로 확정하기 어려운 지점을 찾습니다.

02 / 후보 예측필요한 만큼 lookahead

후보의 상태와 입력 위치를 비교하고 후속 입력으로 경로를 구별합니다.

03 / 실제 실행선택된 액션 하나

실제 파서 스택과 파스 트리는 선택한 경로 하나로 진행합니다.

왜 예측기와 실제 실행을 구분하나요? 후보를 비교하려면 예측 내부에서 여러 가능성을 추적해야 합니다. 이 단계에서 실제 트리나 사용자 액션까지 실행하면, 나중에 버릴 후보가 결과에 영향을 줄 수 있습니다. 예측은 상태와 입력을 바탕으로 판단하고, 실제 트리 구성과 액션 실행은 경로를 고른 뒤 수행하도록 분리합니다.

비교여러 후보를 진행하는 위치실제 파싱
GLR의 분기 처리파싱 중 여러 후보 스택을 유지여러 파싱 경로를 유지하며 실패·병합을 처리
ANTLR4의 ALL(*)대안을 선택하는 예측 단계선택한 대안 하나를 실행
장림의 추가 예측 설계특정 LR 충돌의 예측 단계선택한 액션 하나를 실행

이 설계에서는 실제 파싱의 단일 경로 실행을 유지합니다. 예측기 내부의 후보 비교에는 추가 계산이 필요합니다. EOF까지 여러 후보가 남으면 선택 정책을 적용하고, C# 검사 함수의 예측 중 평가 규약도 함께 정해야 합니다. 예측에서 사용할 조건은 입력 정보 등을 읽고 true 또는 false를 반환하는 순수 검사로 구성하는 방향입니다.

저자의 LR 구조를 보강하는 이유
공통 접두사를 한 상태로 처리하는 기존 LR 구조를 유지하면, 충돌 없이 처리되는 문법은 기존 테이블로 진행할 수 있습니다. 추가 판단이 필요한 조건절 충돌에 예측을 붙이는 설계는 이 기반을 활용하면서 조건절이 앞당긴 선택 문제를 해결하려는 것입니다.

07 · 근거와 재현

조건절 예제를 재현하는 ANTLR4 문법 펼치기

Choice.g4로 저장해 Java 파서를 생성합니다. 각 입력마다 새 파서의 allow 값을 지정하고 start()를 호출한 뒤 문법 오류 수와 predicateCalls를 확인합니다. 문법 오류 수가 0이면 위 표의 성공에 해당합니다.

grammar Choice;

@parser::members {
    public boolean allow = true;
    public int predicateCalls = 0;

    private boolean Allow() {
        predicateCalls++;
        return allow;
    }
}

start : s EOF ;
s : 'x' {Allow()}? 'y'
  | 'x' 'y' 'z'
  ;

WS : [ \t\r\n]+ -> skip ;

실행 환경: ANTLR 4.13.2 · Java 21. predicateCalls는 호출 시점을 관찰하는 실험용 계수입니다.
