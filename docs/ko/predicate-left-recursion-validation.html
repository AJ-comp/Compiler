PredicateLeftRecursionValidation 동작 문서

조건절을 거치는 좌재귀를
파싱 전에 검사합니다.

PredicateLeftRecursionValidation은 문법에서 조건절을 거친 뒤, 입력 토큰을 하나도 소비하지 않고 같은 규칙을 다시 참조할 수 있는 경로를 찾는 클래스입니다. 이런 경로가 있으면 파싱 테이블을 만들기 전에 문법 오류로 알립니다.

이 검사는 예측 계산이 같은 입력 토큰 앞에서 계속 늘어나는 문제를 막기 위해 필요합니다. 파서가 다음 동작을 고르려고 예측하는 동안, 입력을 처리하지 못한 채 계산만 계속 늘어날 수 있기 때문입니다.

이 클래스는 문제가 되는 규칙 이름과 조건 함수 이름, 참조 경로를 오류 정보에 담습니다. 사용자는 입력을 넣어 파싱을 실행하기 전에, 문법의 어느 부분을 고쳐야 하는지 확인할 수 있습니다.

먼저 이 클래스의 검사 기준을 예제로 살펴보겠습니다. 이어서 파싱 테이블과 예측 스택을 통해, 왜 이런 문법을 미리 검사하는지 설명하겠습니다.

1. 두 생성 규칙을 순서대로 살펴보겠습니다.

먼저 문법의 구성을 정하겠습니다.

다음과 같은 문법을 정의했다고 가정하겠습니다. 비단말 A를 정의하는 생성 규칙은 두 개입니다.

비단말 A의 생성 규칙
A : {Allow()}? A 'x'   // 규칙 1
  | 'x' ;                 // 규칙 2

규칙 1은 조건절 {Allow()}?, 비단말 A에 대한 참조, 마지막 'x'로 구성됩니다. 규칙 2는 'x' 하나로 구성됩니다. 문법에 적힌 'x'는 입력 토큰 x 하나를 뜻합니다.

입력으로 x x가 들어온다고 가정하겠습니다.

각 생성 규칙의 동작을 살펴보기 위해, 입력으로 x x가 들어왔다고 가정하겠습니다. Allow 함수는 참을 반환한다고 가정하겠습니다. 파서는 아직 첫 번째 x 토큰을 소비하지 않은 상태입니다.

두 규칙 모두 이 상태에서 시작하는 경우를 따로 살펴보겠습니다. 먼저 규칙 1을 설명하고, 그다음 규칙 2를 설명하겠습니다.

규칙 1에서는 조건을 검사한 뒤, A 규칙을 다시 참조하고 x를 하나 더 받습니다.

A : {Allow()}? A 'x' ;

먼저 {Allow()}?로 조건을 검사합니다. 이 표기는 C#에 등록한 Allow 함수를 호출합니다. 지금은 Allow가 참을 반환한다고 가정했으므로 조건절을 통과합니다.

조건 검사는 입력 토큰을 소비하지 않습니다. 따라서 조건 검사를 마친 뒤에도 입력 x x는 그대로 남아 있고, 다음에 처리할 토큰은 첫 번째 x입니다.

Allow() 조건절 다음의 A는 같은 비단말 A에 대한 참조입니다. 마지막 'x'를 처리하려면, 먼저 그 앞의 A에 해당하는 입력을 처리해야 합니다. 즉, 마지막 x를 읽기 전에 같은 A 규칙을 다시 참조합니다.

이 클래스가 확인하는 구간은 A 규칙에서 출발해 Allow 조건절을 거친 뒤, 다시 A 규칙을 참조하기 전까지입니다. 이 구간에서는 입력 토큰을 하나도 소비하지 않습니다. 이 경로가 이 클래스에서 검사하는 조건절을 거치는 좌재귀입니다.

규칙 1의 검사 결과: 오류. 조건절을 거친 뒤, 토큰 소비 없이 같은 A 규칙을 다시 참조할 수 있습니다.

그래서 이 클래스는 문제가 된 규칙 이름과 조건 함수 이름, 참조 경로를 다음 오류 정보에 담아 알려줍니다.

RuleName:      A
PredicateName: Allow
RulePath:      A → A

즉, A 규칙에서 Allow 조건절을 거쳐 다시 A 규칙으로 돌아오는 경로를 수정해야 한다는 뜻입니다.

규칙 2에서는 입력 토큰 x 하나를 받습니다.

A : 'x' ;

이번에는 규칙 2를 살펴보겠습니다. 시작할 때의 입력은 똑같이 x x입니다.

규칙 2는 'x' 하나로 끝납니다. 따라서 첫 번째 x 토큰 하나를 소비하면 이 생성 규칙의 처리가 끝나고, 입력에는 두 번째 x가 남습니다.

규칙 2 자체의 검사 결과: 통과. 이 생성 규칙에는 조건절과 재귀 참조가 없습니다.

두 생성 규칙을 살펴본 결과, 이 문법은 규칙 1에서 발견한 경로 때문에 문법 오류로 처리됩니다. 다음 절에서는 바로 이 경로를 따라가며, 파서가 첫 동작을 고르기 위해 예측할 때 어떤 문제가 생기는지 설명하겠습니다.

2. 규칙 1의 경로가 파서의 예측 계산에서 왜 문제가 되는지 살펴보겠습니다.

앞에서 규칙 1은 Allow() 조건절을 검사한 뒤, 입력 토큰을 소비하지 않고 같은 A 규칙을 다시 참조한다는 점을 확인했습니다. 이 절에서는 이 경로 때문에 파서의 예측 계산이 어떻게 반복될 수 있는지 설명하겠습니다.

그 과정을 따라가 보기 위해, 여기서는 문법 검사를 생략하고 같은 문법으로 장림의 LALR 파싱 테이블을 만들었다고 가정하겠습니다. 입력은 앞에서 정한 x x이고, Allow는 계속 참을 반환합니다. 파서는 아직 첫 번째 x 토큰을 소비하지 않은 상태입니다.

이 첫 번째 x 앞에서 규칙 1 쪽으로 진행하려면, Allow() 조건절부터 처리해야 합니다. 규칙 2 쪽으로 진행하려면, 입력 토큰 x 하나를 바로 소비해야 합니다. 지금은 Allow가 참이므로 두 동작 모두 가능합니다.

장림은 각 동작으로 시작했을 때의 진행을 예측해, 실제로 실행할 첫 동작을 고릅니다. 그런데 규칙 1 쪽을 예측하면, 입력 토큰을 소비하기 전에 Allow() 조건절을 처리하고 A를 다시 참조하는 계산이 반복될 수 있습니다.

장림의 LR 파서는 파싱 테이블에 적힌 액션을 따라 진행합니다. 따라서 이 계산이 왜 반복되는지 확인하려면, 먼저 Allow() 조건절이 테이블에서 어떤 액션으로 표현되는지 알아야 합니다.

먼저 Allow() 조건절을 파싱 테이블에서 표현하는 방법을 살펴보겠습니다.

앞에서 확인했듯이 Allow() 조건절은 입력 토큰을 소비하지 않습니다. 장림은 이 동작을 오른쪽이 비어 있는 생성 규칙으로 표현합니다. 이를 ε 생성 규칙이라고 부릅니다.

이 조건절을 테이블 안에서 가리킬 수 있도록, 조건절을 나타내는 비단말에 설명용 이름 P를 붙이겠습니다. 그러면 규칙 1의 {Allow()}? 자리는 P로 바뀌고, 그 조건절의 처리는 P → ε로 표현됩니다.

조건절을 비단말 P로 나타낸 문법
A → P A 'x'   // 규칙 1
A → 'x'       // 규칙 2
P → ε         // Allow가 참일 때 Reduce 허용

P → ε의 오른쪽은 비어 있습니다. 이 생성 규칙을 Reduce하는 것이 Allow() 조건절을 처리하는 동작이며, 입력 토큰을 소비하지 않으므로 입력 위치는 그대로입니다. 이후에 나오는 “규칙 1 쪽의 ε Reduce”는 바로 이 조건절 처리를 뜻합니다.

이제 첫 번째 x 앞에서 두 동작이 테이블에 어떻게 나타나는지 확인하겠습니다.

설명용 상태 이름으로, 시작 상태를 I0, P를 처리한 뒤의 상태를 I1이라고 부르겠습니다.

규칙 1의 조건절 처리는 P → ε의 Reduce로 나타납니다. 규칙 2의 x 토큰 소비는 Shift로 나타납니다. 앞에서 살펴본 두 동작이 테이블에서는 같은 상태 I0와 입력 토큰 x에 대한 두 액션으로 함께 들어가는 것입니다. 이것이 이 예제의 ε Reduce / Shift 충돌입니다. 다시 말해, 같은 상태에서 현재 입력 토큰을 보았을 때 조건절의 ε Reduce로 시작하는 경로와 Shift로 시작하는 경로가 모두 가능하다면, Shift / ε Reduce 충돌은 반드시 발생합니다.

ACTION[I0, x] = { Shift, ε Reduce }

예측기는 실제 파서의 복사본으로 두 액션을 비교합니다.

이처럼 같은 테이블 칸에 두 액션이 남아 있으면, 그 칸만 보고는 실행할 액션 하나를 고를 수 없습니다. 그래서 장림은 각 액션으로 진행하는 경우를 미리 계산하는 예측기를 호출합니다.

이 예제의 충돌은 Shift 하나와 조건절의 ε Reduce 하나로 이루어져 있어, 장림 예측기가 지원하는 형태에 해당합니다. 코드에서는 LRConflictPredictor.IsSupportedConflict()가 원래 테이블 칸이 이 형태인지 확인합니다. 조건 검사 뒤에도 두 액션이 모두 남아 있으면 SelectFirstAction()이 예측을 시작합니다.

이때 두 경우를 따로 계산하기 위해, 예측기는 실제 파서의 상태 스택과 입력 위치를 복사합니다. ε Reduce로 시작하는 복사본과 Shift로 시작하는 복사본이 각각 예측 후보입니다.

예측 중에는 실제 파서의 스택과 입력 위치를 바꾸지 않습니다. 예측기가 첫 액션 하나를 고른 뒤에, 실제 파서가 그 액션을 실행합니다. 아래에서는 문제가 되는 ε Reduce 쪽 후보를 계속 따라가겠습니다.

ε Reduce 쪽 후보는 입력을 소비하지 않고 I1에 도달합니다.

이 후보의 시작 스택은 [I0]입니다. P → ε를 Reduce할 때는 오른쪽 기호 수가 0개이므로 스택에서 제거할 상태도 0개입니다.

이어서 GOTO[I0, P] = I1에 따라 I1을 스택에 추가합니다.

ε Reduce 쪽 후보의 시작 스택
[I0]

P를 ε Reduce한 뒤 Goto
[I0, I1]

입력 위치: 0
다음 입력 토큰: 첫 번째 x

여기서 처리한 것은 조건절 P입니다. 따라서 입력 x x는 그대로 남아 있습니다.

이 후보는 상태 I1에 도달했습니다. 다음 절에서는 I1의 테이블 항목을 확인하고, 여기서도 ε Reduce를 선택하면 스택이 어떻게 변하는지 살펴보겠습니다.

3. I1에서 ε Reduce와 Goto를 반복하면, 입력 위치는 그대로이고 스택만 길어집니다.

I1에서도 같은 충돌이 생기는 이유부터 확인하겠습니다.

방금 P를 처리했으므로, I1에는 A → P · A 'x'라는 아이템이 있습니다. 점 뒤의 A에 해당하는 입력을 다음에 처리해야 하는 상태입니다.

점 뒤에 비단말 A가 있으므로 closure에는 A를 시작하는 아이템들도 들어갑니다. 관련 아이템을 모으면 다음과 같습니다. 여기서는 점의 위치에 집중할 수 있도록 룩어헤드 표기를 생략했습니다.

A → P · A 'x'
A → · P A 'x'
A → · 'x'
P → ·

A → · P A 'x'에서 P를 처리할 수 있고, P → ·에 따라 다시 ε Reduce할 수 있습니다. 동시에 A → · 'x'에서는 x를 Shift할 수 있습니다.

따라서 I1에서도 첫 번째 x를 보았을 때 두 액션이 충돌합니다. 여기서 다시 P를 처리하면 A → P · A 'x'까지 진행한 아이템이 만들어집니다. 점 뒤에 A가 있으므로 같은 closure 계산을 거쳐 다른 아이템들도 다시 추가됩니다. 그 결과 이 예제의 파싱 테이블에서는 Goto 상태가 다시 I1입니다.

ACTION[I1, x] = { Shift, ε Reduce }

ε Reduce를 반복하는 동안 I1이 스택에 계속 쌓입니다.

예측기가 여기서도 ε Reduce 쪽을 계산한다고 가정하겠습니다. 스택에서 제거할 상태는 0개이고, GOTO[I1, P] = I1에 따라 I1을 하나 더 추가합니다. 같은 동작을 반복하면 다음과 같습니다.

시작
[I0]

조건절을 1번 처리한 뒤
[I0, I1]

조건절을 2번 처리한 뒤
[I0, I1, I1]

조건절을 3번 처리한 뒤
[I0, I1, I1, I1]

모든 단계의 입력 위치: 0
모든 단계의 다음 토큰: 첫 번째 x

첫 번째 ε Reduce 이후에는 스택 맨 위가 계속 I1이고, 다음 입력 토큰도 같은 x입니다. 그러나 스택 전체는 매번 길어집니다. x를 Shift하지 않았으므로 입력 위치도 0에 그대로 있습니다.

스택에 I1이 하나씩 추가되는 동안, 문법에서는 Allow() 조건절을 처리한 뒤 A 규칙을 다시 참조하는 구간을 반복해서 따라가고 있습니다. 즉, 앞의 스택 변화를 원래 문법의 참조 관계로 그리면 다음과 같습니다.

A
└─ Allow → A
           └─ Allow → A
                      └─ Allow → A
                                 …

아직 읽지 않은 다음 토큰: x
소비한 입력 토큰:        0개

이 경로 때문에 예측기가 처리할 스택과 후보가 계속 늘어납니다.

이 반복이 예측에 미치는 영향을 이해하려면, 예측기가 후보들을 어디까지 계산한 뒤 비교하는지 알아야 합니다. LRConflictPredictor는 두 시작 동작 가운데 어느 쪽으로 계속 진행할 수 있는지 비교하기 위해, 후보들을 토큰 하나를 Shift한 지점까지 진행시킵니다. 그 계산을 담당하는 AdvanceOneToken()은 Shift에 도달하기 전에 가능한 Reduce와 Goto를 먼저 계산합니다.

그런데 앞에서 확인한 반복 경로에서는 ε Reduce 쪽으로 더 깊은 스택을 계속 만들 수 있습니다. 깊어진 스택에서도 Shift 쪽 후보가 생깁니다. 따라서 첫 번째 x 앞에서 계산할 스택과 후보가 계속 늘어나, Shift한 후보들을 비교하는 단계로 넘어가지 못할 수 있습니다.

예측기는 이미 계산한 후보를 다시 계산하지 않도록 중복 검사를 합니다. 이때 입력 위치와 상태 스택 전체를 함께 봅니다. 그런데 [I0, I1]과 [I0, I1, I1]은 서로 다른 스택이므로, 스택 맨 위가 같다는 이유로 합칠 수 없습니다.

이처럼 서로 다른 스택을 계속 계산하면, 스택 깊이와 후보 수, 액션 전이 횟수도 늘어납니다. 그중 하나가 예측기의 자원 한도에 도달할 수 있습니다. 장림은 그때 예측을 중단하고 오류를 알립니다.

PredicateLeftRecursionValidation은 이 문제가 파싱 중에 나타나기 전에, 조건절을 거쳐 토큰 소비 없이 같은 규칙을 다시 참조하는 문법 경로를 찾아 오류로 알려줍니다.

4. 검사 기준을 통과하는 문법도 같은 순서로 살펴보겠습니다.

앞 예제에서는 Allow() 조건절을 거쳐 같은 A 규칙을 다시 참조할 때까지 입력 토큰을 소비하지 않았습니다. 그래서 이 클래스가 해당 경로를 오류로 처리했습니다. 반대로 이런 경로가 없는 문법은 검사를 통과합니다. 다음 세 예제에서 어떤 차이가 있는지 살펴보겠습니다.

첫 번째 예제는 조건절이 없는 일반 좌재귀입니다.

A : A 'x'   // 규칙 1
  | 'x' ;   // 규칙 2

규칙 1은 A 규칙에 해당하는 입력을 처리한 뒤 x를 하나 더 받습니다. 장림의 LR 파서는 이렇게 인식한 A와 다음 x를 묶어 다시 A로 Reduce할 수 있습니다.

규칙 2는 x 토큰 하나를 받아 A로 인식하는 기본 규칙입니다.

두 생성 규칙 모두 조건절을 포함하지 않습니다. 따라서 조건절을 거쳐 같은 A 규칙으로 돌아오는 경로도 없습니다.

검사 결과: 통과. 일반 좌재귀를 그대로 사용할 수 있습니다.

두 번째 예제는 재귀 참조 뒤에 조건절이 있습니다.

A : A {Allow()}? 'x'   // 규칙 1
  | 'x' ;                 // 규칙 2

규칙 1은 먼저 A 규칙에 해당하는 입력을 처리합니다. 그다음 Allow 조건을 검사하고, 조건절을 통과하면 x를 하나 더 받습니다.

규칙 2는 x 토큰 하나를 받습니다.

이 문법에는 조건절이 있지만, A에서 다시 A를 참조하기 전까지의 구간에는 조건절이 없습니다. 조건절은 그 A를 처리한 뒤에 나옵니다.

검사 결과: 통과. 조건절을 거쳐 A를 다시 참조하는 경로가 없습니다.

세 번째 예제는 재귀 참조 전에 x를 반드시 소비합니다.

A : 'x' {Allow()}? A   // 규칙 1
  | 'x' ;               // 규칙 2

규칙 1은 먼저 x를 소비하고, 이어서 Allow 조건을 검사합니다. 조건절을 통과하면 같은 A 규칙을 다시 참조합니다. 이 A를 참조할 때는 이미 x 토큰 하나를 소비한 상태입니다.

규칙 2는 x 토큰 하나를 받습니다.

따라서 규칙 1을 통해 A를 다시 참조할 때마다 입력 위치가 앞으로 이동합니다.

검사 결과: 통과. 재귀 참조 전에 토큰 소비가 보장됩니다.

여기까지는 조건절과 토큰의 위치가 A의 생성 규칙에 직접 드러나는 경우를 살펴보았습니다. 하지만 A가 다른 비단말을 거쳐 돌아오거나 앞의 토큰을 생략할 수 있다면, 그 참조 경로도 따라가야 합니다. 다음 절에서는 이런 경우에 같은 검사 기준을 적용하겠습니다.

5. 다른 비단말과 선택적 토큰을 거치는 경로를 살펴보겠습니다.

첫 번째 예제는 B를 거쳐 다시 A를 참조합니다.

A : B 'x'   // A의 규칙 1
  | 'x' ;   // A의 규칙 2

B : {Allow()}? A ;

A에는 생성 규칙이 두 개 있고, B에는 하나가 있습니다. 먼저 A의 규칙 1에서 시작하는 경로를 살펴보겠습니다.

A의 규칙 1은 B를 먼저 처리하고, 그다음 x를 받습니다. B는 Allow 조건을 검사한 뒤 A를 다시 참조합니다. 따라서 B에서 A를 다시 참조할 때까지, A의 규칙 1 끝에 있는 x를 소비하지 않습니다.

이 경로에서 진행한 것은 A → B → Allow 조건 검사 → A입니다. 조건 검사는 입력을 소비하지 않으므로, 같은 A를 다시 참조하기 전까지 소비한 토큰은 0개입니다.

A의 규칙 2는 x 토큰 하나를 받는 기본 규칙입니다. 이 생성 규칙에는 조건절과 재귀 참조가 없습니다.

문법의 검사 결과: 오류. A의 규칙 1에서 B를 거쳐 돌아오는 경로가 조건절을 거치는 무소비 좌재귀입니다.

두 번째 예제는 앞의 x를 생략할 수 있습니다.

A : 'x'? {Allow()}? A 'x'   // 규칙 1
  | 'x' ;                      // 규칙 2

규칙 1은 선택적인 x, 조건절, A 참조, 마지막 x로 구성됩니다. 처음의 'x'?는 x를 한 번 받거나 생략할 수 있다는 뜻입니다.

처음의 x를 받는 경로에서는 토큰을 하나 소비한 뒤 조건절과 A 참조로 진행합니다.

처음의 x를 생략하는 경로에서는 토큰을 소비하지 않고 Allow 조건을 검사합니다. 이어서 같은 A 규칙을 다시 참조하므로, 이 경로에는 토큰 소비가 없습니다. 마지막 x는 그 A 참조 뒤에서 처리합니다.

규칙 2는 x 토큰 하나를 받는 기본 규칙입니다.

문법의 검사 결과: 오류. 규칙 1에서 처음의 x를 생략하면, 조건절을 거쳐 토큰 소비 없이 같은 A 규칙으로 돌아올 수 있습니다.

세 번째 예제는 조건절이 A의 재귀 경로 밖에 있습니다.

S : {Allow()}? A 'y' ;

A : A 'x'   // A의 규칙 1
  | 'x' ;   // A의 규칙 2

S는 Allow 조건을 검사한 뒤 A를 처리하고, 마지막으로 y를 받습니다.

A의 규칙 1은 A를 다시 참조한 뒤 x를 하나 더 받습니다. 이 재귀 경로에는 조건절이 없습니다.

A의 규칙 2는 x 토큰 하나를 받습니다.

따라서 A의 재귀를 반복해도 S에 있는 Allow 조건절을 다시 거치지 않습니다. 조건절이 있는 S → A 참조와 A의 재귀 경로는 구분해서 검사합니다.

검사 결과: 통과. 조건절이 같은 비단말로 돌아오는 경로에 포함되지 않습니다.

다른 비단말을 거치는 경로를 따라갈 때는, 그 비단말에 생성 규칙이 여러 개 있을 수도 있습니다. 그러면 조건절을 거치는 경로와 토큰을 소비하지 않는 경로가 서로 다를 수 있으므로, 두 정보가 같은 경로에서 나오는지 함께 확인해야 합니다.

6. 한 경로의 조건절과 토큰 소비를 함께 확인합니다.

이 점을 확인하기 위해, 다음 예제에서는 B의 두 생성 규칙을 하나씩 살펴보겠습니다. 각 규칙에서 조건절을 거치는지와, 같은 A를 다시 참조하기 전에 토큰을 소비하는지를 함께 확인하겠습니다.

먼저 A와 B의 구성을 확인하겠습니다.

A : B A 'x'   // A의 규칙 1
  | 'x' ;     // A의 규칙 2

B : {Allow()}? 'z'   // B의 규칙 1
  | 'q'? ;             // B의 규칙 2

A의 규칙 1은 B를 처리한 뒤 A를 다시 참조하고, 마지막으로 x를 받습니다. 따라서 A를 다시 참조하기 전까지 토큰을 소비하는지는 B의 처리 결과에 달려 있습니다. A의 규칙 2는 x 토큰 하나를 받는 기본 규칙입니다.

B의 규칙 1은 조건을 검사한 뒤 z를 반드시 소비합니다.

B의 규칙 1인 {Allow()}? 'z'는 먼저 Allow 조건을 검사합니다. 조건절을 통과한 뒤에는 z 토큰 하나를 소비해야 B의 처리가 끝납니다.

따라서 이 경로에는 조건절이 있지만, A를 다시 참조할 때는 이미 z를 소비한 상태입니다.

B의 규칙 2는 q를 생략할 수 있지만 조건절이 없습니다.

B의 규칙 2인 'q'?는 q를 한 번 받거나 생략할 수 있습니다. q를 생략하면 토큰 소비 없이 B의 처리가 끝납니다. 하지만 이 생성 규칙에는 조건절이 없습니다.

두 경로의 결과를 합쳐 검사하겠습니다.

B에서 사용하는 생성 규칙같은 A를 다시 참조하기 전의 결과
{Allow()}? 'z'조건절을 거치지만 z를 반드시 소비합니다.
'q'?토큰을 소비하지 않을 수 있지만 조건절을 거치지 않습니다.

어느 경로에도 조건절을 거치면서 토큰 소비 없이 A를 다시 참조하는 경우가 없습니다. 한 생성 규칙의 조건절과 다른 생성 규칙의 무소비 경로를 섞어서 판단하면 결과가 잘못됩니다.

검사 결과: 통과. 조건절과 토큰 소비를 각각 같은 경로에서 확인합니다.

이번에는 B가 조건절만 처리하고 끝날 수 있도록 바꾸겠습니다.

앞 예제의 B는 조건절을 사용하는 경로에서 z를 반드시 소비했습니다. 이제 B를 다음처럼 바꿔, 조건절만 검사한 뒤 토큰 소비 없이 끝날 수 있게 하겠습니다.

A : B A 'x'   // A의 규칙 1
  | 'x' ;     // A의 규칙 2

B : ({Allow()}?)? ;

A의 구성은 그대로입니다. A의 규칙 1에서는 B를 처리한 뒤 A를 다시 참조하고, 마지막으로 x를 받습니다. A의 규칙 2는 x 토큰 하나를 받습니다.

달라진 부분은 B입니다. {Allow()}?의 물음표는 조건절 표기의 일부이고, 바깥 괄호 뒤의 물음표는 그 조건절을 한 번 사용하거나 생략할 수 있다는 뜻입니다.

조건절을 생략하면, B는 조건 검사와 토큰 소비 없이 끝납니다.

반면 조건절을 사용하고 Allow가 참을 반환하는 경우에는, B가 조건만 검사한 뒤 끝납니다. 이 경로에서는 조건절을 거쳤지만 입력 토큰을 소비하지 않았습니다. 이어서 A를 다시 참조할 때도 입력 위치는 그대로입니다.

검사 결과: 오류. B에서 조건절을 사용하는 경로를 따라가면, 조건절을 거쳐 토큰 소비 없이 같은 A를 다시 참조할 수 있습니다.

이 차이를 구분하기 위해 검사 클래스는 토큰 없이 끝날 수 있는 경로와, 그 경로에서 거치는 조건절을 함께 기록합니다. 다음 절에서 이 분석 순서를 살펴보겠습니다.

7. 검사 클래스가 문법을 분석하는 순서를 살펴보겠습니다.

앞 절에서는 B가 토큰 없이 끝날 수 있는지와, 그 경로에 조건절이 있는지를 함께 확인했습니다. 검사 클래스도 이 두 정보를 먼저 계산합니다. 그런 다음 그 정보를 이용해 비단말의 참조를 연결하고, 출발점으로 돌아오는 경로를 찾습니다.

이 검사는 조건 함수를 호출하지 않고 문법 구조를 분석합니다. 조건절을 통과할 수 있다고 보고 가능한 참조 경로를 확인합니다. 검사 결과는 문법에 해당 경로가 존재하는지에 따라 결정됩니다.

검사 기준은 세 단계로 정리할 수 있습니다.

  1. 1.
    조건절이 포함된 좌재귀 경로를 찾습니다.

    한 비단말에서 출발해 조건절을 거친 뒤, 같은 비단말을 다시 참조하는 경로를 찾습니다.

  2. 2.
    그 경로를 토큰 소비 없이 지날 수 있는지 확인합니다.

    같은 비단말을 다시 참조하기 전까지, 입력 토큰을 반드시 소비하는 부분이 있는지 확인합니다.

  3. 3.
    조건절을 거쳐 토큰 소비 없이 돌아올 수 있으면 오류로 알립니다.

    문제가 되는 규칙 이름과 조건 함수 이름, 참조 경로를 오류 정보에 담습니다.

코드에서는 이 기준을 다음 다섯 단계로 계산합니다.

  1. 정의된 비단말과 생성 규칙을 모읍니다.

    A와 B 같은 비단말의 생성 규칙을 하나씩 읽습니다. 시작 규칙에서 사용하지 않는 비단말도 검사 대상에 포함합니다.

  2. 토큰 없이 끝날 수 있는 경로를 계산합니다.

    이렇게 모은 생성 규칙을 바탕으로, AnalyzeEmptyPaths()는 토큰 없이 끝날 수 있는 규칙(nullable)을 찾습니다. 그 경로에 있는 조건 함수 이름도 함께 기록합니다.

    다른 비단말의 결과가 필요한 경우에는 새 정보를 반영해 다시 계산합니다. 더 이상 정보가 바뀌지 않으면 이 단계를 마칩니다.

  3. 첫 토큰을 소비하기 전에 참조할 수 있는 비단말을 연결합니다.

    BuildLeftCornerEdges()는 앞 단계에서 구한 빈 경로 정보를 이용해, 각 생성 규칙의 왼쪽부터 첫 토큰을 소비하기 전에 참조할 수 있는 비단말을 찾습니다. A : {Allow()}? B 'x' ;에서는 토큰 소비 없이 B를 참조할 수 있으므로 A → B를 기록합니다. 이 연결에는 B 앞에서 Allow 조건절을 거쳤다는 정보도 붙입니다.

    A : 'x' B ;에서는 B를 참조하기 전에 x를 반드시 소비합니다. 따라서 토큰 소비 없는 A → B 연결을 만들지 않습니다.

  4. 조건절을 거친 연결에서 출발점으로 돌아오는 길을 찾습니다.

    앞 단계에서 조건절을 거친 A → B 연결을 찾았다면, FindReturnPath()는 B에서 A로 돌아오는 길도 있는지 확인합니다.

    이 단계의 연결들은 모두 첫 토큰을 소비하기 전의 참조입니다. 따라서 A로 돌아오는 길이 있으면, 조건절을 거쳐 토큰 소비 없이 같은 A를 다시 참조하는 경로가 완성됩니다. 방문 기록을 사용해 같은 연결을 끝없이 탐색하지 않습니다.

  5. 고쳐야 할 규칙과 경로를 오류 정보에 담습니다.

    이렇게 출발점으로 돌아오는 경로가 발견되면, CreateException()은 규칙 이름과 조건 함수 이름, 참조 순서를 PredicateLeftRecursionException에 담습니다.

문법 분석은 여기서 끝납니다. 다음 절에서는 이 검사가 언제 호출되고, 발생한 오류가 사용자에게 어떻게 전달되는지 살펴보겠습니다.

8. 검사 시점과 오류 전달 방식을 살펴보겠습니다.

검사는 파싱 테이블을 만들기 전에 실행됩니다.

EBNF 파일로 구성한 문법과 C# 트리식으로 구성한 문법은 모두 Grammar.Optimization()에서 공통 검사를 거칩니다. 이 메서드는 먼저 입력 진행을 검사하고, 이어서 조건절을 거치는 좌재귀를 검사합니다.

EBNF 또는 C# 트리식으로 문법 구성
↓
Grammar.Optimization()에서 문법 준비
↓
GrammarProgressValidation 검사
↓
PredicateLeftRecursionValidation 검사
↓
검사를 통과한 문법을 내부 형태로 정리
↓
파싱 테이블 생성

PredicateLeftRecursionValidation이 조건절을 거치는 무소비 좌재귀 경로를 발견하면, PredicateLeftRecursionException이 발생합니다. 예외에는 규칙 이름, 조건 함수 이름, 참조 경로가 들어 있습니다. 여러 비단말을 거치는 문법이라면 RulePath에 그 참조 순서도 들어갑니다. 이 정보가 사용자에게 전달되는 방식은 문법을 구성한 방법에 따라 달라집니다.

EBNF 파일을 읽은 경우에는 읽기 결과의 오류 목록으로 전달됩니다.

EBNF 리더는 문법을 준비하다가 발생한 이 오류를 읽기 결과의 오류 목록에 추가합니다. 사용자는 문법 읽기 결과에서 문제가 되는 규칙과 경로를 확인할 수 있습니다.

C# 트리식으로 구성한 경우에는 예외로 전달됩니다.

C# 코드에서 문법을 구성했다면, 문법을 준비하는 코드에서 PredicateLeftRecursionException을 받습니다. 호출한 코드는 예외의 규칙 이름과 조건 함수 이름, 참조 경로를 사용자에게 표시할 수 있습니다.

어느 방식으로 문법을 구성했든, 입력을 넣어 파싱을 실행하기 전에 수정할 문법 경로를 확인할 수 있습니다. 앞의 검사 순서에는 GrammarProgressValidation과 이번 클래스가 함께 있었습니다. 둘 다 토큰 소비와 관련된 문제를 검사하지만, 확인하는 구간이 다릅니다. 마지막으로 이 차이를 살펴보겠습니다.

9. 기존 입력 진행 검사와 이번 검사의 담당 범위를 구분하겠습니다.

먼저 기존 검사가 처리하는 반복과 순환을 살펴보겠습니다. 그 설명을 마친 뒤, 이번 클래스가 추가로 확인하는 구간을 설명하겠습니다.

기존 검사는 반복 한 번을 마쳐도 토큰을 소비하지 않을 수 있는 문법을 막습니다.

S : ({Allow()}?)* 'y' ;

이 문법의 반복 내용은 Allow 조건절 하나입니다. Allow가 계속 참이라고 가정하면, 조건절을 한 번 처리한 뒤에도 입력 위치가 그대로입니다. 따라서 같은 입력 위치에서 반복을 계속할 수 있습니다.

*와 +는 모두 여러 번 반복할 수 있으므로, 반복 내용을 한 번 완료할 때마다 토큰 소비를 요구합니다. EBNF 문법을 구성할 때는 EbnfRepetitionValidation이 이 조건을 확인하고, 공통 문법에서는 GrammarProgressValidation이 반복 내용을 확인합니다.

검사 결과: 오류. 조건절만 처리하는 반복은 입력 토큰을 소비하지 않습니다.

반복 내용에 필수 토큰 x를 넣으면 입력이 앞으로 진행합니다.

S : ('x' {Allow()}?)* 'y' ;

이번 문법은 x를 받은 뒤 Allow 조건을 검사하는 순서로 반복합니다. 반복을 한 번 완료하려면 x를 반드시 소비해야 합니다.

따라서 반복할 때마다 입력 위치가 앞으로 이동합니다.

검사 결과: 통과. 한 번의 반복에 토큰 소비가 보장됩니다.

기존 검사는 재귀를 한 번 더 사용해도 필수 토큰이 추가되지 않는 조건절 순환도 막습니다.

조건 검사를 되풀이하는 방법에는 재귀 참조도 있습니다. 이 경우에도 토큰 소비 없이 같은 조건 검사를 반복할 수 있으므로, 기존 검사는 다음 형태도 확인합니다.

A : {Allow()}? A   // 규칙 1
  | 'x' ;             // 규칙 2

규칙 1은 Allow 조건을 검사하고 A를 다시 참조합니다. 이 생성 규칙에는 조건절과 A 참조만 있으므로, 재귀를 한 번 더 사용해도 필수로 받아야 할 입력 토큰이 추가되지 않습니다.

규칙 2는 x 토큰 하나를 받는 기본 규칙입니다.

검사 결과: 오류. GrammarProgressValidation이 토큰을 추가하지 않는 조건절 순환으로 처리합니다.

이번 클래스는 뒤쪽에 x가 있어도, A를 다시 참조하기 전까지의 구간을 따로 확인합니다.

방금 본 순환 예제의 규칙 1에는 조건절과 A 참조만 있었습니다. 이제 그 A 참조 뒤에 필수 토큰 x를 하나 추가해 보겠습니다.

A : {Allow()}? A 'x'   // 규칙 1
  | 'x' ;                 // 규칙 2

규칙 1에는 A 참조 뒤에 필수 토큰 x가 있습니다. 따라서 규칙 1을 한 번 더 사용하면, 전체 입력에 필요한 x가 하나 더 추가됩니다. 그래서 이 문법은 GrammarProgressValidation의 무소비 순환 검사를 통과합니다.

그러나 같은 A를 다시 참조하기 전까지는 Allow 조건만 검사합니다. 뒤쪽 x는 아직 처리하지 않았으므로, 이 앞부분의 입력 위치는 그대로입니다.

규칙 2는 x 토큰 하나를 받는 기본 규칙입니다.

앞에서 파싱 테이블로 확인한 ε Reduce와 Goto 반복은 이 앞부분에서 생깁니다. PredicateLeftRecursionValidation은 바로 이 구간을 추가로 검사합니다.

검사 결과: 오류. 조건절을 거친 뒤 같은 A를 다시 참조하기 전까지 토큰 소비가 없습니다.

각 검사가 토큰 소비를 확인하는 구간은 다음과 같습니다.

검사 대상토큰 소비를 확인하는 구간
*·+ 반복반복 내용을 한 번 완료할 때까지
기존의 조건절 순환 검사재귀를 한 번 더 사용할 때 필수 토큰이 추가되는지
이번 조건절 좌재귀 검사출발한 비단말을 다시 참조하기 전까지

반복 문법의 다른 예제는 조건절과 반복의 입력 진행 문서에서 볼 수 있습니다.

저자의 설계와 이 문서의 역할

저자는 Janglim의 핵심 LR 구조를 설계하고 작성했습니다. 이 문서는 그 구조에 조건절을 연결할 때, 어떤 좌재귀를 미리 검사하는지 설명합니다.

저자의 판단은 일반 좌재귀를 유지하면서, 조건절을 거쳐 토큰 소비 없이 같은 규칙으로 돌아오는 경로를 따로 검사하는 것입니다. 이 문서는 그 판단의 이유와 예제별 검사 결과를 실제 클래스의 동작에 연결합니다.

구현 파일은 src/FrontEnd/Parse.FrontEnd.Grammars/PredicateLeftRecursionValidation.cs입니다. 클래스의 summary 주석에 이 문서의 링크가 있습니다.

관련 클래스는 PredicateLeftRecursionValidation, PredicateLeftRecursionException, Grammar, GrammarProgressValidation입니다. 구현은 프로젝트 저장소에서 확인할 수 있습니다.
