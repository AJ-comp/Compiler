멤버와 본문의 사용 조건을 검사합니다.

JavaScript 클래스에는 생성자, 메서드, 필드와 초기화 코드가 들어갑니다. Janglim의 JavaScript 문법은 이 구성 요소를 구문 트리로 만들고, Validate는 생성자 중복이나 선언하지 않은 private 이름처럼 클래스의 정적 문법 조건을 어긴 오류를 찾습니다.

예를 들어 class Counter { #value = 0; read() { return this.#value; } }를 파싱하면 클래스, 필드, 메서드와 속성 접근이 하나의 트리에 들어갑니다. 이때 #value가 해당 클래스에서 선언되었는지도 함께 검사합니다.

클래스 지원은 기존 JavaScript 언어 계층에 추가됩니다. 개발자는 기존 Grammar → CreateTokenSource → Parsing → Validate 순서로 사용합니다. 먼저 지원하는 클래스 구문을 확인한 뒤, 실제 사용 코드와 각 검사가 필요한 이유를 차례로 살펴보겠습니다.

1. 일반 메서드·접근자와 필드·static 블록을 함께 파싱합니다.

기준은 ECMAScript 2026, 제17판의 클래스 문법입니다. 기존의 엄격 모드 Script 입력에 클래스 선언을 추가하며, 표현식 입력에서는 클래스 표현식도 사용할 수 있습니다.

클래스 선언은 Module 입력에서도 사용할 수 있습니다. 이 경우 모듈의 예약어와 top-level await 문맥을 함께 적용하며, 모듈의 클래스 본문 설명에서 그 경계를 예제로 확인할 수 있습니다.

일반 메서드에 더해 async·제너레이터·async 제너레이터 메서드도 사용할 수 있습니다. 함수·메서드 문서에서 표기와 본문의 await·yield 조건을 비교합니다. 이 클래스 문서는 멤버 이름·private 선언·생성자와 클래스 본문의 검사에 집중합니다.

2. 클래스를 포함한 Script도 기존 C# API로 처리합니다.

JavaScriptGrammar의 기본 입력 종류인 Script에는 여러 선언과 문장을 함께 전달할 수 있습니다. 아래 입력은 private 필드 하나와 생성자·일반 메서드 하나씩을 정의합니다.

using System;
using Janglim.FrontEnd.Grammars.JavaScript;
using Janglim.FrontEnd.Parsers.LR;

var language = new JavaScriptGrammar();
var parser = new LALRParser(language.Grammar);
var input = @"
class Counter {
    #value = 0;
    constructor(start) { this.#value = start; }
    read() { return this.#value; }
}
const counter = new Counter(3);
";

var source = language.CreateTokenSource(input);
var parsed = parser.Parsing(source);
if (!parsed.Success)
{
    Console.WriteLine(parser.FiredException?.Message);
    return;
}

var diagnostics = language.Validate(parsed.ToParseTree);
foreach (var diagnostic in diagnostics)
    Console.WriteLine($"{diagnostic.Code}: {diagnostic.Message} " +
        $"(위치 {diagnostic.SourceOffset}, 길이 {diagnostic.Length})");

if (diagnostics.Count == 0)
    Console.WriteLine(parsed.ToParseTree.AllInputDatas);

CreateTokenSource는 원문과 JavaScript 토큰 규칙을 연결한 source를 만듭니다. 파서는 이 공급자에서 토큰을 받아 구문 트리를 만들고, Validate는 성공한 트리에서 정적 문법 오류를 찾습니다. 반환하는 진단의 위치와 길이는 .NET 문자열의 UTF-16 코드 단위입니다.

입력을 올바른 코드로 받아들이려면 parsed.Success가 참이고, Validate의 진단 목록이 비어 있어야 합니다. 이 과정은 JavaScript 입력을 실행하거나 인스턴스를 생성하지 않습니다. 위 예제의 new Counter(3)도 구문 트리에 기록합니다.

클래스 표현식 하나만 입력하려면 같은 클래스에서 inputKind: JavaScriptInputKind.Expression을 선택합니다. 예를 들어 class { read() { return 1; } }를 전달하면 클래스 표현식 하나를 읽습니다. 파싱과 검사 순서는 그대로입니다.

3. 클래스 선언은 이름을 만들고, 클래스 표현식은 값의 자리에 들어갑니다.

먼저 아래 선언은 현재 범위에 Counter라는 이름을 만듭니다. 따라서 같은 범위에 let Counter;나 var Counter;를 함께 선언하면 이름 충돌로 검사합니다.

class Counter {
    read() { return 1; }
}

반면 클래스 표현식은 변수의 초기값이나 함수 인자처럼 표현식이 들어갈 자리에 사용합니다. 클래스 표현식에는 이름을 적어도 되고 생략해도 됩니다.

const First = class { read() { return 1; } };
const Second = class Inner { read() { return Inner; } };

두 번째 줄의 Inner는 그 클래스 안에서 사용하는 이름입니다. 이 이름이 클래스 표현식 바깥의 범위에 새 선언으로 추가되지는 않습니다.

이제 상속 관계를 문법에 표현하려면 클래스 이름 뒤에 extends와 부모 클래스를 나타내는 표현식을 적습니다.

class Counter extends BaseCounter {
    constructor(start) { super(start); }
    read() { return super.read(); }
}

const Generated = class extends makeBase() {};

extends 뒤에는 속성 접근이나 함수 호출 같은 좌변식이 들어갈 수 있습니다. Janglim은 그 표현식의 구조를 파싱합니다. 실제로 BaseCounter가 어떤 값인지, makeBase()가 무엇을 반환하는지는 입력을 실행하는 환경에서 결정합니다.

4. 메서드의 종류에 따라 이름과 매개변수 조건이 달라집니다.

일반 메서드는 이름 뒤에 매개변수 목록과 본문을 적습니다. 매개변수에는 기존 함수와 같은 기본값·구조 분해·rest를 사용할 수 있고, 본문에는 선언·문장과 return을 사용할 수 있습니다.

class User {
    read({name = 'guest'}, ...other) { return name; }
    static create(data) { return new User(data); }
    [methodName](value) { return value; }
}

앞에 static을 붙이면 static 메서드입니다. 대괄호로 감싼 [methodName]은 표현식으로 속성 이름을 정하는 표기입니다. 일반 메서드의 매개변수 이름은 중복할 수 없으며, 매개변수 이름과 본문 최상위의 let·const·클래스 선언 이름도 충돌하면 오류입니다.

인스턴스 constructor 메서드는 클래스마다 하나만 정의합니다.

인스턴스 메서드의 이름을 constructor로 적으면 생성자를 정의합니다. 생성자를 두 번 정의하거나 생성자 이름으로 getter·setter·async·제너레이터 메서드를 정의하면 오류입니다.

class User {
    constructor(name) { this.name = name; }
}

class Invalid {
    constructor() {}
    constructor(value) {}   // 오류: 생성자 중복
}

이 특별한 이름 규칙은 계산하지 않은 속성 이름에 적용합니다. 예를 들어 ['constructor']() {}는 계산된 이름의 일반 메서드이므로 위 생성자 개수에 포함하지 않습니다. static 메서드의 constructor() {}도 인스턴스 생성자와 구분합니다.

getter는 매개변수가 없고, setter는 매개변수 하나를 받습니다.

접근자는 get 또는 set 뒤에 속성 이름을 적습니다. 다음 getter는 값을 반환하는 본문을, setter는 전달받은 값을 사용하는 본문을 가집니다.

class User {
    #name;
    get name() { return this.#name; }
    set name(value) { this.#name = value; }
}

setter의 매개변수 하나에는 기본값이나 바인딩 패턴을 사용할 수 있습니다. 다만 rest 매개변수는 사용할 수 없습니다. get()·set()처럼 이름 바로 뒤에 괄호가 오면, 이름이 각각 get·set인 일반 메서드입니다.

5. 필드는 초기값을 가질 수 있고, 줄바꿈으로 구분할 수도 있습니다.

필드는 메서드와 달리 매개변수 목록이나 문장 본문이 없습니다. 이름 뒤에 초기값을 생략하거나 =와 표현식을 적습니다.

class Counter {
    value;
    step = 1;
    static defaultStep = 1;
    [fieldName] = makeValue();
}

필드 이름 앞의 static은 static 필드를 나타냅니다. 이름을 계산하는 대괄호 구문도 메서드와 같은 방식으로 사용할 수 있습니다. 계산하지 않은 필드 이름으로 constructor를 사용할 수 없고, static 필드 이름으로 prototype도 사용할 수 없습니다.

위 예제는 각 필드를 세미콜론으로 끝냈습니다. 세미콜론을 생략하면 JavaScript의 자동 세미콜론 조건을 적용합니다. 예를 들어 다음처럼 줄바꿈으로 필드를 나눌 수 있습니다.

class Counter {
    value = 0
    step = 1
}

다만 줄바꿈만 있다고 항상 필드가 끝나는 것은 아닙니다. 다음 코드의 대괄호는 앞의 초기값 표현식에 붙을 수 있으므로, 전체 초기값을 makeValue()[fieldName]으로 읽습니다.

class Counter {
    value = makeValue()
    [fieldName]
}

의도한 구성이 두 필드라면 첫 번째 필드 뒤에 세미콜론을 적습니다. 그러면 두 번째 대괄호는 새 필드의 이름으로 파싱합니다.

class Counter {
    value = makeValue();
    [fieldName];
}

이 구분은 JavaScript 전용 종료 조건이 담당합니다. 입력 토큰의 줄바꿈 정보와 초기값을 계속 읽을 수 있는지를 확인하며, 공통 파서에 가짜 세미콜론 토큰을 추가하지 않습니다.

필드를 줄바꿈으로 끝낼 때에는, 앞에서 읽은 단어가 수식어인지 실제 멤버 이름인지도 구분해야 합니다. static은 static 멤버를 표시하는 수식어이면서 멤버 이름으로도 사용할 수 있기 때문입니다. 다음 예제에서는 static이 두 번 나옵니다.

class Counter {
    static static
    read() {}
}

첫 번째 static은 수식어이고, 두 번째 static은 필드 이름입니다. 따라서 줄바꿈에서 static 필드 하나가 끝나고, 다음 줄의 read() {}는 인스턴스 메서드가 됩니다.

반면 다음 예제의 get은 필드 이름이 아니라 getter를 시작하는 표시입니다. getter의 이름은 다음 줄에 있는 value이므로, 이 줄바꿈에서는 멤버를 끝내지 않습니다.

class Counter {
    static get
    value() { return 1; }
}

두 예제 모두 줄바꿈 바로 앞에 특별한 역할을 가질 수 있는 단어가 있습니다. 하지만 첫 번째 예제는 필드를 끝내고, 두 번째 예제는 static getter를 이어 읽습니다. 따라서 직전 토큰의 철자만 보고 필드 종료 여부를 판단할 수는 없습니다. JavaScript 언어 계층은 토큰에 연결된 불변 문맥에 수식어를 읽는 중인지, 실제 멤버 이름까지 읽었는지를 기록합니다. 필드 종료 조건과 수식어 조건은 이 문맥을 함께 사용해 두 경우를 구분합니다.

6. private 이름은 클래스 본문 안에서 선언한 이름과 연결합니다.

이름 앞에 #을 붙이면 private 필드·메서드·접근자를 정의합니다. 다음 예제는 #value를 선언하고, 메서드 안에서 그 이름을 두 가지 방식으로 사용합니다.

class Counter {
    #value = 0;
    read(other) { return other.#value; }
    contains(other) { return #value in other; }
}

other.#value는 private 속성 접근이고, #value in other는 그 private 이름의 존재를 확인하는 표현식입니다. other?.#value처럼 선택적 접근도 사용할 수 있습니다. 어느 표현식이든 현재 클래스나 바깥 클래스에서 선언한 private 이름이어야 합니다.

이름의 선언 순서는 접근 위치보다 앞설 필요가 없습니다. 검사기는 클래스 본문의 선언을 먼저 모으므로, 메서드 뒤에 선언한 필드도 찾을 수 있습니다.

class Counter {
    read() { return this.#value; }
    #value = 0;
}

클래스 본문은 자기 private 이름의 범위를 만듭니다. 따라서 계산된 속성 이름에서도 자기 private 이름을 참조할 수 있고, 중첩 클래스는 바깥 클래스의 private 이름을 참조할 수 있습니다. 중첩 클래스가 같은 이름을 선언하면 그 안에서는 가까운 클래스의 이름을 사용합니다.

한편 extends 뒤의 부모 클래스 표현식은 자기 클래스 본문에 들어가기 전에 평가하는 구간입니다. 그러므로 그 구간에서는 바깥 클래스의 private 이름만 참조할 수 있습니다. 자기 클래스에 나중에 선언한 private 이름은 부모 클래스 표현식의 선언으로 인정하지 않습니다.

class Invalid extends object.#value {
    #value;   // 이 선언은 extends 표현식의 #value를 제공하지 않음
}

private 이름은 클래스마다 모아서 검사합니다. 한 클래스 안의 같은 이름은 같은 static 여부를 가진 getter·setter 한 쌍에서만 중복을 허용합니다. 따라서 private 필드와 메서드에 같은 이름을 쓰거나, 인스턴스 필드와 static 필드에 같은 private 이름을 선언하면 오류입니다. #constructor도 사용할 수 없습니다.

private 속성은 delete로 삭제할 수 없습니다. 검사기는 delete other.#value뿐 아니라 괄호나 선택적 접근으로 감싼 형태에서도 같은 조건을 확인합니다.

7. 같은 표현식도 어느 본문에 있는지에 따라 허용 여부가 달라집니다.

클래스의 이름과 멤버 구조를 확인했다면, 이제 본문 안의 표현식을 볼 차례입니다. 특히 super·new.target·arguments는 그 표현식이 들어 있는 위치를 알아야 검사할 수 있습니다.

각 표현식을 사용할 수 있는 문맥
표현식검사 기준
super.name·super[key]클래스 메서드·생성자·필드 초기값·static 블록에서 허용합니다. 해당 클래스에 extends가 있는지는 이 구문 조건과 별개입니다.
super(...)extends가 있는 클래스의 인스턴스 생성자에서만 허용합니다. 생성자의 매개변수 기본값과 본문을 함께 검사합니다.
new.target일반 함수·메서드·생성자와 필드 초기값·static 블록에서 허용합니다.
arguments 참조필드 초기값과 static 블록에서는 금지합니다. 그 안에 정의한 일반 함수의 매개변수·본문은 별도 함수 문맥을 사용합니다.

화살표 함수는 이 세 표현식에 관한 바깥 문맥을 이어받습니다. 예를 들어 아래 화살표 함수의 super.read()는 메서드 본문의 문맥에서 검사합니다.

class Counter extends BaseCounter {
    read() { return () => super.read(); }
}

반면 일반 함수는 독립적인 함수 문맥을 만듭니다. 메서드 안에 일반 함수를 다시 정의했다고 해서, 그 함수 안의 super.read()까지 메서드의 권한을 이어받지는 않습니다.

class Invalid extends BaseCounter {
    read() {
        return function () { return super.read(); }; // 오류
    }
}

계산된 속성 이름과 extends 표현식에는 그 바깥 문맥을 적용합니다. 예를 들어 최상위 클래스의 [new.target]는 함수 안의 표현식이 아니므로 오류입니다. 같은 클래스 정의가 일반 함수 안에 있다면, 계산된 속성 이름도 그 함수의 문맥에서 검사합니다.

이처럼 검사기는 클래스 전체에 하나의 허용 여부를 붙이지 않습니다. 메서드 본문, 필드 초기값, 계산된 이름, 부모 클래스 표현식을 각각의 문맥에서 검사합니다.

8. static 블록은 자기 선언 범위와 제어문 문맥을 가집니다.

static 필드는 초기값 표현식 하나를 적습니다. 여러 선언과 문장으로 초기화 코드를 구성하려면 static { ... }를 사용합니다.

class Counter {
    static value;
    static {
        const initial = 1;
        this.value = initial;
    }
}

이 블록의 선언은 블록 안에 속합니다. var나 함수 선언도 클래스 바깥의 범위로 전달하지 않으며, 서로 다른 static 블록도 독립적인 범위를 사용합니다.

class Counter {
    static { var initial = 1; }
    static { let initial = 2; }   // 앞 블록의 이름과 충돌하지 않음
}

블록 안에서 루프와 레이블을 만들고 break·continue를 사용할 수 있습니다. 다만 클래스 바깥의 루프나 레이블로 이동할 수는 없습니다. static 블록의 return도 오류입니다.

또한 static 블록에서는 await를 직접 사용할 수 없습니다. await를 변수 이름으로 사용하거나 축약 속성 {await}로 참조하는 경우도 이 제한에 포함됩니다. object.await나 {await: 1}의 await는 속성 이름이므로 구분합니다.

블록 안에 일반 함수를 정의하면 그 함수의 매개변수·본문에는 일반 함수 문맥을 적용합니다. 화살표 함수는 매개변수 목록을 바깥 문맥에서 검사하고, 표현식·블록 본문에는 일반 화살표 함수의 문법을 적용합니다. 따라서 Script 입력에서 static 블록의 await => 1은 잘못된 매개변수 이름이지만, () => await의 본문에서는 await를 식별자로 사용할 수 있습니다. Module 입력은 await를 전체 원문에서 식별자로 금지하므로, 이 화살표 본문에서도 사용할 수 없습니다.

9. 파싱은 구조를 만들고, Validate는 그 구조의 사용 조건을 확인합니다.

다음 클래스는 메서드 두 개의 모양을 갖추고 있습니다. 하지만 두 메서드가 모두 인스턴스 생성자이므로, 올바른 클래스 정의로 받아들일 수 없습니다.

class Invalid {
    constructor() {}
    constructor(value) {}
}

이 오류를 찾으려면 현재 메서드 하나만 읽는 것으로는 부족합니다. 검사기는 같은 클래스에 정의한 메서드들을 모아 생성자 개수를 확인해야 합니다. private 이름의 중복이나 선언 여부도 같은 방식으로 클래스 범위를 알아야 판단할 수 있습니다.

이처럼 실행 전에 확인하는 정적 문법 조건을 ECMAScript 명세에서는 early error라고 부릅니다. Janglim은 Validate에서 클래스의 이름과 문맥을 순회하며 다음 조건을 검사합니다.

  • 클래스 선언 이름이 같은 범위의 다른 선언과 충돌하는가
  • 생성자·static 멤버·필드 이름이 각 이름 제한을 지키는가
  • 메서드·접근자의 매개변수 개수와 바인딩 이름이 올바른가
  • private 이름이 선언되어 있고, 같은 클래스의 중복 조건을 지키는가
  • super·new.target·arguments를 현재 문맥에서 사용할 수 있는가
  • static 블록의 선언·레이블·제어문이 블록 범위를 지키는가

따라서 파싱 성공만으로 클래스 검사가 끝나지 않습니다. 같은 구문 트리에 Validate를 적용하고 진단이 없는지도 확인해야 합니다. 검사는 원래 트리의 노드와 입력 토큰을 바꾸지 않으며, 오류가 있는 원문 위치를 진단에 기록합니다.

클래스 멤버 안의 표현식에도 기존 JavaScript 검사를 함께 적용합니다. 예를 들어 필드 초기값이나 메서드 본문에 /[z-a]/u가 있으면, Validate가 잘못된 정규식 범위를 찾습니다. 이 본문 검사의 모드와 실행 순서는 정규식 문서에서 설명합니다.
