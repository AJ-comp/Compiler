async 함수·제너레이터·메서드를 읽고,
await와 yield를 쓸 수 있는 위치를 검사합니다.

Janglim의 JavaScript 문법은 함수 선언·표현식·화살표 함수와 객체·클래스의 메서드를 구문 트리로 만듭니다. 개발자가 파싱한 트리를 Validate에 전달하면, 검사기는 함수 종류에 맞지 않는 await·yield, 잘못된 매개변수와 본문 사용을 찾습니다.

예를 들어 async function load() { return await read(); }에서 await는 async 함수 본문에 속합니다. 반면 일반 함수 function load() { return await read(); }에서는 같은 await 표현식을 사용할 수 없습니다. 함수의 모양을 읽는 일에 이어, 각 표현식이 어느 함수의 매개변수나 본문에 속하는지도 확인해야 합니다.

먼저 기존 C# API로 사용하는 순서를 살펴봅니다. 이어서 async 함수, 화살표 함수, 제너레이터, 메서드를 각각 설명한 뒤, 이 구문들이 중첩되었을 때의 검사 기준을 정리합니다.

1. 기존 Parsing → Validate 순서로 새 함수 구문도 검사합니다.

JavaScriptGrammar의 기본 입력은 여러 선언과 문장을 포함한 엄격 모드 Script입니다. 다음 예제는 이 기본 설정으로 async 함수와 제너레이터를 같은 입력에서 파싱합니다.

using System;
using Janglim.FrontEnd.Grammars.JavaScript;
using Janglim.FrontEnd.Parsers.LR;

var language = new JavaScriptGrammar();
var parser = new LALRParser(language.Grammar);
var input = @"
async function load(path) {
    return await read(path);
}
function* count() {
    yield 1;
    yield 2;
}
";

var parsed = parser.Parsing(language.CreateTokenSource(input));
if (!parsed.Success)
{
    Console.WriteLine(parser.FiredException?.Message);
    return;
}

var diagnostics = language.Validate(parsed.ToParseTree);
foreach (var diagnostic in diagnostics)
    Console.WriteLine($"{diagnostic.Code}: {diagnostic.Message} " +
        $"(위치 {diagnostic.SourceOffset}, 길이 {diagnostic.Length})");

if (diagnostics.Count == 0)
    Console.WriteLine("문법 검사 통과");

파싱이 성공하면 트리에 함수 종류, 매개변수와 본문이 남습니다. Validate는 그 구조를 사용해 정적 오류를 검사합니다. 개발자는 파싱이 성공했고 정적 오류도 없는지 함께 확인해야 합니다. 진단의 위치와 길이는 .NET 문자열의 UTF-16 코드 단위입니다.

함수 표현식 하나를 읽을 때에는 같은 클래스의 inputKind를 JavaScriptInputKind.Expression으로 지정합니다. import·export가 있는 파일에는 JavaScriptInputKind.Module을 지정합니다. 입력 종류에 관계없이 Parsing과 Validate의 순서는 같으며, 그 결과로 구문 트리와 문법 진단을 받습니다. 입력한 함수를 호출하거나 비동기 작업을 실행하는 과정은 포함하지 않습니다.

2. async 함수 본문에서는 await 표현식을 사용할 수 있습니다.

함수 선언의 function 앞에 async를 붙이면 async 함수입니다. 함수 표현식에도 같은 표기를 사용할 수 있습니다.

async function load(path) {
    const data = await read(path);
    return data;
}

const loadAgain = async function (path) {
    return await read(path);
};

첫 번째 예제의 await read(path)는 read 호출의 결과를 기다리는 표현식입니다. Janglim은 await 표현식과 그 피연산자인 호출 표현식을 트리에 기록합니다. await 뒤에는 기다릴 값의 표현식이 필요하므로 async function load() { await; }는 오류입니다.

async 함수 본문에서는 비동기 반복의 for await (... of ...)도 사용할 수 있습니다. 반복문 본문과 바인딩은 기존 문장·구조 분해 검사와 함께 처리합니다.

async function collect(stream) {
    for await (const {value} of stream) {
        save(value);
    }
}

여기까지는 async function 형태의 함수입니다. 다음 절에서는 같은 async 본문을 화살표 표기로 만드는 경우를 살펴봅니다.

3. async 화살표 함수는 매개변수 앞에 async를 붙입니다.

식별자 하나는 괄호 없이 적을 수 있습니다. 여러 매개변수, 기본값·구조 분해·rest는 기존 화살표 함수처럼 괄호 안에 적습니다. 본문에는 표현식 하나 또는 중괄호로 감싼 문장 목록을 사용합니다.

const load = async path => await read(path);
const pick = async ({path = 'default'}) => {
    return await read(path);
};
const collect = async (...paths) => await readAll(paths);

첫 번째 함수는 await 표현식을 본문으로 사용합니다. 두 번째 함수는 블록 안의 return 문에서 await를 사용합니다. 두 형태 모두 async 함수 본문이므로 await 표현식을 허용합니다.

다만 async라는 글자가 나왔다고 바로 async 함수로 정할 수는 없습니다. async(value)는 이름이 async인 함수를 호출하는 표현식이고, async (value) => value는 async 화살표 함수입니다.

async(value)                  // 일반 함수 호출
async (value) => value        // async 화살표 함수
value => value                // 일반 화살표 함수

async는 일반 식별자나 속성 이름으로도 사용할 수 있습니다. 예를 들어 const async = read;와 ({async() { return 1; }})를 허용합니다. 객체의 async()는 이름이 async인 일반 메서드이고, async load()는 이름이 load인 async 메서드입니다.

따라서 문법은 호출과 화살표 헤드가 공유하는 형태를 읽은 뒤, 실제로 =>가 이어진 헤드에 매개변수 조건을 적용합니다. 이 과정에서도 원문과 구문 트리를 보존합니다. async라는 이름의 일반 호출에 화살표 매개변수 규제를 잘못 적용하지 않기 위해서입니다.

4. 제너레이터 본문에서는 yield로 값을 내보내는 구문을 적습니다.

function 뒤의 별표 *는 제너레이터 함수를 나타냅니다. 함수 이름을 선언할 수도 있고, 제너레이터 표현식을 다른 변수에 넣을 수도 있습니다.

function* values() {
    yield 1;
    yield* otherValues;
    yield;
}

const makeValues = function* () {
    yield 2;
};

yield 1은 값 하나를 내보내는 구문입니다. yield* otherValues는 다른 반복 가능한 값에 위임하는 구문이며, yield;처럼 값의 표현식을 생략할 수도 있습니다. Janglim은 이 세 형태를 구분해 트리에 남깁니다.

이제 async와 제너레이터를 함께 사용하면, 본문에서 await와 yield를 모두 사용할 수 있습니다. 이 함수는 async function*으로 시작합니다.

async function* pages(stream) {
    for await (const page of stream) {
        yield await decode(page);
    }
    yield* morePages;
}

이 예제에서 for-await-of와 await는 비동기 문맥을 사용하고, yield는 제너레이터 문맥을 사용합니다. 일반 async 함수에는 yield 표현식을 사용할 수 없고, 일반 제너레이터 함수에는 await 표현식을 사용할 수 없습니다. 각 조합을 메서드에도 적용할 수 있으며, 다음 절에서 그 표기를 살펴봅니다.

5. 객체와 클래스에는 일반·async·제너레이터 메서드를 적습니다.

객체 리터럴의 메서드는 속성 이름 뒤에 매개변수 목록과 본문을 바로 적습니다. getter는 속성 값을 읽는 접근자이고, setter는 속성 값을 쓰는 접근자입니다.

({
    run(value) { return value; },
    get value() { return this._value; },
    set value(next) { this._value = next; }
})

run은 일반 메서드입니다. get value()는 매개변수를 받지 않고, set value(next)는 매개변수 하나를 받습니다. setter의 매개변수에는 기본값이나 바인딩 패턴을 사용할 수 있지만 rest나 뒤쪽 쉼표를 붙일 수 없습니다. 이름이 get인 일반 메서드 get() {}는 getter와 구분합니다.

같은 객체 안에서 메서드 이름 앞에 async·별표를 붙이면 본문의 종류도 달라집니다. 아래 세 메서드는 앞에서 설명한 세 함수 종류에 각각 대응합니다.

({
    async load(path) { return await read(path); },
    *values() { yield 1; },
    async *pages() { yield await readPage(); }
})

이 표기는 클래스의 인스턴스·static·private 메서드에도 사용할 수 있습니다. 기존 클래스의 필드와 접근자, private 이름 검사는 그대로 함께 적용합니다.

class Store {
    async load() { return await read(); }
    static *keys() { yield 'first'; }
    async *#pages() { yield await readPage(); }
}

클래스의 인스턴스 생성자는 일반 constructor 메서드여야 합니다. 따라서 async constructor() {}나 *constructor() {}는 오류입니다. 반면 객체의 constructor라는 속성 이름이나 클래스의 static 메서드 이름에는 이 생성자 조건을 적용하지 않습니다.

객체 메서드는 super.name 같은 상위 객체 속성 접근도 사용할 수 있습니다. 하지만 객체 메서드에서 super()로 생성자를 호출할 수는 없습니다. 속성 접근과 생성자 호출은 서로 다른 조건으로 검사합니다.

6. 안쪽 함수를 정의하면 그 함수 종류에 맞는 본문 문맥을 적용합니다.

앞 절까지는 함수 하나씩 살펴봤습니다. 실제 코드에서는 async 함수 안에 일반 함수를 넣거나, 제너레이터 안에 화살표 함수를 넣을 수 있습니다. 이때 바깥 함수가 사용할 수 있는 표현식을 안쪽 함수에도 그대로 허용하면 잘못된 입력을 받아들이게 됩니다.

async function outer() {
    await read();                     // 허용: outer의 본문
    function inner() {
        return await read();          // 오류: 일반 함수 inner의 본문
    }
    const again = async () => await read(); // 허용: 새 async 본문
}

inner를 정의한 위치는 async 함수 안이지만, inner 자체는 일반 함수입니다. 따라서 inner의 본문에는 await 표현식을 사용할 수 없습니다. 마지막 화살표 함수는 자기 앞에 async가 있으므로 자기 본문에서 await를 사용할 수 있습니다.

각 함수의 본문에 허용하는 표현식
함수·메서드의 종류await 표현식yield 표현식
일반 함수·일반 화살표·일반 메서드·접근자사용 불가사용 불가

이 표는 await 표현식의 조건입니다. 엄격 모드 Script의 일반 함수 본문에서는 const await = 1;처럼 await를 식별자로 사용할 수 있습니다. 반면 Module에서는 중첩된 일반 함수까지 await를 식별자로 사용할 수 없습니다. Module 최상위의 await 표현식은 모듈 문서에서 설명합니다.

메서드 이름을 계산하는 대괄호 안은 메서드 본문과 구분해야 합니다. 예를 들어 아래 [await name()]은 load 함수 본문에서 계산하므로 await를 허용합니다. 하지만 이름을 계산한 뒤 시작되는 run 메서드는 일반 메서드이므로, run의 본문에서는 await 표현식을 허용하지 않습니다.

async function load() {
    return {
        [await name()]() { return 1; }
    };
}

클래스 필드 초기화식은 await 이름과 await 표현식을 구분합니다.

함수 안에 클래스를 정의하면 필드의 초기값에도 표현식이 들어갑니다. 이 위치에서는 두 가지를 구분합니다. 하나는 await라는 이름을 식별자로 쓸 수 있는지이고, 다른 하나는 await read()처럼 초기화를 중단하는 표현식을 쓸 수 있는지입니다.

class Store {
    value = await;          // Script 최상위: await 식별자 허용
    static cached = await;  // 같은 Script 문맥: await 식별자 허용
}

async function load() {
    class Store {
        value = await;      // 오류: 바깥 async 문맥의 await 예약어 조건
        static cached = await; // 같은 이유로 오류
    }
}

필드 초기화식에서 식별자로 사용한 await에는 바깥 문법의 Await 조건을 확인합니다. 따라서 async 함수 안의 두 초기화식에서는 await를 식별자로 사용할 수 없습니다. 이 기준은 인스턴스 필드와 static 필드에 동일하게 적용합니다. Module 원문의 await 예약어 조건과 static 블록에서 이어지는 await 제한도 함께 검사합니다.

이 이름 조건과 별도로, Janglim은 필드 초기화식을 동기적인 초기화 구문으로 검사합니다. 따라서 value = await read()와 value = yield item처럼 초기화 자체를 중단하는 표현식은 오류로 처리합니다. 초기값 안에 별도로 정의한 async 함수나 제너레이터의 본문은 그 함수의 문맥에서 검사합니다.

이 경계에는 알려진 명세 문제가 있습니다. ECMAScript 2026의 FieldDefinition은 Await·Yield 조건을 초기화식으로 전달하지만, 그 결과 허용되는 중단 표현식과 동기 초기화의 관계가 TC39 #2437·#3333에 미해결 문제로 기록되어 있습니다. Janglim은 위의 검사 기준을 유지하며, 이 부분의 다른 엔진 결과를 그대로 문법의 정의로 사용하지 않습니다.

한편 화살표 함수의 super·new.target은 이 await·yield 경계와 검사 기준이 다릅니다. 화살표 함수는 super·new.target에 관한 바깥 권한을 이어받으므로, 검사기는 각 기능의 경계를 별도로 관리합니다. 그 사용 조건은 클래스 본문 문서에서 설명합니다.

7. 매개변수의 기본값에는 해당 함수의 await·yield를 직접 사용할 수 없습니다.

함수 본문에서 await나 yield를 사용할 수 있다고 해서, 그 함수의 매개변수 기본값에서도 같은 표현식을 사용할 수 있는 것은 아닙니다.

async function load(value = await read()) {}   // 오류
function* values(value = yield 1) {}           // 오류
async function* pages(value = await read()) {} // 오류

매개변수는 함수 본문에 들어가기 전에 준비합니다. 따라서 명세는 이 위치의 await·yield 표현식을 정적 문법 오류로 정합니다. 검사기는 매개변수의 기본값과 구조 분해 패턴의 계산된 속성 이름도 이 기준으로 확인합니다.

다만 기본값 안에 별도 함수를 정의한 경우에는 그 안쪽 함수의 본문을 구분합니다. 다음 await는 load의 매개변수에서 직접 수행할 표현식이 아니라, 새로 정의한 async 화살표 함수의 본문에 속합니다.

async function load(factory = async () => await read()) {}
function* values(factory = function* () { yield 1; }) {}

따라서 이 두 함수 정의는 허용합니다. 검사기가 매개변수 아래의 모든 await·yield를 한꺼번에 오류로 처리하지 않고 함수 경계를 확인하는 이유입니다.

기존 매개변수 조건도 함께 적용합니다. 바인딩 이름 중복, 매개변수와 본문 직접 lexical 선언의 충돌, rest 위치, 엄격 모드 예약어와 eval·arguments 제한을 검사합니다. 기본값·구조 분해·rest가 있는 매개변수와 함수 자신의 'use strict' 지시문을 함께 쓰는 경우도 오류입니다.

8. async 수식어와 yield 뒤의 줄바꿈은 서로 다르게 처리합니다.

먼저 async 수식어 바로 뒤에는 줄바꿈을 넣을 수 없습니다. async와 function, async와 화살표 매개변수, async와 async 메서드 이름 사이가 이 조건에 해당합니다. async 제너레이터 메서드에서는 async와 그다음 별표 사이에 같은 조건을 적용합니다. 화살표 매개변수와 => 사이에도 기존 줄바꿈 금지 조건을 적용합니다.

async function load() {}          // async 함수
async /* 같은 줄의 주석 */ x => x // async 화살표 함수

async
function load() {}                // Script에서 async 문장 + 일반 함수 선언

마지막 두 줄은 async 함수 하나가 아닙니다. Script는 async 식별자 문장을 먼저 끝내고, 다음 줄의 일반 함수 선언을 별도로 읽을 수 있습니다. 주석 안의 줄바꿈도 실제 줄바꿈과 같이 판단합니다.

다음으로 yield 뒤의 값을 같은 yield 표현식에 붙이려면 그 사이에 줄바꿈이 없어야 합니다. 줄바꿈이 있으면 값 없는 yield가 먼저 끝날 수 있습니다.

function* values() {
    yield
    nextValue;  // 값 없는 yield와 nextValue 문장
}

function* delegated() {
    yield* items; // 위임 구문
}

yield*에서도 yield와 별표 사이에 줄바꿈을 넣을 수 없습니다. 반면 await와 피연산자 사이에는 이 줄바꿈 금지 조건이 없으므로 await 다음 줄에 read()를 적어도 하나의 await 표현식으로 읽습니다.

이 판단은 기존 토큰의 줄바꿈 정보와 JavaScript 프레디케이트를 사용합니다. 문장 종료와 다음 슬래시의 읽기 방식도 JavaScript 정책에서 연결하므로, 공통 렉서·LR 파서의 동작을 바꾸지 않고 적용합니다.

문법과 정적 검사를 JavaScript 지원 계층에 둡니다.

함수의 토큰 순서는 JavaScript EBNF가 표현합니다. 언어 전용 C# 코드는 await·yield의 문맥, 매개변수와 선언 범위, 메서드의 사용 조건을 확인합니다. 파서는 기존 입력 공급자와 정책의 호출 구조를 그대로 사용합니다.

명세의 Await·Yield 문법 매개변수는 해당 구문을 읽을 수 있는지 나타냅니다. 예를 들어 async 함수 본문은 Await를 켜고 Yield를 끄며, async 제너레이터 본문은 둘을 모두 켭니다. 안쪽 일반 함수는 둘을 다시 끕니다. 구현에서는 JavaScriptFunctionGrammar가 언어 문법을 준비하면서 Await가 꺼진 규칙과 켜진 __Await 규칙을 연결합니다. Yield 표현식은 공통 구문으로 읽은 뒤, 최종 정적 검사에서 함수 종류와 사용 위치를 확인합니다. 공통 EBNF 엔진에 JavaScript 전용 키워드나 문법 매개변수 기능을 추가하지 않습니다.
