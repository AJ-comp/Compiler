명세가 허용하는 코드는 받고,
금지하는 코드는 진단하는지 확인합니다.

JavaScript 문법을 지원한다는 말에는 두 가지 약속이 들어 있습니다. 올바른 코드는 구문 트리로 만들 수 있어야 하고, 잘못된 코드는 문법 검사에서 발견해야 합니다. 이 문서는 그 두 약속을 확인하기 위해 명세·구현·테스트를 연결한 검증 기록입니다.

예를 들어 const value = 1;은 받아야 하지만, 같은 범위에서 let value; let value;라고 선언한 코드는 거부해야 합니다. 두 번째 코드는 토큰 순서만 보면 선언 두 개로 읽을 수 있습니다. 따라서 구문을 읽는 검사와, 읽은 구문의 이름·문맥을 확인하는 정적 오류 검사를 함께 검증합니다.

먼저 기준 명세의 항목을 빠짐없이 목록으로 만들고, 각 항목이 구현된 파일과 테스트 파일을 연결합니다. 그다음 Test262의 실제 입력을 사용해 허용·거부 결과를 비교합니다. 목록 작성과 테스트 통과는 서로 다른 근거이므로 각각의 상태를 따로 기록합니다.

1. 비교 대상은 고정된 ECMAScript 2026 명세입니다.

기준은 ECMAScript 2026, 제17판입니다. 새 제안이 계속 합쳐지는 현재 초안과 비교하면, 검증 중에 지원 대상이 바뀔 수 있습니다. 그래서 명세 주소에 /2026/이 들어간 판본을 사용합니다.

Test262 저장소에도 정식 명세 이후의 기능에 대한 테스트가 들어올 수 있습니다. 예를 들어 using 선언이나 import의 새 단계 표기를 포함한 사례는 해당 기능이 2026 판본에 있는지 먼저 확인해야 합니다. 테스트를 발견했다는 이유만으로 2026 지원 누락으로 판정하지 않습니다.

또한 Script와 Module, 엄격 모드와 비엄격 모드, 웹 호환 옵션을 구분합니다. 같은 입력이라도 선택한 문맥에 따라 허용 여부가 달라지기 때문입니다. 예를 들어 with (obj) {}는 비엄격 Script에서는 허용할 수 있지만 Module에서는 오류입니다.

2. 명세의 생성 규칙과 정적 오류 항목을 먼저 목록으로 만듭니다.

자동 추출기는 공식 명세 HTML 10개를 읽고, 문법·정적 의미를 70개 규칙 그룹으로 나눕니다. 이 그룹에는 원본 생성 규칙 정의 388개와 Early Errors 41개 절의 검사 항목 213개가 연결되어 있습니다. 숫자는 명세 대조 목록의 크기이며, 구현의 통과 개수를 뜻하지 않습니다.

같은 생성 규칙은 의미를 설명하는 여러 절에서 반복됩니다. 이를 각각 다른 문법으로 세면 대조 목록이 부풀려집니다. 추출기는 원본 정의의 prod-<이름> 또는 웹 호환 정의의 prod-annexB-<이름> 앵커만 수집합니다. 부속서 A의 문법 요약은 같은 정의를 다시 싣기 때문에 중복 집계에서 제외합니다.

각 원본 HTML의 SHA-256, 생성 규칙의 대안 수와 내용 해시, 정적 오류 절의 항목 수와 내용 해시도 함께 남깁니다. 정적 오류 규칙 안에 중첩된 세부 조건이나 알고리즘 단계는 별도 규칙으로 중복 집계하지 않습니다. 나중에 추출 결과가 바뀌면 원본이 바뀌었는지, 추출 코드가 바뀌었는지 확인할 수 있습니다. 전체 목록과 대응 경로는 ecmascript-2026-coverage.json에 있습니다.

실행 기능은 문법 검사와 구분합니다.

ECMAScript 명세에는 문법뿐 아니라 프로그램 실행, 객체, 내장 함수, 모듈 로딩도 들어 있습니다. 이번 대조에서는 입력을 읽는 문법과 실행 전에 판정할 정적 오류를 검사합니다. 따라서 Math의 계산 결과나 Promise의 동작 같은 실행 항목은 별도 범위로 분류합니다.

정규식은 두 단계로 나눠 다룹니다. /.../flags의 경계를 찾는 규칙은 12절에 있고, 그 안쪽 본문의 문법과 오류 조건은 22.2.1절에 있습니다. 실제 문자열과 정규식을 매칭하는 실행 동작과 달리, 두 문법 검사는 모두 이번 대조에 포함합니다.

3. 각 명세 항목을 JavaScript 지원 파일과 연결합니다.

Janglim의 EBNF는 토큰 순서와 문법 구조를 표현합니다. 이름의 중복, 대입 대상, 함수·클래스 문맥처럼 트리를 보고 판단할 조건은 JavaScript 검증 클래스가 담당합니다. 그래서 명세 한 항목에 EBNF와 C# 파일이 함께 연결되는 경우가 많습니다.

4. Test262에서는 입력의 허용 여부와 오류 발생 시점을 비교합니다.

Test262는 ECMAScript의 공식 테스트 모음입니다. 테스트의 본문과 함께 엄격 모드 여부, Module 여부, 필요한 기능, 예상 오류의 단계가 기록되어 있습니다. 검증기는 이 메타데이터를 읽어 각 입력에 맞는 JavaScriptGrammar 설정을 만듭니다.

정상 입력은 파싱과 정적 검사를 모두 통과해야 합니다.

구문 검증을 할 때 테스트 안의 JavaScript를 실행할 필요는 없습니다. 입력이 올바른 문법이라면 구문 트리를 만들 수 있어야 하고, Validate가 정적 오류를 반환하지 않아야 합니다. 실행 단계에서 의도적으로 예외를 던지는 테스트라도 구문이 올바르면 이 검사는 통과해야 합니다.

parse 단계의 SyntaxError 사례는 거부해야 합니다.

메타데이터가 negative.phase: parse, negative.type: SyntaxError를 지정하면 구문을 읽거나 정적 오류를 검사하는 과정에서 문제를 찾아야 합니다. Janglim은 정적 오류를 별도 Validate 호출에서 반환하므로, 두 호출의 결과를 함께 판정합니다.

모듈 연결 오류는 문법 오류와 구분합니다.

예를 들어 존재하지 않는 다른 모듈에서 이름을 가져오는 문제는 의존 모듈을 연결해야 알 수 있습니다. Test262가 이를 resolution 단계의 오류로 지정했다면, 그 결과를 한 파일의 문법 검사로 판정하지 않습니다. 해당 입력의 구문 자체를 읽을 수 있는지는 별도로 확인할 수 있습니다.

메타데이터에 맞게 엄격 모드 변형을 만듭니다.

onlyStrict 입력은 엄격 모드로, noStrict 입력은 비엄격 모드로 검사합니다. module 입력은 Module 문법으로 검사합니다. 이번 Test262 실행에서는 모든 입력에 webCompatibility: true를 적용했으며, 각 입력의 엄격·비엄격·Module 문맥에 맞는 웹 호환 규칙이 적용됩니다. 두 모드 모두를 요구하는 입력은 각 문맥에서 따로 확인하므로 파일 수와 실제 검사한 입력 수는 서로 다를 수 있습니다.

테스트 저장소의 커밋과 선택 기준도 결과에 남겨야 합니다. 그래야 이후에 사례 수가 바뀌더라도, 검증 범위가 넓어진 것인지 구현 결과가 바뀐 것인지 구분할 수 있습니다. 제외한 기능이나 사례도 사유별로 기록합니다.

검증에서 발견한 문제를 JavaScript 지원 계층에서 수정했습니다.

첫 번째 문제는 수천 개의 요소가 있는 배열이었습니다. 기존 배열 생성 규칙에서는 요소를 하나 읽을 때마다 LR 스택이 길어졌고, 파싱 과정에서 보관하는 스택 기록도 함께 커졌습니다. 배열 리터럴과 배열 바인딩 목록을 왼쪽으로 누적하는 생성 규칙으로 바꿔, 요소 수가 늘어도 목록 처리에 필요한 스택 깊이가 일정하게 유지되도록 수정했습니다. 배열의 빈칸·쉼표·나머지 요소와 중첩 구조는 그대로 검사합니다.

두 번째 문제는 템플릿 안에서 yield 뒤에 값이 없는 경우였습니다. 템플릿의 }는 뒤의 문자열과 함께 TemplateMiddle 또는 TemplateTail 토큰에 들어갑니다. 문장 조건 검사가 이 토큰도 표현식의 끝으로 인식하도록 수정해, function* f() { return `${yield}`; }를 올바르게 처리합니다.

세 번째 문제는 비엄격 모드에서 let을 식별자로 사용하는 문장이었습니다. 아래 입력에서 if의 본문은 식별자 let으로 이루어진 문장입니다. 줄바꿈에서 그 문장이 끝나고, 다음 줄의 x;는 별도의 문장이 됩니다.

if (false) let
x;

반면 아래 입력은 두 줄에 걸친 하나의 let 선언입니다. 문장 목록에서는 뒤의 이름 x가 선언할 변수 이름이 됩니다. 두 입력을 문법의 위치에 맞게 구분하도록 조건 함수를 수정했습니다.

let
x;

이 문장 경계를 교차 검사하는 과정에서, 줄바꿈 뒤의 함수·클래스 선언이 앞 문장의 표현식 문맥을 이어받는 문제도 찾았습니다. 예를 들어 아래 입력은 let 식별자 문장, 클래스 선언, 정규식으로 시작하는 문장 순서로 읽어야 합니다.

let
class Next {}
/ab/.test(text);

클래스 선언이 끝나면 다음 문장의 시작을 읽어야 하므로, JavaScript 정책은 정규식 리터럴을 읽을 규칙 묶음을 반환해야 합니다. 줄바꿈으로 문장이 끝나는 시점과 async function 선언의 시작을 판단하는 순서를 수정해, 앞 문장의 문맥이 다음 선언 뒤까지 남지 않도록 했습니다.

다만 await 뒤에서는 줄바꿈만으로 표현식이 끝나지 않습니다. 아래 입력에서 await의 피연산자는 클래스 표현식이고, 클래스 표현식 뒤의 /는 나눗셈 연산자입니다.

async function outer() {
    await
    class {} / divisor;
}

이 경우까지 올바르게 처리하려면, 정책이 확인한 문맥을 토큰을 읽는 경로마다 보존해야 합니다. 정책은 파싱 상태의 기대 토큰을 보고 await가 값을 기다리는 키워드인지 확인하며, 그 결과를 해당 토큰 요청에 연결해 전달합니다. 입력 공급자는 이 정보를 사용해 함수·클래스를 표현식으로 기록합니다. 변수 이름이나 레이블에 쓰인 await는 각각의 문법에 맞게 처리합니다.

이 수정들은 JavaScript의 EBNF·문맥 추적·조건 함수·정적 검사와 테스트에 적용했습니다. 기존 공통 렉서·LR 파서·EBNF 리더를 그대로 사용하며, 저자가 설계한 핵심 LR 구조를 유지합니다.

이 사례들에는 허용해야 하는 입력과 거부해야 하는 입력을 함께 추가했습니다. 예를 들어 배열 바인딩 패턴의 나머지 요소 뒤에 쉼표를 붙인 입력은 계속 거부하며, yield* 뒤의 피연산자가 빠진 입력도 계속 거부합니다. 또한 토큰 종류와 구문 트리의 구조까지 확인해, 입력을 통과시키기만 하는 수정으로 끝나지 않도록 했습니다.

정규식 생성자의 문자열 본문도 별도로 검사합니다.

new RegExp("(")는 JavaScript의 호출 구문으로는 읽을 수 있습니다. 하지만 그 문자열을 정규식 본문으로 읽으면 닫는 괄호가 없다는 오류가 생깁니다. 파일 전체를 파싱하는 검사만으로는 이 안쪽 문자열의 정규식 문법을 확인할 수 없으므로, 기존 정규식 본문 검사기를 직접 호출하는 독립 감사 도구를 추가했습니다.

정규식을 매칭하지 않고 본문 문법만 비교한 독립 검사
입력의 출처검사 수결과
반복·이스케이프·그룹·문자 집합의 경계와 조합66,546개참조 엔진과 차이가 난 55개는 모두 거대한 반복 횟수의 비교였습니다. 명세의 정수 값 비교에 따라 Janglim이 올바르게 거부했습니다.

RegExp 테스트의 문자열 내용을 일반·u·v 문법에 넣은 추가 입력33,084개차이가 난 128개는 Unicode 17에서 추가된 네 Script의 별칭이었습니다. 공식 Unicode 17 자료로 Janglim의 허용 결과를 확인했습니다.

참조 엔진은 Node 24.12.0이며 Unicode 16 자료를 사용합니다. Janglim은 Unicode 17.0.0 자료를 사용하므로, 참조 엔진과 결과가 다르면 고정 명세와 Unicode 원본을 기준으로 다시 판단합니다. 이 비교에서 확인한 Janglim 구현 결함과 예기치 않은 예외는 0개였습니다.

세 검사에서 사용한 문자열은 원래의 UTF-16 코드 단위를 보존해 전달했습니다. 단독 surrogate를 포함해 Node와 C#이 받은 문자열의 해시가 원본과 같은지 입력마다 확인했습니다. 이 추가 입력들은 정규식 문법을 조사하는 독립 검사이므로 Test262 원본 테스트의 통과 개수와 따로 기록합니다.

명세 목록과 검증 결과를 다시 만드는 방법

전체 실행은 검증 도구 안내의 순서를 따릅니다. 고정 ZIP에서 입력을 준비하고, 별도 디렉터리에 검증 바이너리를 빌드한 뒤, 세 프로필을 실행하고 집계합니다. 집계할 때 실제 바이너리 디렉터리를 지정하면 입력과 결과뿐 아니라 DLL 해시도 확인합니다.

명세 목록을 다시 추출하려면

다음 명령은 Python 표준 라이브러리만 사용합니다. 명세 HTML을 ignored artifacts/ecmascript-2026/spec 폴더에 보관하고, 저장소의 JSON 대조 목록을 다시 생성합니다.

python tools/Test262/extract-ecmascript-coverage.py --refresh

이미 받은 원본으로 추출 코드만 다시 확인하려면 --refresh를 생략합니다. 원본 파일의 해시와 항목 목록을 함께 비교하면 됩니다. JSON에는 저장소의 여섯 EBNF 파일에 정의된 생성 규칙 이름도 들어 있어, 명세의 규칙 이름과 구현의 규칙 이름을 대조할 수 있습니다.

명세의 매개변수 확장이나 커버 문법 때문에 두 목록의 이름과 개수가 그대로 같지는 않습니다. 예를 들어 Janglim은 문맥별 규칙을 확장하고, 같은 표현식 트리를 구조 분해 대상으로 검사하기도 합니다. 따라서 단순 이름 일치율 대신 대응 파일과 실제 입력 결과를 함께 사용합니다.

정규식 독립 감사를 다시 실행하려면

먼저 JavaScript 지원 DLL과 고정 Test262 스냅샷을 준비한 뒤 다음 명령을 실행합니다. 도구는 이미 빌드된 DLL을 읽고 독립 어댑터만 빌드합니다. 공통 엔진이나 제품 프로젝트를 다시 빌드하거나 수정하지 않습니다.

python tools/Test262/audit_regexp_patterns.py --assembly tools/Janglim.Test262/bin/Release/net8.0/Parse.FrontEnd.Grammars.Ebnf.dll --test262-root artifacts/ecmascript-2026/test262 --string-probes

재현 입력·운송 데이터·해시·참조 엔진 차이·예기치 않은 예외는 artifacts/ecmascript-2026/regexp-repro에 남깁니다. summary.json에서 검사 수와 버전을 확인하고, 각 *.report.json에서 차이가 난 최소 입력을 확인할 수 있습니다. 생성자 인수를 계산하는 코드나 테스트의 실행 결과는 평가하지 않습니다.

저자의 설계와 이번 검증의 관계

Janglim의 핵심 LR 구조는 저자가 설계하고 작성했습니다. 이번 명세 대조·Test262 연결·언어별 오류 검사는 그 기존 구조 위의 JavaScript 지원 계층을 검증하는 AI 보조 작업입니다. 기존 엔진에 담긴 저자의 설계·구현과 이번 언어 지원·검증 작업을 구분합니다.

사용법은 JavaScript 입력 종류·엄격 모드·웹 호환 옵션에서 이어 볼 수 있습니다. 내부 토큰 요청 구조는 파서 주도 렉싱 문서에 설명되어 있습니다.
