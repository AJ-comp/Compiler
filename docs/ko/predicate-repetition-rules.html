문법 동작 노트 / 조건절의 반복을 왜 검사하는가

조건을 반복한다면,
입력은 어디까지 읽었을까요?

먼저 조건을 한 번 확인하는 문법을 읽겠습니다. 그다음에 괄호로 묶고 반복했을 때 무엇이 달라지는지 따라가겠습니다. 중심 질문은 하나입니다. 반복의 본문을 한 번 마쳤을 때, 입력 위치가 앞으로 갔는가?

이번 설명의 출발점
S : 'x' {Allow()}? 'y' ;

입력의 x와 y 사이에서 조건을 한 번 확인합니다.

S는 우리가 정의한 규칙의 이름입니다. 작은따옴표 안의 'x'와 'y'는 실제 입력에서 읽을 토큰입니다. {Allow()}?는 등록한 C# 검사 함수를 호출할 자리입니다.

이 규칙을 따라가려면 x를 읽고, Allow가 true인지 확인한 다음, y를 읽습니다. 마지막의 ;는 이 규칙의 정의가 끝났다는 표시입니다.

지금은 Allow가 true를 돌려준다고 가정하겠습니다. 입력은 x y입니다. 입력의 공백을 구분으로 처리하면 렉서는 토큰 x와 y를 준비하고, 파서는 마지막에 입력 끝 표시 EOF를 붙여 확인합니다.

원문:          x y
토큰 목록:     [x, y, EOF]
목록의 번호:    0  1   2
01 · 현재 어디에 있는지부터 확인합니다

x를 읽으면 위치가 1이 됩니다.

처음에는 아직 아무 토큰도 읽지 않았습니다. 다음에 읽을 x는 0번에 있습니다. x를 Shift하면 x를 읽었다고 처리하고, 다음에 확인할 위치가 1번 y로 옮겨집니다.

x를 읽기 전위치 0다음은 x
→
x를 읽은 뒤위치 1다음은 y

그다음 Allow를 확인해도, y는 아직 읽지 않았습니다.

이제 x와 y 사이의 조건을 확인합니다. Allow가 true라고 답하면 그 자리를 통과할 수 있습니다. 하지만 조건을 확인한 동안 입력 토큰을 읽은 수는 0개입니다.

따라서 조건을 확인하기 전에도 다음 토큰은 y이고, 확인한 뒤에도 다음 토큰은 y입니다. 위치 번호도 1 그대로입니다. 조건이 false라면 그 조건을 가진 경로를 더 진행할 수 없습니다.

조건은 “이 길로 가도 되는가”를 판단합니다.
입력 위치를 앞으로 옮기는 것은 토큰을 읽는 Shift입니다.

파서 안에서는 이 자리를 빈 규칙으로 처리합니다.

입력을 0개 읽고 완성되는 규칙을 빈 규칙이라고 부릅니다. 기호 ε로 표시합니다. 조건이 있는 빈 규칙을 Reduce하는 행동이 조건이 있는 ε Reduce입니다.

이후 Goto로 다음 상태를 찾고, 실제로 y를 Shift할 때 입력 위치가 2로 옮겨집니다. 상태를 바꾸는 일과 입력을 읽는 일은 각각 구별해서 기록합니다.

02 · 같은 ?처럼 보여도, 붙어 있는 대상부터 봅니다

{Allow()}? 전체가 조건절 한 개입니다.

조건 표기는 여는 중괄호부터 끝의 물음표까지 함께 읽습니다. {Allow()}?의 마지막 물음표는 “Allow 검사를 선택적으로 생략한다”는 뜻으로 붙인 반복 연산자가 아니라, 조건절의 표기를 완성하는 기호입니다.

일반 토큰이나 괄호 뒤에 붙이는 연산자는 따로 있습니다. 'x'?는 x를 0번 또는 1번 읽습니다. 'x'*는 x를 0번 이상, 'x'+는 x를 1번 이상 읽습니다.

표기읽는 방법
{Allow()}?Allow를 확인하는 조건절 한 개입니다. true이면 그 자리를 통과합니다.
'x'?입력 토큰 x를 읽거나 생략합니다.
({Allow()}?)?괄호 안의 조건절 전체를 실행하거나 생략합니다. 마지막 물음표는 괄호에 붙은 선택 연산자입니다.

조건절 바로 뒤에 연산자를 더 붙이는 표기는 문법 오류입니다.

Janglim은 조건절 한 개를 {Name()}?로 읽습니다. 그 뒤에 바로 *, +, ?를 하나 더 붙이면 리더가 오류를 반환합니다. 먼저 무엇에 연산자를 적용하는지 명확하게 적도록 정한 표기 규칙입니다.

{Allow()}?       # 조건절 한 개: 정상
{Allow()}?*      # 조건절 뒤에 * 추가: 오류
{Allow()}?+      # 조건절 뒤에 + 추가: 오류
{Allow()}??      # 조건절 뒤에 ? 추가: 오류

괄호를 만들면 연산자를 적용할 대상이 괄호의 본문임을 알 수 있습니다. 여기까지는 표기를 읽는 검사입니다. 다음으로 그 본문이 반복해도 안전하게 앞으로 진행하는지 검사합니다. 괄호를 넣었다는 사실만으로 그 두 번째 검사를 통과하는 것은 아닙니다.

03 · 반복은 어디부터 어디까지가 한 번인가

괄호 안의 전체 순서를 한 번 수행합니다.

이번에는 조건과 토큰을 함께 묶어 보겠습니다.

S : ('x' {Allow()}?)* 'y' ;

괄호 안에 x와 조건이 함께 있습니다. 바깥의 별표는 이 괄호의 내용을 0번 이상 수행하라는 뜻입니다. 이때 반복의 한 번은 x를 읽는 일부터 Allow를 확인하는 일까지 모두 마친 것입니다.

1

본문에 들어가기 전 위치를 기억합니다.

예를 들어 위치 0에서 반복을 시작합니다. 다음 토큰은 x입니다.

2

본문의 x를 읽습니다.

x를 Shift했으므로 위치가 0에서 1로 옮겨집니다.

3

본문의 Allow를 확인합니다.

조건이 true이면 본문을 마칩니다. 조건 자체는 토큰을 읽지 않으므로 위치는 1입니다.

4

본문 한 번을 마친 위치를 비교합니다.

시작 위치는 0, 끝 위치는 1입니다. 본문 전체로 보면 토큰 1개를 읽고 앞으로 진행했습니다.

조건이 토큰을 읽지 않아도,
본문 안의 필수 x가 한 번마다 입력을 앞으로 옮깁니다.

04 · 이번에는 괄호에서 x를 빼 봅니다

조건만 있는 본문은, 한 번 마쳐도 같은 위치입니다.

S : 'x' ({Allow()}?)* 'y' ;

맨 앞의 x를 읽고 위치 1, y 앞에 도착했다고 가정하겠습니다. 그다음에 반복할 괄호 안에는 Allow 조건 하나만 있습니다. Allow가 true라면 본문 한 번을 통과합니다. 하지만 y를 읽는 항목은 괄호 바깥에 있습니다.

본문을 한 번 마쳐도 다음 토큰은 y이고 위치도 1입니다. 다시 본문에 들어갈 수 있다고 생각해 보면, 같은 y 앞에서 같은 조건을 또 확인할 수 있습니다. 반복 횟수가 늘어도 읽은 토큰 수는 0개입니다.

가정한 수행시작 위치끝 위치읽은 토큰
본문 첫 번째 수행110개
본문 두 번째 수행110개
본문을 더 수행해도110개

왜 문법을 읽을 때 이 반복을 거절할까요?

입력이 그대로인데도 같은 본문을 계속 완료할 수 있으면, 본문을 몇 번 수행했는지 입력으로 구별할 수 없습니다. 빈 경로가 반복되는 순환과 중복 경로가 만들어질 수 있습니다.

Allow는 실행할 때 전달되는 문맥으로 판단하는 C# 함수입니다. 문법을 만드는 시점에는 특정 입력에서 언제 false가 나올지에 기대어 반복의 종료를 보장할 수 없습니다. 그래서 리더는 본문을 한 번 성공적으로 마칠 때 토큰을 0개 읽는 길이 있는가를 구조로 검사합니다.

조건만 있는 본문은 그런 길이 있습니다. 따라서 ({Allow()}?)*와 ({Allow()}?)+는 문법을 구축하기 전에 오류로 알립니다.

+를 붙여도 같은 문제가 남습니다.

+는 본문을 최소 한 번 수행한다는 뜻입니다. “최소 한 토큰을 읽는다”가 보장되려면 본문이 실제 토큰을 읽어야 합니다. 조건만 있는 본문을 한 번 수행해도 토큰은 0개이고, 그 뒤에는 다시 같은 위치에서 수행할 수 있습니다.

05 · 필수 토큰을 본문 안에 다시 넣습니다

x를 꼭 읽어야 한다면, 성공한 반복은 앞으로 갑니다.

S : ('x' {Allow()}?)* 'y' ;

이 본문은 x를 먼저 읽어야 합니다. 조건이 true라고 해도 x를 생략할 수 없습니다. 따라서 본문을 한 번 성공적으로 마쳤다면 적어도 x 한 개를 읽은 것입니다.

입력 x x y를 따라가 보겠습니다. 첫 번째 본문 수행은 첫 x를 읽고 위치 1에 도착합니다. 두 번째 본문 수행은 두 번째 x를 읽고 위치 2에 도착합니다. 다음 토큰이 y이면 본문의 첫 x를 읽을 수 없으므로 x 반복을 더 진행하지 않고, 괄호 뒤의 y를 읽습니다.

진행한 부분시작 위치끝 위치읽은 토큰
첫 번째 본문01첫 x
두 번째 본문12두 번째 x
반복 뒤의 y23y

*의 “0번 수행”과 본문의 “토큰 0개 소비”를 구별합니다.

별표는 처음부터 본문을 생략하는 길을 허용합니다. 그래서 이 문법은 입력 y만 있어도 괄호를 0번 수행하고 뒤의 y를 읽을 수 있습니다.

진행 검사가 확인하는 대상은 본문에 실제로 들어가 한 번을 완료하는 길입니다. 이 문법의 본문에 들어갔다면 x가 필수이므로 토큰을 읽습니다. 본문에 아예 들어가지 않는 별표의 종료 선택과, 본문 한 번이 빈 채로 끝나는 것은 따로 생각해야 합니다.

        07 · x라는 글자가 보이는 것만으로 판단하지 않습니다
x를 생략할 수 있다면, 빈 본문 경로가 남습니다.

        
S : ('x'? {Allow()}?)* 'y' ;

        
괄호 안에 x가 보이지만 그 뒤에 물음표가 있습니다. 그래서 본문은 x를 읽는 길과, x를 생략하는 길을 모두 갖습니다.
x를 생략한 뒤 Allow가 true라면 본문 한 번을 성공적으로 마칩니다. 그 길에서는 읽은 토큰 수가 0개입니다. 입력을 읽는 길도 있다는 사실이, 빈 길까지 없어지게 만들지는 않습니다.

        
본문의 길 1:  x 읽기 → Allow 통과    → 토큰 1개 읽음
본문의 길 2:  x 생략 → Allow 통과    → 토큰 0개 읽음

* 또는 +의 본문에 길 2가 남음 → 오류

        
이런 성질을 nullable이라고 부릅니다.
nullable은 토큰을 0개 읽고 성공할 수 있는가를 표현하는 문법 용어입니다. 조건 자리는 토큰을 0개 읽습니다. 선택 항목 x?도 생략하는 길이 있습니다. 두 항목을 순서대로 수행해도 0개인 길이 이어질 수 있습니다.
리더의 진행 검사는 반복 본문이 nullable인지 살펴봅니다. 본문이 nullable이면 *와 +를 허용하지 않습니다. 이 검사는 조건 이름이 어떻게 생겼는지보다 본문의 전체 구조를 기준으로 합니다.

        
다른 규칙에 숨겨 놓아도 끝까지 따라갑니다.
S : Piece* 'y' ;
Piece : MaybeX {Allow()}? ;
MaybeX : 'x'? ;
S의 별표 바로 앞에는 Piece라는 이름만 보입니다. Piece의 내용을 보면 MaybeX와 조건이 있고, MaybeX는 x를 생략할 수 있습니다. 그래서 Piece도 토큰을 0개 읽고 끝나는 길이 있습니다.
검사는 참조한 규칙을 따라 nullable 정보를 계산하고, 한 규칙의 정보가 다른 규칙으로 전달되면 다시 반영합니다. 정보가 더 바뀌지 않을 때까지 반복해 Piece의 빈 길을 알아낸 뒤, Piece*를 오류로 표시합니다.

        
순서와 대안도 함께 봅니다.
순서대로 붙은 항목은 모든 항목이 빈 길을 가질 때 전체 순서도 빈 길을 가집니다. 예를 들어 'x' {Allow()}?는 x가 필수이므로 빈 길이 없습니다.
|로 나뉜 대안은 하나라도 빈 길을 가지면 전체 본문에 빈 길이 있습니다. 따라서 ('x' | {Allow()}?)*도 오류입니다. x를 읽는 대안과 별개로, 조건만 확인하는 대안이 본문 한 번을 빈 채로 끝낼 수 있기 때문입니다.

      


      

        08 · 한 번 선택하는 경우는 따로 봅니다
괄호의 ?는 최대 한 번 수행합니다.

        
S : ({Allow()}?)? 'y' ;

        
이번에는 괄호 뒤에 별표나 더하기 대신 물음표를 붙였습니다. 괄호 안의 조건을 한 번 수행하거나, 괄호 전체를 생략할 수 있습니다. 본문을 마친 뒤 다시 같은 본문을 반복하는 구조는 없습니다.
그래서 이 표기는 리더의 반복 진행 검사를 통과합니다. 문법을 읽는 결과는 성공입니다. 그다음 실제 입력을 고르는 과정에서, 같은 입력을 받아들이는 방법이 둘 있는지도 따로 봅니다.

        
Allow가 true일 때의 입력 y를 보겠습니다.
첫 번째 방법은 괄호를 생략하고 y를 읽는 것입니다. 두 번째 방법은 조건을 통과한 뒤 y를 읽는 것입니다. 조건이 토큰을 읽지 않으므로 두 방법 모두 같은 입력 y를 끝까지 받아들입니다.
이 문법에서는 Shift와 조건이 있는 ε Reduce를 예측할 때 두 최초 액션이 모두 입력 끝까지 성공합니다. 현재 Janglim의 선택 정책은 이 경우 AmbiguousPredictionException을 기록하고 파싱 실패로 알립니다.
Allow가 false라면 조건을 수행하는 경로가 탈락합니다. 괄호를 생략하는 경로로 y를 읽을 수 있으므로 입력 y의 파싱에 성공합니다.

        
확인 단계결과
문법 리더최대 한 번 수행하는 구조이므로 허용합니다.
Allow가 false · 입력 y조건 경로를 제외하고, 생략 경로로 파싱에 성공합니다.
Allow가 true · 입력 y두 방법이 같은 입력을 완성하므로 모호성 오류를 기록합니다.

        
반복의 안전성과 입력 선택의 모호성은 각각 확인합니다.
한 번 수행하는 선택은 유한합니다. 그 선택의 두 방법이 같은 입력을 완성할 수는 있습니다.

      


      

        09 · 앞에서 읽은 이유를 표기로 연결합니다
무엇을 검사해서 허용하거나 오류로 알리는가

        
아래 표의 결과는 EBNF 문법을 읽고 구축하는 단계입니다. 옵션에 Allow를 등록해 두었다고 가정합니다. 개별 입력의 파싱 결과는 조건값과 문법의 대안에 따라 결정됩니다.

        
규칙의 본문리더 결과와 이유

          
{Allow()}? 'y'허용조건절 한 개입니다.

          
{Allow()}?* 'y'
{Allow()}?+ 'y'
{Allow()}?? 'y'		표기 오류조건절 바로 뒤에 추가 연산자를 붙였습니다.

          
({Allow()}?)* 'y'
({Allow()}?)+ 'y'		진행 검사 오류본문 한 번이 토큰 0개로 끝날 수 있습니다.

          
({Allow()}?)? 'y'허용선택은 최대 한 번입니다. 입력을 고를 때의 모호성은 따로 검사합니다.

          
('x' {Allow()}?)* 'y'
('x' {Allow()}?)+ 'y'		허용성공하는 본문은 매번 필수 x를 읽습니다.

Piece* 'y'
Piece가 간접적으로 빈 경로를 가짐		진행 검사 오류참조된 규칙의 nullable 정보를 따라 검사합니다.

        

        
세 단계의 순서로 생각하면 됩니다.
먼저 {Name()}?와 괄호·연산자 표기를 읽습니다. 다음에는 *와 +의 본문에 빈 경로가 있는지 검사합니다. 이 두 단계를 통과한 문법으로 파싱 테이블을 만들고, 실제 입력에서 조건과 액션 선택을 처리합니다.
예측 함수는 원래 테이블 칸에 정확히 Shift 하나와 조건이 있는 ε Reduce 하나가 겹친 경우를 처리합니다. 후보의 상태와 토큰 위치를 시험하고, 가능한 최초 액션의 번호가 하나로 좁혀지면 그 액션을 반환합니다. SelectFirstAction 동작 문서에서 이 선택을 처음부터 따라갈 수 있습니다.

      


      

        10 · ANTLR4에서도 같은 구조를 확인합니다
직접 표기 오류와 빈 반복 오류를 구별합니다.

        
ANTLR4 4.13.2의 생성 도구로 아래 문법들을 직접 실행해 확인했습니다. 조건 함수 Allow는 true를 반환하도록 등록했습니다. ANTLR 예제에서는 시작 규칙 이름을 소문자 s로 적고 마지막에 EOF를 명시합니다.

        
grammar Example;
@parser::members {
    boolean Allow() { return true; }
}
s : ('x' {Allow()}?)* 'y' EOF ;
아래 비교에서는 s의 본문을 각각 바꾸어 생성 도구의 결과를 확인했습니다.

        
ANTLR 규칙 s의 본문확인 결과

          
{Allow()}?* 'y' EOF
{Allow()}?+ 'y' EOF
{Allow()}?? 'y' EOF		error(50)

({Allow()}?)+ 'y' EOF		error(153)
반복 본문에 입력을 0개 읽는 경로가 있습니다. 종료 코드는 1입니다.

선택 본문에 빈 경로가 있습니다. 경고와 함께 생성하며 종료 코드는 0입니다.

진단 번호와 의미는 ANTLR 4.13.2 ErrorType에서 확인할 수 있습니다. 직접 조건 뒤의 표기는 ANTLRParser.g의 element·actionElement 규칙에 정의되어 있습니다.

        
Janglim의 입력 선택 결과는 앞에서 설명한 정책을 따릅니다.
Janglim도 직접 조건절에 추가 연산자를 붙인 표기와, 빈 경로를 가진 반복을 각각 거절합니다. 조건만 들어 있는 선택 그룹은 유한하므로 리더가 허용합니다. 실제 입력에서 두 최초 액션이 끝까지 함께 성공하면 Janglim은 앞에서 살펴본 모호성 오류를 기록합니다.
ANTLR 표의 warning(154)는 문법을 생성할 때의 경고입니다. Janglim의 AmbiguousPredictionException은 실제 입력에서 두 최초 액션을 끝까지 구별하지 못했을 때의 파싱 결과입니다. 각 도구의 확인 단계와 판단 정책을 함께 읽어야 결과를 정확히 이해할 수 있습니다.

      


      

        11 · 문법을 실제 C# 프로그램에 연결합니다
조건 이름과 검사 함수를 등록한 뒤 읽습니다.

        
문법 안에는 조건 이름 Allow를 적었습니다. 프로그램에서는 그 이름에 실행할 C# 함수를 연결합니다. EbnfReaderOptions를 만들고 RegisterPredicate를 호출한 다음, Read에 옵션을 함께 넘깁니다.

        
using Janglim.FrontEnd.Grammars.Ebnf;

var options = new EbnfReaderOptions()
    .RegisterPredicate("Allow", context => true);

var read = EbnfGrammarReader.Read(
    "S : ('x' {Allow()}?)* 'y' ;", options);

if (!read.Success)
{
    // 표기 오류나 반복 진행 오류의 설명이 들어 있습니다.
    foreach (var error in read.Errors)
        System.Console.WriteLine(error);
}
else
{
    var grammar = read.Grammar;
    // 이 문법으로 렉서와 LALRParser를 구성합니다.
}

        
context는 조건을 확인하는 자리의 토큰 정보입니다.
PreviousToken은 바로 앞의 토큰이고, NextToken은 지금 확인할 토큰입니다. TokenIndex는 EOF를 포함한 목록에서 0부터 세는 위치입니다. IsEndOfInput은 현재 다음 토큰이 입력 끝인지 알려 줍니다.
반복 예시에서 첫 x를 읽은 뒤에는 PreviousToken이 그 x이고, NextToken은 다음 x 또는 y입니다. 조건을 여러 번 나란히 확인하는 동안 토큰을 읽지 않았다면 TokenIndex도 같은 번호를 유지합니다.
NextToken의 LeadingTrivia.Text로 앞의 공백·주석 원문을 읽고, HasLineBreakBefore로 줄바꿈을 확인할 수 있습니다. 입력 시작의 PreviousToken은 null입니다. 토큰 하나만 받는 독립 UnitParsing 호출에서는 PreviousToken이 null, TokenIndex가 -1입니다. 복구로 토큰을 바꾼 경우에는 복구된 토큰열의 문맥을 이어서 사용하고, 원문의 글자 위치는 TokenData.StartIndex에 보관합니다.

        
조건은 같은 문맥에 같은 답을 내도록 작성합니다.
파서는 실제로 실행할 액션을 고르려고 복사한 상태로 후보를 시험합니다. 따라서 동일한 조건 함수를 예측 중에 여러 번 호출할 수 있습니다. 조건이 외부 값을 바꾸거나 호출 횟수에 따라 결과를 바꾸면 후보 비교의 의미도 바뀝니다.
조건은 전달받은 정보를 읽고 true 또는 false를 반환하는 순수한 검사로 둡니다. 파일 저장이나 실제 처리 결과 반영은 선택한 파싱 결과를 받은 뒤에 수행합니다.
함수가 예외를 던지면 GrammarPredicateEvaluationException으로 조건 이름, 검사 문맥, 원래 예외를 보관합니다. false는 해당 후보의 조건 실패이고, 예외는 검사 함수 실행의 실패이므로 각각 구별합니다.

        
반복 검사와 실행 중의 보호 장치가 각각 역할을 맡습니다.
문법의 반복 본문이 nullable인지 확인하는 검사는 문법을 구축할 때 수행합니다. 파싱 테이블의 후보를 실제 입력에 맞추어 시험하는 예측은 파싱 중에 수행합니다.
예측은 확인할 토큰 수 k를 미리 고정하지 않고, 첫 행동이 하나로 좁혀질 때까지 필요한 입력을 살펴봅니다. 전이 횟수·상태 구성 수·상태 스택 깊이에는 내부 자원 한도를 두고, 같은 토큰 앞에서 되풀이되는 상태도 검사합니다. 이 보호 장치에 도달하면 원인을 오류로 알립니다.

        관련 검사 · 반복 몸체와 재귀 진입을 구분합니다
        
조건을 거쳐 같은 규칙으로 돌아오는 경로도 검사합니다.

        
반복 몸체 한 번의 입력 진행과 함께, 조건절을 지나 같은 규칙으로 재진입할 때까지 토큰을 읽는지도 확인합니다. 다음 문법에서는 뒤의 x를 읽기 전에 조건절을 거쳐 A에 다시 들어갈 수 있습니다.

        
A : {Allow()}? A 'x' | 'x' ;

        
A → Allow → A
소비한 입력 토큰: 0개
→ 문법 오류

        
이 문법의 대안 전체에는 x가 있습니다. 하지만 검사할 구간은 “같은 규칙으로 다시 들어가기 전까지”입니다. 조건 예측에서 이 구간의 재귀 후보가 계속 늘어날 수 있어, 문법을 준비할 때 해당 경로를 차단합니다.

        
핵심은 세 단계입니다. 조건절이 관련된 좌재귀 후보를 모으고 → 조건을 거쳐 토큰 없이 복귀하는 경로를 찾고 → 그 경로를 문법 오류로 알려줍니다. 일반적인 좌재귀는 그대로 허용합니다.
