Script의 엄격 모드를 선택하고,
브라우저 호환 문법은 따로 켭니다.

JavaScriptMode.NonStrict를 선택하면 Janglim은 비엄격 모드 Script를 읽습니다. 여기에 webCompatibility: true를 지정하면 오래된 웹 스크립트와의 호환 문법도 함께 적용합니다.

예를 들어 비엄격 코드에는 077 같은 구형 숫자 리터럴을 적을 수 있습니다. HTML 형태의 주석 <!-- ...을 읽으려면 웹 호환 옵션도 켭니다. 엄격 모드를 선택하는 일과 웹 호환 문법을 선택하는 일은 각각 따로 설정합니다.

기본 생성자 new JavaScriptGrammar()는 엄격 모드 Script를 읽으며, 웹 호환 옵션은 꺼져 있습니다. 아래에서는 먼저 비엄격 입력을 검사하는 C# 코드를 살펴보고, 두 설정이 무엇을 바꾸는지 차례로 설명합니다.

1. 모드를 정한 뒤, Parsing과 Validate를 순서대로 호출합니다.

JavaScriptGrammar의 기본 입력 종류는 여러 선언과 문장으로 구성된 Script입니다. 다음 C# 코드는 이 기본 입력에 비엄격 모드와 웹 호환 문법을 켠 뒤, HTML 주석과 구형 숫자 리터럴이 들어 있는 Script를 검사합니다.

using System;
using Janglim.FrontEnd.Grammars.JavaScript;
using Janglim.FrontEnd.Parsers.LR;

var language = new JavaScriptGrammar(
    JavaScriptMode.NonStrict,
    webCompatibility: true);
var parser = new LALRParser(language.Grammar);

// 아래 문자열이 실제 JavaScript 입력입니다.
var input = @"<!-- 이전 웹 문서의 주석
var total = 077;
with (settings) {
    total = value;
}";

var parsed = parser.Parsing(language.CreateTokenSource(input));
if (!parsed.Success)
{
    Console.WriteLine(parser.FiredException?.Message ?? "파싱 오류");
    return;
}

var diagnostics = language.Validate(parsed.ToParseTree);
foreach (var diagnostic in diagnostics)
    Console.WriteLine($"{diagnostic.Code}: {diagnostic.Message} " +
        $"(위치 {diagnostic.SourceOffset}, 길이 {diagnostic.Length})");

if (diagnostics.Count == 0)
    Console.WriteLine("문법 검사 통과");

Parsing은 입력을 구문 트리로 만듭니다. 이어서 Validate는 각 구문이 놓인 위치의 엄격 모드와 이름·대입 대상 등의 조건을 검사합니다. 개발자는 파싱 성공과 정적 진단 0개를 함께 확인해야 합니다. 입력한 JavaScript의 실행 결과 대신 구문 트리와 진단을 받는 사용 순서입니다.

표현식 하나나 모듈 파일도 같은 클래스로 검사합니다. 달라지는 설정은 inputKind입니다. 다음 코드는 각각 비엄격 표현식 하나와 웹 호환 옵션을 켠 모듈을 준비합니다.

// 예: 077 + value
var expression = new JavaScriptGrammar(
    mode: JavaScriptMode.NonStrict,
    inputKind: JavaScriptInputKind.Expression);

// 예: import {value} from './settings.js';
var module = new JavaScriptGrammar(
    webCompatibility: true,
    inputKind: JavaScriptInputKind.Module);

선택한 입력 종류는 InputKind에 보관하며, Module의 Mode는 항상 Strict입니다. 모듈 예제의 웹 호환 옵션은 그 엄격 모드를 유지하면서 Module에도 적용할 수 있는 호환 조건만 켭니다. 따라서 엄격 모드와 웹 호환 여부는 서로 다른 설정이며, 다음 절에서 이 차이를 구체적으로 살펴봅니다.

2. Mode는 엄격 모드를, WebCompatibility는 웹 호환 조건을 정합니다.

Mode는 Script 또는 표현식 입력이 어떤 엄격 모드에서 시작하는지 정합니다. NonStrict로 시작해도 함수의 "use strict" 지시문이나 클래스 때문에 안쪽 코드가 엄격 모드가 될 수 있습니다.

WebCompatibility는 별도의 웹 호환 규칙을 적용할지 정합니다. 이 규칙마다 엄격 모드와 입력 종류에 대한 조건이 다릅니다. 그래서 웹 호환 옵션을 비엄격 모드 안에 묶으면, 엄격 코드에서도 허용해야 하는 호환 문법을 표현하기 어렵습니다.

HTML 주석은 엄격 Script에서도 웹 호환 옵션으로 켤 수 있습니다.

다음은 실제 JavaScript 입력입니다. 이 Script는 첫 줄에서 엄격 모드를 선택하지만, 웹 호환 옵션을 켜면 두 번째 줄의 HTML 주석을 허용합니다. Module에서는 웹 호환 옵션을 켜도 HTML 주석을 허용하지 않습니다.

"use strict";
<!-- 웹 호환 Script 주석
value;

단순 catch 매개변수와 var의 이름 중복 예외는 Module에도 적용합니다.

다음 입력은 error 하나를 catch 매개변수로 받으며, catch 블록에서 같은 이름을 var로 선언합니다. 웹 호환 옵션을 켜면 이 형태는 엄격 Script와 Module에서도 허용합니다. catch 매개변수가 구조 분해 패턴인 경우에는 기존 이름 충돌 조건을 적용합니다.

try {
    read();
} catch (error) {
    var error;
}

두 예제에서 엄격 모드는 그대로 유지됩니다. 웹 호환 옵션은 각 항목에 정해진 예외만 추가합니다. 세부 조건은 Annex B.1.1과 B.3.4를 따릅니다.

3. 비엄격 모드의 기본 문법은 웹 호환 옵션 없이 사용합니다.

이제 new JavaScriptGrammar(JavaScriptMode.NonStrict)를 선택했다고 가정하겠습니다. 웹 호환 옵션은 기본값인 끄기 상태입니다. 이 설정으로도 다음과 같은 비엄격 문법을 읽을 수 있습니다.

var legacy = 077;
var decimal = 08.5;
var text = "\141\8";
var eval = 1;
delete value;
with (settings) { value = next; }
function pick(value, value) { return value; }

위 입력에서 077은 구형 8진수 리터럴이고, 08.5는 앞에 0이 붙은 구형 10진수 리터럴입니다. 문자열의 \141과 \8도 비엄격 코드에서 허용하는 이스케이프입니다. eval 바인딩, 식별자를 대상으로 하는 delete, with 문도 해당 코드가 비엄격 모드일 때 허용합니다.

마지막 함수처럼 단순 식별자만 받는 목록에서는 비엄격 함수의 중복 매개변수를 허용합니다. 이 조건은 일반·async·제너레이터·async 제너레이터의 함수 선언과 함수 표현식에 적용합니다. 반면 화살표 함수와 객체·클래스 메서드는 같은 이름의 매개변수를 중복해서 받을 수 없습니다. 함수 종류와 관계없이 기본값·구조 분해·rest가 있는 목록에서도 중복 이름을 금지합니다.

yield·let·static 같은 이름도 문맥에 맞춰 검사합니다. 예를 들어 비엄격 일반 코드에서는 var yield = 1;을 허용하지만, 제너레이터 안에서는 yield의 예약어 조건을 적용합니다. NonStrict는 비엄격 코드에 정해진 문법을 선택하며, 함수 종류와 선언 위치에 대한 검사는 함께 유지합니다.

앞의 예제를 함수나 클래스 안에 넣으면 엄격 모드가 달라질 수 있습니다. 따라서 다음으로는 원문 전체에 설정한 모드와 실제 코드 구간의 모드를 구분해 봅니다.

4. 안쪽 코드의 엄격 모드는 지시문과 포함 관계로 결정합니다.

비엄격 Script 안에서도 함수 본문이 "use strict" 지시문으로 시작하면 그 함수는 엄격 모드입니다. 그 함수 안에 정의한 함수도 엄격 모드를 이어받습니다. 다음 입력에서 inner의 구형 숫자는 오류이지만, 바깥의 별도 함수 sibling은 비엄격 모드를 유지합니다.

function outer() {
    "use strict";
    function inner() {
        return 077;       // 오류: outer의 엄격 모드를 이어받음
    }
}

function sibling() {
    return 077;           // 허용: 비엄격 Script의 별도 함수
}

검사기는 함수의 매개변수와 본문 전체에 이 엄격 모드를 적용합니다. 지시문 앞에 다른 문자열 문장이 있더라도, 그 문장들이 지시문 영역을 이루고 뒤에 "use strict"가 나오면 같은 함수 전체가 엄격 모드가 됩니다. 이 때문에 앞쪽 문자열의 구형 이스케이프도 오류로 찾아야 합니다.

function read() {
    "\1";                 // 오류: 같은 함수의 엄격 모드가 적용됨
    "use strict";
}

일반 블록 안의 문자열 { "use strict"; ... }은 새로운 엄격 모드 지시문 영역을 만들지 않습니다. 괄호로 감싼 ("use strict")나 이스케이프를 사용한 "use\x20strict"도 엄격 모드 지시문으로 취급하지 않습니다. 검사기는 Script와 함수 본문 앞의 실제 지시문 표기를 확인합니다.

클래스는 비엄격 Script 안에서도 엄격 모드입니다.

클래스의 필드 초기값·메서드·static 블록에는 클래스의 엄격 모드를 적용합니다. 따라서 다음 클래스에서 필드 초기값 077과 메서드 안의 with 문은 모두 오류입니다.

class Store {
    value = 077;                      // 오류: 클래스 코드
    read() { with (settings) {} }      // 오류: 클래스 메서드 본문
}

객체 메서드의 계산된 이름은 그 메서드를 정의한 바깥 문맥에 속합니다.

다음 객체에서 대괄호 안의 077은 바깥 비엄격 코드의 표현식입니다. 반면 메서드 본문은 자신의 "use strict" 지시문으로 엄격 모드가 됩니다. 그러므로 계산된 이름의 숫자는 허용하고, 본문의 같은 숫자는 오류로 처리합니다.

({
    [077]() {             // 허용: 바깥 비엄격 문맥의 계산된 이름
        "use strict";
        return 077;       // 오류: 이 메서드의 엄격 본문
    }
})

클래스의 계산된 멤버 이름은 클래스 자체가 엄격 모드인 조건을 함께 받습니다. Module도 전체가 엄격 모드이므로, 안쪽 함수를 정의해도 그 엄격 모드를 이어받습니다. 이 구간별 판정은 ECMAScript 2026의 엄격 모드 조건을 따릅니다.

5. 비엄격 입력의 리터럴은 구문 트리를 만든 뒤 사용 조건을 검사합니다.

앞 절의 "\1"; "use strict";를 다시 보겠습니다. 토큰 공급자가 첫 번째 문자열을 읽을 때에는 뒤의 지시문과 함수의 전체 구문 트리를 아직 읽지 않은 상태입니다. 첫 번째 문자열만 보고 비엄격 리터럴의 사용 조건까지 확정하면, 뒤에서 정해지는 엄격 모드를 놓칠 수 있습니다.

그래서 비엄격 모드로 시작한 입력에서는 토큰 공급자가 구형 숫자·문자열의 형태를 읽고 원문을 보존합니다. 파서가 트리를 완성하면 JavaScriptStrictness가 코드 구간별 모드를 정합니다. 마지막으로 Validate가 엄격 구간의 리터럴에서 금지된 표기를 찾습니다. 리터럴을 토큰으로 읽는 일과, 그 위치에서 사용할 수 있는지 검사하는 일을 순서대로 처리합니다.

엄격 구간의 구형 리터럴 진단
Code진단 범위
strict_legacy_numeric_literal077·08.5 같은 숫자 토큰 전체
strict_legacy_string_escape문자열 안의 첫 번째 금지 이스케이프. \400에서는 실제 이스케이프인 \40 부분

진단의 SourceOffset과 Length는 UTF-16 코드 단위입니다. 따라서 input.Substring(diagnostic.SourceOffset, diagnostic.Length)로 문제 원문을 바로 가져올 수 있습니다.

모드가 달라져도 잘못된 Unicode 코드 포인트나 중복 정규식 플래그 같은 기본 토큰 오류는 계속 검사합니다. 숫자 00n·08_1도 허용하지 않습니다. 08.1_2처럼 표준이 허용하는 소수부의 구분자와 구형 정수부 안의 구분자를 구분해야 하기 때문입니다. 리터럴의 모드별 조건은 12.9.3과 12.9.4에 정의되어 있습니다.

여기까지 설명한 검사는 기본 비엄격 문법에 대한 처리입니다. 이제 웹 호환 옵션을 추가로 켰을 때 적용하는 항목을 따로 정리합니다.

6. 웹 호환 옵션은 각 Annex B 항목의 적용 조건을 확인합니다.

webCompatibility: true는 아래 문법과 정적 검사 예외를 선택합니다. 표에서 비엄격 조건이 붙은 항목은 지시문·클래스 때문에 엄격 모드가 된 구간에서는 허용하지 않습니다.

항목적용하는 형태와 조건
B.1.1 HTML 주석Script의 <!--와 줄 시작 조건의 -->. 엄격 Script에도 허용하며 Module에서는 금지합니다.

B.3.3 if의 함수 선언비엄격 코드의 if·else 본문에 바로 적는 일반 함수 선언입니다.

닫는 HTML 주석은 같은 글자가 연산자로 쓰인 경우와 구분합니다.

<!--는 그 위치부터 줄 끝까지 주석으로 읽습니다. 반면 -->는 원문 시작이나 줄바꿈 뒤에 공백·주석만 앞선 위치에서 닫는 주석으로 읽습니다. 줄바꿈이 포함된 블록 주석 뒤도 이 조건에 맞춰 처리합니다. 실제 입력과 토큰 위치는 그대로 보존합니다.

value; <!-- 주석
--> 이 줄도 주석
a-->b;                 // 이 위치에서는 a-- 와 > 연산자로 읽음

함수 선언 예외는 일반 함수와 허용된 문장 위치에 한정합니다.

레이블과 if의 호환 형태에는 일반 함수 선언을 사용합니다. async 함수·제너레이터 선언이나 while·for·with 바로 뒤의 함수 선언까지 같은 방식으로 허용하지 않습니다. 중괄호 블록에 함수를 선언하는 표준 형태는 별도로 사용할 수 있습니다.

블록 함수의 경우에는 일반 함수 선언끼리의 중복 이름 조건을 완화합니다. 같은 범위의 let·const·클래스와 충돌하는 이름은 계속 검사합니다. 이 단계에서 다루는 B.3.2의 범위는 구문과 정적 이름 검사이며, 실행 시 바인딩 생성은 JavaScript 실행 환경의 역할입니다.

호출을 대입 대상으로 허용하면 실행 시 오류로 넘어가는 형태도 표현할 수 있습니다.

웹 호환 비엄격 코드에서는 call() = value 같은 형태를 구문·정적 검사에서 수락합니다. 이 형태는 JavaScript에서 실제 대입을 평가할 때 ReferenceError가 되는 호환 구문입니다. Janglim은 해당 원문의 트리와 정적 검사 결과를 반환합니다.

허용 범위에는 일반 대입과 산술·비트 복합 대입, 증감과 반복 대상이 포함됩니다. call() &&= value 같은 논리 대입, [call()] = values 같은 구조 분해 대상, 선택적 호출·new·태그 템플릿에는 이 예외를 적용하지 않습니다. 세부 기준은 고정된 ECMAScript 2026 Annex B를 따릅니다.

JavaScript 문법과 정적 검사 계층이 모드별 차이를 담당합니다.

공통 렉서와 LR 파서는 기존 토큰 공급자·정책·프레디케이트 구조를 사용합니다. JavaScriptGrammar가 입력 종류와 모드에 맞는 토큰 규칙·시작 규칙·정책을 준비하고, 최종 트리의 검사기가 코드 구간별 조건을 확인합니다.
