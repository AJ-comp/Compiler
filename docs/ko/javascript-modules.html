모듈의 import·export를 파싱하고,
선언한 이름과 사용 문맥을 검사합니다.

JavaScriptGrammar에서 Module 입력을 선택하면 다른 모듈에서 이름을 가져오는 import와 현재 모듈의 이름을 공개하는 export를 읽습니다. 개발자는 입력을 파싱한 뒤 Validate를 호출해 중복된 이름, 선언하지 않은 이름의 export, 잘못된 await 사용을 검사합니다.

예를 들어 import {calculate} from './math.js'; export const answer = calculate(6, 7);을 입력하면, 파서는 import 선언과 변수 선언·함수 호출·export의 구조를 하나의 구문 트리로 만듭니다. 그다음 Validate는 가져온 이름 calculate와 새로 선언한 이름 answer가 이 모듈의 다른 선언과 충돌하는지 확인합니다.

Module도 문법 준비 → 입력 파싱 → 정적 오류 검사 순서로 사용합니다. 먼저 Module 입력을 따로 선택하는 이유와 C# 사용 코드를 살펴본 뒤, import와 export의 각 형태를 차례로 설명합니다.

1. import·export가 있는 파일은 Module 문법으로 읽습니다.

JavaScript 명세는 일반 Script와 Module을 서로 다른 시작 문법으로 정합니다. Module에서는 최상위 import·export와 import.meta를 사용할 수 있고, 함수 밖에서도 await를 사용할 수 있습니다. Janglim에서는 클래스 하나를 사용하되, 생성자의 inputKind로 이 검사 문맥을 선택합니다.

JavaScriptGrammar에서 선택하는 입력 종류
입력JavaScriptInputKind
Script의 선언·문장 목록Script — 기본값
Module의 import·export와 선언·문장 목록Module — 항상 엄격 모드
Script 문맥의 표현식 하나Expression

어떤 입력 종류를 선택해도 파싱과 검사의 사용 순서는 같습니다. 다음 C# 코드는 inputKind: JavaScriptInputKind.Module로 모듈 문법을 준비하고, 모듈 원문을 입력한 뒤 정적 오류까지 검사합니다.

using System;
using Janglim.FrontEnd.Grammars.JavaScript;
using Janglim.FrontEnd.Parsers.LR;

var language = new JavaScriptGrammar(inputKind: JavaScriptInputKind.Module);
var parser = new LALRParser(language.Grammar);
var input = @"
import {calculate} from './math.js';
export const answer = calculate(6, 7);
";

var source = language.CreateTokenSource(input);
var parsed = parser.Parsing(source);
if (!parsed.Success)
{
    Console.WriteLine(parser.FiredException?.Message);
    return;
}

var diagnostics = language.Validate(parsed.ToParseTree);
if (diagnostics.Count > 0)
{
    foreach (var diagnostic in diagnostics)
        Console.WriteLine($"{diagnostic.Code}: {diagnostic.Message} " +
            $"(위치 {diagnostic.SourceOffset}, 길이 {diagnostic.Length})");
    return;
}

Console.WriteLine(parsed.ToParseTree.AllInputDatas);

CreateTokenSource는 입력 원문을 토큰 단위로 읽을 공급자를 만들고, Parsing은 그 토큰으로 구문 트리를 만듭니다. 이어서 Validate가 트리의 선언과 사용 문맥을 검사합니다. 파싱 성공과 빈 진단 목록을 함께 확인해야 문법 검사가 끝납니다.

이 예제에서 './math.js'는 원문에 적힌 모듈 경로입니다. Janglim은 이 경로를 구문 트리에 보존합니다. 실제 파일을 읽고 의존 모듈을 연결하거나 calculate를 실행하는 일은 이 구문 검사 다음에 필요한 애플리케이션에서 담당합니다.

2. 정적 import는 가져올 이름과 모듈 경로를 선언합니다.

모듈 파일의 최상위에는 다음 형태의 import 선언을 작성할 수 있습니다. 각 줄은 가져오는 대상의 종류가 다릅니다.

import './setup.js';
import calculate from './calculate.js';
import * as tools from './tools.js';
import {parse, format as formatText} from './text.js';

첫 번째 선언은 가져올 이름 없이 모듈 경로만 적습니다. 두 번째 선언은 상대 모듈의 default 항목을 가져와 이 모듈에서 calculate라는 이름으로 사용합니다. 세 번째 선언의 tools는 상대 모듈의 공개 항목들을 속성으로 접근할 이름입니다.

네 번째 선언은 상대 모듈의 parse와 format을 가져옵니다. parse는 같은 이름으로 사용하고, format as formatText는 가져온 format을 이 모듈에서 formatText라는 이름으로 사용하겠다는 뜻입니다.

default 항목과 다른 항목을 함께 가져올 수도 있습니다. 다음 예제의 각 줄은 별도 모듈 입력입니다.

import main, {parse, format} from './text.js';
import main, * as tools from './tools.js';

가져온 이름은 이 모듈의 선언 범위에 추가됩니다. 따라서 import {parse} from './text.js'; let parse;처럼 같은 범위에 parse를 다시 선언하면 Validate가 이름 충돌을 알립니다.

이 선언은 Module 최상위에 작성합니다. 함수나 if·블록의 실행 중에 모듈을 불러오는 표현식이 필요하면, 뒤에서 설명하는 동적 import를 사용합니다.

3. export는 현재 모듈의 공개 이름을 정합니다.

import로 이름을 가져왔다면, export는 이 모듈이 다른 모듈에 공개할 이름을 정합니다. 먼저 선언과 export를 나누어 작성하는 예제를 보겠습니다.

const answer = 42;
export {answer};

이 모듈은 answer를 선언한 뒤 같은 이름으로 공개합니다. 공개 이름을 바꾸려면 export {answer as result};처럼 작성합니다. 이때 모듈 안의 변수 이름은 answer이고, 상대 모듈이 가져갈 이름은 result입니다.

선언 앞에 export를 붙이면 선언과 공개를 한 번에 표현할 수 있습니다.

export const answer = 42;
export function read() { return answer; }
export class Counter { value = 0; }

이 예제는 answer·read·Counter를 선언하고 각각 같은 이름으로 공개합니다. 변수의 구조 분해 선언도 사용할 수 있으며, 선언한 각 이름이 공개됩니다.

default 항목은 모듈마다 하나의 이름으로 공개합니다.

default export는 공개 이름 default를 사용하는 형태입니다. 다음 세 예제는 각각 별도의 모듈입니다.

export default 42;

export default function read() { return 42; }

export default class Counter { value = 0; }

일반 표현식과 함수·클래스 선언을 default 항목으로 공개할 수 있습니다. 함수와 클래스에는 이름을 생략할 수도 있습니다. 이름이 있는 default 선언의 read나 Counter는 이 모듈 안에서도 사용할 수 있는 선언 이름입니다.

반면 export default (class Counter {});는 괄호로 감싼 클래스 표현식의 값을 공개합니다. 이 표현식의 Counter 이름은 클래스 표현식 안에 속합니다. Module 최상위의 이름으로 추가되지 않으므로, 이 이름을 별도의 local export 대상으로 사용할 수 없습니다.

from을 붙이면 다른 모듈의 항목을 다시 공개합니다.

export {parse as parseCode} from './parser.js';
export * from './values.js';
export * as helpers from './helpers.js';

첫 번째 선언은 상대 모듈의 parse를 parseCode라는 이름으로 다시 공개합니다. 두 번째 선언은 상대 모듈의 default를 제외한 공개 항목들을, 세 번째 선언은 상대 모듈의 공개 항목들을 모은 항목 하나를 helpers라는 이름으로 공개합니다.

이처럼 from을 사용하는 재내보내기는 다른 모듈에 공개할 이름을 정합니다. 현재 모듈 안에서도 해당 항목을 변수로 사용하려면 별도의 import 선언을 작성합니다. Janglim의 정적 검사도 재내보낼 이름과 현재 모듈의 선언 이름을 구분합니다.

공개 이름에는 문자열도 사용할 수 있습니다.

// 이름을 공개하는 모듈
const value = 42;
export {value as 'answer-value'};

// 그 이름을 가져오는 다른 모듈
import {'answer-value' as answer} from './value.js';

'answer-value'는 공개 이름이고, answer는 현재 모듈에서 사용할 변수 이름입니다. 공개 이름은 문자열일 수 있지만, 가져온 항목을 사용할 변수에는 유효한 식별자 이름이 필요합니다.

문자열 공개 이름은 Unicode 이스케이프를 해독한 값으로 비교합니다. 따라서 'name'과 '\u006eame'은 같은 이름입니다. 문자열 공개 이름에 짝이 없는 surrogate가 들어간 경우도 정적 오류로 검사합니다.

4. with 속성은 import와 재내보내기에 부가 정보를 붙입니다.

지금까지의 예제는 모듈 경로만 지정했습니다. 모듈 종류 같은 부가 정보가 필요하면 경로 뒤에 with와 속성 목록을 붙일 수 있습니다.

import data from './data.json' with {type: 'json'};
export {default as data} from './data.json' with {type: 'json'};

속성 이름은 식별자나 문자열로, 속성 값은 문자열로 작성합니다. 빈 목록 with {}와 마지막 쉼표도 허용합니다. 두 속성 이름의 이스케이프를 해독한 결과가 같으면 중복 이름으로 처리합니다.

import data from './data.json'
    with {type: 'json', 'type': 'other'}; // 오류: 속성 이름 type 중복

이 구문에서 Janglim이 검사하는 것은 속성 목록의 형태와 이름 중복입니다. 호스트가 어떤 속성이나 값을 지원하는지, type: 'json'에 따라 파일을 어떻게 읽을지는 실제 모듈 로더가 결정합니다.

5. 동적 import는 표현식이 들어갈 자리에 작성합니다.

정적 import는 모듈 최상위의 선언이었습니다. 반면 import('./feature.js')는 값을 만드는 표현식이므로 함수 안이나 조건문의 본문에도 작성할 수 있습니다.

function loadFeature() {
    return import('./feature.js');
}

const loadData = () =>
    import('./data.json', {with: {type: 'json'}});

ECMAScript 실행 환경에서 이 표현식은 모듈을 불러오는 작업의 Promise를 만듭니다. Janglim은 호출의 구조와 인수 표현식을 파싱합니다. 따라서 위 예제의 함수나 동적 import를 실행하지 않고도 구문을 검사할 수 있습니다.

동적 import는 세 입력 종류에서 모두 사용할 수 있습니다. Expression 입력에는 import('./feature.js') 자체를, Script·Module 입력에는 위와 같이 선언·문장과 함께 전달합니다.

인수는 한 개 또는 두 개이며, 끝의 쉼표를 허용합니다. 첫 번째 인수는 모듈 경로를 계산할 표현식이고, 두 번째 인수는 옵션을 계산할 표현식입니다.

import(path)
import(path,)
import(path, options)
import(path, options,)

import()처럼 인수를 생략하거나, 세 번째 인수 또는 펼치기 인수 ...items를 넣으면 구문 오류입니다. 한편 두 번째 인수의 {with: {type: 'json'}}은 일반 객체 표현식입니다. 정적 선언의 with { ... }와 달리 이 객체에는 일반 표현식·객체의 검사 규칙을 적용합니다.

동적 import의 결과에는 import(path).then(handle)처럼 속성 접근과 호출을 이어 붙일 수 있습니다. import 자체를 변수에 담거나 new import(path)처럼 생성자 자리에 직접 쓰는 형태는 허용하지 않습니다.

6. import.meta는 현재 모듈의 정보를 가리키는 표현식입니다.

동적 import가 다른 모듈을 불러올 표현식이라면, import.meta는 현재 모듈에 대한 정보를 가리킵니다. 이 표현식은 Module 입력에서 사용합니다.

export const moduleUrl = import.meta.url;

export function getModuleUrl() {
    return import.meta.url;
}

두 번째 예제처럼 같은 모듈 안의 일반 함수에서도 import.meta를 사용할 수 있습니다. 함수 안에 들어가도 원문을 읽는 시작 문법은 계속 Module이기 때문입니다. 반면 Script나 독립 Script 표현식 입력에서 이 표현식을 사용하면 Validate가 문맥 오류를 반환합니다.

문법 표기는 import.meta이며 meta를 Unicode 이스케이프로 바꾼 표기는 허용하지 않습니다. 그 뒤의 url은 일반 속성 이름입니다. 어떤 속성이 실제로 제공되는지는 호스트가 정하며, Janglim은 속성 접근의 구문을 검사합니다.

7. Module 최상위에서는 await와 for-await-of를 사용할 수 있습니다.

Module의 문장과 표현식은 비동기 작업을 기다리는 await를 함수 밖에서 사용할 수 있습니다. 이 사용 형태를 top-level await라고 부릅니다.

const feature = await import('./feature.js');
export const value = feature.value;

for await (const item of stream) {
    consume(item);
}

첫 번째 문장은 동적 import의 결과를 기다린 뒤 feature에 저장하는 구문입니다. 반복문은 비동기 반복이 제공하는 값을 차례로 받을 구문입니다. Janglim은 await·반복문과 본문의 구조를 파싱하고 사용 위치를 검사합니다.

여기서 최상위는 중괄호가 하나도 없는 자리만을 뜻하지 않습니다. 모듈의 if·블록·반복문 안에 있어도 일반 함수의 본문으로 들어가지 않았다면 같은 Module 평가 문맥을 사용합니다.

if (enabled) {
    const feature = await import('./feature.js'); // 허용
}

function loadFeature() {
    return await import('./feature.js');        // 오류: 일반 함수 본문
}

const load = () => await import('./feature.js'); // 오류: 일반 화살표 함수 본문

일반 함수와 async 수식이 없는 화살표 함수는 자기 본문의 문법 문맥을 만듭니다. 따라서 바깥 모듈에서 await를 사용할 수 있어도, 이 함수들의 매개변수·본문에는 await 표현식을 사용할 수 없습니다. 반면 async 함수·async 화살표와 async 제너레이터는 자기 본문에서 await를 사용할 수 있습니다. 함수별 문맥과 매개변수 조건은 함수 종류별 문서에서 이어서 설명합니다.

클래스도 각 부분이 평가되는 문맥을 구분합니다. 다음 클래스의 부모 클래스 표현식과 계산된 속성 이름은 바깥 Module 문맥에서 평가됩니다.

class Feature extends (await loadBase()) {
    [await loadName()]() { return 1; }
}

따라서 위 두 자리의 await는 허용합니다. 반면 일반 메서드의 매개변수·본문, 필드 초기값과 static 블록에는 await 표현식을 사용할 수 없습니다. 이 경계는 for await (... of ...)에도 동일하게 적용합니다.

await를 표현식으로 사용할 수 있는 자리와 별개로, Module 원문에서는 await를 변수·매개변수·레이블의 이름이나 식별자 참조로 사용할 수 없습니다. 이 예약어 규칙은 중첩된 일반 함수에도 적용됩니다. 속성 이름 object.await나 {await: 1}은 허용합니다.

8. Validate는 모듈 전체의 선언과 공개 이름을 함께 검사합니다.

이제 각 구문을 읽는 순서를 확인했으므로, 파싱 뒤에 Validate를 호출하는 이유를 살펴보겠습니다. import나 export 한 줄의 형태만으로는 모듈 전체의 이름 관계를 판단할 수 없습니다.

export {answer};
const answer = 42;

이 모듈은 유효합니다. export 줄 뒤에서 선언했더라도 answer는 이 모듈의 선언 이름입니다. Validate는 모듈의 선언을 먼저 모은 뒤, local export가 가리키는 이름이 그 목록에 있는지 확인합니다.

반대로 export {missing};만 있으면 현재 모듈에 선언하지 않은 이름을 공개한 오류입니다. export {missing} from './other.js';는 상대 모듈의 항목을 재내보내는 구문이므로, 현재 모듈의 선언 목록에 missing이 있어야 한다는 조건을 적용하지 않습니다.
