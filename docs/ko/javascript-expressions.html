JavaScript 표현식 하나를 파싱하고,
정적 문법 오류를 검사합니다.

JavaScriptExpressionGrammar는 JavaScript 표현식을 읽는 데 필요한 문법과 토큰 규칙을 준비합니다. 개발자는 이 문법으로 LALRParser를 만들고, 입력 문자열을 파싱한 뒤 Validate로 정적 문법 오류를 검사합니다.

예를 들어 a + b * c를 입력하면 파서는 곱셈이 덧셈보다 먼저 묶이는 구문 트리를 만듭니다. object?.value = 1을 입력하면, 파싱 후 검사가 선택적 체이닝 결과에 대입하려는 오류를 찾아냅니다.

문법 준비 → 입력 파싱 → 정적 오류 검사가 전체 사용 순서입니다. 먼저 어떤 입력을 받는지 확인한 다음, 이 세 단계를 C# 코드로 살펴보겠습니다.

1. 입력은 엄격 모드 Script 문맥의 표현식 하나입니다.

이 문법은 ECMAScript 2026, 제17판의 표현식 문법을 기준으로 구성했습니다. 입력 전체를 엄격 모드 Script 문맥의 표현식 하나로 읽습니다. 그 표현식 안에 일반·async·제너레이터 함수나 화살표 함수가 나오면 함수의 매개변수와 본문을, 클래스 표현식이 나오면 클래스의 멤버와 본문을 함께 파싱합니다.

문맥을 정하는 이유는 같은 단어도 사용 위치에 따라 의미가 달라지기 때문입니다. 표현식 최상위와 일반 함수 본문에서 await는 식별자로 사용할 수 있습니다. async 함수·async 화살표 본문에서는 await 표현식의 키워드로 읽습니다. 반면 yield와 let은 엄격 모드에서 예약된 단어이므로 식별자 참조로 사용할 수 없습니다. object.yield처럼 속성 이름으로 쓰는 경우에는 허용합니다.

입력 문자열에는 다음처럼 표현식 하나를 전달합니다. 여기서 대입식도 표현식에 해당합니다.

a + b * c
result = /ab/g.test(value)
object?.items[index] ?? fallback
({ name: value, ...other })
`안녕하세요, ${name}님!`
tag`값: ${value}`
({name = 'guest'}) => name

위 예제의 각 줄은 별도의 입력입니다. result = 1;처럼 세미콜론으로 끝나는 코드는 표현식 문장이므로, 이 클래스에는 세미콜론을 제외한 result = 1을 전달합니다. 선언과 문장을 여러 개 함께 입력하려면 JavaScriptScriptGrammar를 사용합니다.

2. 문법을 준비하고, 입력을 파싱한 뒤 검사합니다.

사용할 클래스의 네임스페이스는 Janglim.FrontEnd.Grammars.JavaScript입니다. 문법과 파서는 여러 입력에서 다시 사용할 수 있으므로, 먼저 두 객체를 준비합니다.

using System;
using Janglim.FrontEnd.Grammars.JavaScript;
using Janglim.FrontEnd.Parsers.LR;

var language = new JavaScriptExpressionGrammar();
var parser = new LALRParser(language.Grammar);

language.Grammar는 EBNF를 읽어 만든 문법 객체입니다. LALRParser는 이 객체로 파싱 테이블을 만듭니다. 다음으로, 입력 문자열을 읽을 source를 준비하고 파서에 전달합니다.

var input = "result = /ab/g.test(value)";
var source = language.CreateTokenSource(input);
var parsed = parser.Parsing(source);

CreateTokenSource는 입력 문자열과 JavaScript 토큰 규칙을 연결합니다. 파서가 다음 토큰을 요청할 때마다 source가 원문을 읽고 토큰 하나를 반환합니다. 개발자가 식별자·숫자·나눗셈·정규식 규칙을 호출마다 직접 등록할 필요는 없습니다.

파싱을 마쳤으면 먼저 parsed.Success를 확인합니다. 성공한 경우에는 구문 트리를 Validate에 전달해, 대입 대상과 예약어 사용 등의 정적 오류까지 검사합니다.

if (!parsed.Success)
{
    Console.WriteLine(parser.FiredException?.Message);
    return;
}

var diagnostics = language.Validate(parsed.ToParseTree);
if (diagnostics.Count > 0)
{
    foreach (var diagnostic in diagnostics)
    {
        Console.WriteLine(
            $"{diagnostic.Code}: {diagnostic.Message} " +
            $"(위치 {diagnostic.SourceOffset}, 길이 {diagnostic.Length})");
    }
    return;
}

// 구조와 정적 문법 검사를 모두 통과한 구문 트리입니다.
var tree = parsed.ToParseTree;
Console.WriteLine(tree.AllInputDatas);

입력을 올바른 JavaScript 표현식으로 받아들이려면, 파싱 성공과 Validate의 빈 진단 목록을 함께 확인해야 합니다. 다음 절에서는 두 검사가 나뉘는 이유를 설명합니다.

3. 파싱은 구조를 만들고, Validate는 그 구조의 사용 조건을 검사합니다.

다음 입력을 보겠습니다.

(a + b) = value

괄호식 뒤에 대입 연산자와 값이 있으므로, 파서는 이 입력을 대입식 모양의 구문 트리로 만들 수 있습니다. 하지만 a + b의 계산 결과는 값을 저장할 수 있는 대입 대상이 아닙니다. 따라서 Validate는 구문 트리에서 대입 연산자의 왼쪽을 살펴보고 오류를 반환합니다.

이처럼 입력을 실행하기 전에 확인할 수 있는 정적 문법 오류를 ECMAScript 명세에서는 early error라고 부릅니다. 이 클래스는 다음 오류를 구문 트리에서 확인합니다.

검사하는 조건오류 예제
대입·증감 대상과 연산자의 조합이 올바른가(a + b) = value, 1++, object?.value = 1. 배열·객체 패턴은 구조 분해 할당의 조건으로 검사합니다.
구조 분해의 대상·기본값·나머지 요소가 올바른가[...rest,] = values, ({...{name}} = user), 일반 객체 리터럴의 {name = 'guest'}
화살표 함수의 매개변수가 바인딩 조건을 지키는가([object.name]) => 0, (value, value) => value, (...rest,) => 0. 기본값·계산된 속성 이름 안의 식은 일반 표현식으로 검사합니다.
엄격 모드에서 허용하는 식별자 사용인가eval = value, arguments++, 예약어를 Unicode 이스케이프로 숨긴 식별자 참조
delete가 엄격 모드의 식별자 참조에 적용되었는가delete value. 속성 삭제인 delete object.value는 허용합니다.
같은 객체 리터럴에 __proto__ 설정이 중복되었는가{__proto__: a, __proto__: b}. 계산된 속성 이름과 축약 속성은 구분해서 검사합니다.
정규식 리터럴의 본문이 모드별 문법을 지키는가/[z-a]/u, /(a)\2/u. 그룹·범위·역참조와 v 집합의 검사 순서는 정규식 본문 설명에서 확인합니다.
태그 없는 템플릿에 잘못된 이스케이프가 있는가`\u{110000}`. 태그가 붙은 템플릿과 검사 결과가 달라지는 이유는 템플릿 이스케이프 검사에서 설명합니다.

진단 하나에는 Code, Message, SourceOffset, Length가 있습니다. 위치와 길이는 .NET 문자열과 같은 UTF-16 코드 단위로 계산합니다. 오류가 발생한 원문 범위는 input.Substring(SourceOffset, Length)로 가져올 수 있습니다.

토큰 자체가 잘못되었거나 표현식 구조가 맞지 않으면 파싱 단계에서 실패합니다. 반면 위 표처럼 만들어진 구조의 사용 조건에 해당하는 오류는 Validate가 반환합니다. 두 결과를 모두 확인하면, 토큰 인식부터 정적 문법 검사까지 이어서 처리할 수 있습니다.

이 검사는 표현식을 실행하지 않습니다. 예를 들어 1n + 1과 null.value는 실행 시 문제가 생길 수 있지만, 표현식의 구조와 이 문맥의 정적 문법 조건은 만족합니다.

4. 정책은 파싱 문맥에 맞춰 /를 읽을 규칙 묶음을 선택합니다.

지금까지의 사용 코드에는 규칙 묶음을 선택하는 코드가 보이지 않았습니다. JavaScriptExpressionGrammar가 그 설정을 Policy에 미리 준비하고, CreateTokenSource가 반환하는 입력 공급자에 연결하기 때문입니다.

먼저 /의 처리에 필요한 차이부터 보겠습니다. 식별자·숫자·문자열·기호 등의 공통 규칙에 나눗셈 /·대입 /= 규칙을 더하면 Div 계열의 묶음이 됩니다. 공통 규칙에 정규식 리터럴 규칙을 더하면 RegExp 계열의 묶음이 됩니다.

a / b

이 입력에서 파서가 식별자 a를 소비한 상태라고 하겠습니다. 파서는 현재 상태에서 받을 수 있는 토큰 종류와 입력 위치를 context에 담아 정책에 전달합니다. 정책은 그 문맥에서 나눗셈 토큰을 받을 수 있다는 사실을 확인하고 Div 계열의 묶음을 반환합니다. 그러면 파서는 반환된 묶음을 그대로 source.Peek(cursor, goal)에 전달하고, source는 원문의 /를 토큰 하나로 만듭니다.

이제 정규식으로 시작하는 입력을 보겠습니다.

/ab/g.test(value)

입력의 처음에는 표현식을 시작할 값이 필요합니다. 파서가 이 상태의 문맥을 전달하면 정책은 RegExp 계열의 묶음을 반환합니다. 파서는 앞의 예제와 같은 코드로 다음 토큰을 요청하고, 이번에는 source가 /ab/g 전체를 토큰 하나로 반환합니다. 파서는 그 토큰을 처리한 뒤 점·속성 이름·호출 인자를 계속 파싱합니다.

규칙 묶음을 선택하는 책임은 정책에 있습니다. 파서는 문맥을 전달하고, 정책이 반환한 묶음으로 source에 다음 토큰을 요청합니다. 따라서 파서에는 Div와 RegExp를 직접 구분하는 코드가 필요하지 않습니다. 이 호출 순서와 타입은 파서 주도 렉싱 문서에서 이어서 볼 수 있습니다.

source는 선택된 묶음 안에서 실제 입력을 가장 길게 읽는 토큰 규칙을 사용하고, 읽은 길이가 같으면 준비된 규칙 우선순위를 적용합니다. 정규식 앞뒤에 단어 경계 \b를 자동으로 추가하지 않으므로, $name과 name$도 식별자 규칙 그대로 읽습니다. 템플릿에서는 이 선택 과정에 중괄호의 역할을 구분하는 문맥이 하나 더 필요합니다.

5. 템플릿은 문자열 구간과 보간 표현식을 번갈아 읽습니다.

다음 템플릿에서 name은 문자열에 값을 끼워 넣기 위한 표현식입니다. ${와 } 사이에 있는 이런 표현식을 보간 표현식이라고 부릅니다.

`안녕하세요, ${name}님!`

source는 먼저 여는 백틱부터 ${까지를 TemplateHead 토큰으로 반환합니다. 파서는 그 토큰을 처리한 뒤 평소와 같은 표현식 문법으로 name을 파싱합니다. 이어서 source는 보간을 닫는 }부터 마지막 백틱까지를 TemplateTail 토큰으로 반환합니다.

TemplateHead    `안녕하세요, ${
IdentifierName  name
TemplateTail    }님!`

보간이 여러 개라면 }부터 다음 ${까지의 문자열 구간은 TemplateMiddle 토큰이 됩니다. 보간이 전혀 없는 `안녕하세요`는 전체가 NoSubstitutionTemplate 토큰 하나입니다. 각 경우 모두 문자열 구간에는 공백·줄바꿈과 /* ... */처럼 보이는 글자도 그대로 포함됩니다.

보간 안의 객체를 닫는 }와 보간을 끝내는 }를 구분합니다.

앞의 예제에는 보간을 닫는 중괄호가 하나만 있었습니다. 하지만 보간 안에 객체를 넣으면 같은 }가 두 번 나오므로, 정책은 어느 중괄호부터 문자열 구간으로 읽어야 하는지 구분해야 합니다.

`결과: ${{value: a / b}.value}`

이 예제에서 ${ 바로 다음의 {는 객체 리터럴을 엽니다. 따라서 a / b 뒤의 첫 번째 }는 객체를 닫는 토큰입니다. 그 뒤의 .value까지 표현식에 포함되고, 마지막 }에서 보간 표현식이 끝납니다.

이 차이를 기억하기 위해 source는 다음 커서를 만들 때 현재 보간 안의 중괄호 깊이를 LexicalState에 기록합니다. TemplateHead를 읽으면 새 보간 문맥의 깊이를 0으로 시작하고, 표현식의 { 토큰을 읽으면 깊이를 늘리며, } 토큰을 읽으면 깊이를 줄입니다. 위 예제에서는 객체를 열 때 깊이가 1이 되고, 객체를 닫으면 다시 0이 됩니다.

정책은 파서가 전달한 커서의 이 정보를 확인합니다. 깊이가 남아 있으면 일반 } 토큰이 들어 있는 묶음을 반환하고, 깊이가 0인 보간 문맥이면 TemplateMiddle·TemplateTail 규칙이 들어 있는 묶음을 반환합니다. 이와 함께 앞 절의 Div·RegExp 구분도 적용하므로, JavaScript 정책이 보관하는 묶음은 다음 네 개입니다.

슬래시의 역할과 중괄호의 역할을 함께 구분하는 네 묶음
묶음의 구분슬래시 처리닫는 중괄호 처리
일반 + Div나눗셈 /·대입 /=일반 } 토큰
일반 + RegExp정규식 리터럴일반 } 토큰
템플릿 이어 읽기 + Div나눗셈 /·대입 /=TemplateMiddle 또는 TemplateTail
템플릿 이어 읽기 + RegExp정규식 리터럴TemplateMiddle 또는 TemplateTail

모든 묶음에는 식별자·숫자·문자열 등 공통 토큰 규칙도 들어 있습니다. 따라서 템플릿의 문자열 구간을 다시 읽을 수 있는 묶음을 선택했더라도, 다음 원문이 }가 아니라 식별자나 연산자라면 해당 토큰을 계속 읽습니다. 정책은 다음 문자를 미리 읽어 고르는 대신 현재 파싱 문맥과 커서에 기록된 보간 문맥을 사용합니다.

중첩 템플릿은 바깥 보간 문맥을 보관한 채 처리합니다.

`바깥: ${`안쪽: ${name}`}`

안쪽 템플릿의 TemplateHead를 읽으면 source는 다음 커서에 새 보간 문맥을 추가합니다. 안쪽 TemplateTail을 읽고 나면 그 문맥을 제거하고, 보관해 둔 바깥 보간 문맥으로 돌아갑니다. 따라서 두 템플릿의 중괄호 깊이가 섞이지 않습니다.

source가 반환하는 다음 커서에는 토큰을 소비한 뒤의 문맥이 들어 있고, 파서는 Shift할 때 그 커서를 현재 커서로 확정합니다. 예측 후보도 각자의 커서를 사용하므로, 한 후보가 읽은 중첩 템플릿이 다른 후보의 보간 문맥을 바꾸지 않습니다. 문자열·정규식 토큰 안에 있는 중괄호와 주석의 중괄호도 표현식의 중괄호 깊이에 영향을 주지 않습니다.

잘못된 이스케이프는 태그 유무를 확인한 뒤 검사합니다.

템플릿 앞에 함수를 나타내는 표현식을 붙이면 태그 템플릿이 됩니다. 다음 두 입력은 같은 이스케이프를 담고 있지만, 태그 유무 때문에 정적 검사 결과가 달라집니다.

`\u{110000}`      // 일반 템플릿: 잘못된 Unicode 이스케이프
tag`\u{110000}`   // 태그 템플릿: 이 원문 표기를 허용

ECMAScript는 태그 템플릿에서 함수가 잘못된 이스케이프의 원문도 다룰 수 있도록 이 표기를 허용합니다. 그래서 source는 두 경우 모두 템플릿 구간을 토큰으로 반환하고, Validate가 구문 트리에서 태그 유무를 확인합니다. 첫 번째 입력에는 invalid_template_escape 진단을 반환하고, 두 번째 입력에는 이 진단을 반환하지 않습니다.

이 허용 범위는 태그에 직접 연결된 템플릿의 문자열 구간입니다. 태그 템플릿의 보간 표현식 안에 일반 템플릿을 넣었다면, Validate는 그 일반 템플릿의 이스케이프를 다시 검사합니다. 따라서 태그 템플릿이 포함된 입력도 파싱 성공 뒤에 Validate를 호출해야 합니다.

템플릿 토큰의 Input에는 백틱·보간 경계·이스케이프·줄바꿈을 포함한 원문이 그대로 남습니다. 현재 언어 지원 계층은 이 원문과 구문 트리를 제공하며, 이스케이프를 해석한 문자열 값이나 태그 함수의 실행 결과를 계산하지 않습니다.

6. 배열·객체 구조를 사용하여 여러 대상에 값을 대입합니다.

지금까지 템플릿 안에서도 평소의 표현식 문법을 사용한다는 점을 살펴봤습니다. 이제 표현식 문법이 지원하는 대입 형태를 하나 더 보겠습니다. 구조 분해 할당은 배열의 요소나 객체의 속성을 꺼내 여러 대상에 대입하는 표현식입니다.

[first, second] = values

first와 second가 값을 저장할 변수라고 가정하겠습니다. 이 표현식은 values의 첫 번째 요소를 first에, 두 번째 요소를 second에 대입하라는 뜻입니다. 대입 연산자 왼쪽의 [first, second]가 각 값을 어디에 저장할지 나타내는 배열 패턴입니다.

객체에서는 위치 대신 속성 이름으로 값을 고릅니다. 다음 표현식은 user의 두 속성을 각각 변수에 대입합니다.

({name: displayName, age} = user)

name: displayName은 user.name의 값을 displayName에 저장하라는 뜻입니다. 이어서 나오는 age는 age: age를 짧게 쓴 형태이므로, user.age의 값을 같은 이름의 변수 age에 저장합니다. 이때 왼쪽의 {name: displayName, age}가 객체 패턴입니다.

패턴을 중첩하면 내부 배열이나 객체의 값도 꺼낼 수 있습니다.

({profile: {name}, scores: [first]} = user)

먼저 profile: {name}은 user.profile에 객체 패턴 {name}을 적용합니다. 따라서 그 객체의 name 속성을 변수 name에 대입합니다. 다음으로 scores: [first]는 user.scores에 배열 패턴 [first]를 적용하여 첫 번째 요소를 변수 first에 대입합니다.

대입할 값이 undefined라면 기본값을 사용합니다.

({name = 'guest'} = user)

이 표현식은 user.name을 변수 name에 대입하되, 그 값이 undefined이면 문자열 'guest'를 대신 사용하라는 뜻입니다. 배열에서도 [first = 0] = values처럼 기본값을 지정할 수 있습니다.

중첩 패턴 전체에 기본값을 줄 수도 있습니다. 예를 들어 다음 표현식은 user.profile이 undefined일 때 빈 객체를 사용한 뒤, 그 객체의 name 속성을 꺼냅니다.

({profile: {name} = {}} = user)

나머지 요소와 속성은 마지막 대상에 모읍니다.

[first, ...remaining] = values
({name, ...other} = user)

첫 번째 표현식의 ...remaining은 첫 요소를 제외한 나머지 요소를 배열로 모아 변수 remaining에 대입합니다. 두 번째 표현식의 ...other는 name을 제외하고 남은 속성을 새 객체로 모아 변수 other에 대입합니다.

이처럼 남은 값을 모두 받는 대상을 rest 대상이라고 부릅니다. rest 대상은 패턴의 마지막에 와야 하며, 뒤에 쉼표나 rest 자체의 기본값을 붙일 수 없습니다. 다음 표는 이 제한을 적용한 예제입니다.

입력검사 결과와 이유
[first, ...remaining] = values허용. rest 대상이 마지막에 있습니다.
[...remaining, last] = values오류. rest 대상 뒤에 다른 요소가 있습니다.
[...remaining,] = values오류. rest 대상 뒤에 쉼표가 있습니다.
[...remaining = fallback] = values오류. rest 대상 자체에 기본값을 지정했습니다.

rest 대상에 패턴을 다시 사용할 수 있는지는 배열과 객체에서 다릅니다. 배열 rest는 모은 배열에 중첩 패턴을 적용할 수 있습니다. 따라서 [...[first]] = values는 허용합니다. 반면 객체 rest는 식별자나 대입 가능한 속성을 대상으로 받으므로 ({...other} = user)와 ({...target.other} = user)는 허용하지만, ({...{name}} = user)와 ({...[]} = user)는 오류입니다.

구조 분해 패턴은 = 대입의 왼쪽에서 사용합니다.

지금까지의 예제는 모두 일반 대입 연산자 =를 사용했습니다. [first] += values처럼 복합 대입에 배열 패턴을 붙이거나, [first]++처럼 패턴에 증감 연산자를 적용하면 정적 문법 오류가 됩니다.

각 값을 저장할 대상도 확인해야 합니다. [target.name] = values처럼 대입 가능한 속성은 허용하지만, [1] = values나 [target?.name] = values는 허용하지 않습니다. 엄격 모드의 eval·arguments 대입 제한도 각 대상에 적용합니다.

괄호를 사용할 때는 괄호가 감싼 범위를 구분합니다. 다음 첫 번째 입력은 대입식 전체를 괄호로 감쌌습니다. 두 번째 입력은 변수 하나만 괄호로 감쌌습니다. 두 입력은 모두 허용하지만, 세 번째처럼 대입 대상인 패턴 자체를 괄호로 감싸면 오류입니다.

([first] = values)     // 허용: 대입식 전체를 감싼 괄호
[(first)] = values     // 허용: 변수 하나를 감싼 괄호
([first]) = values     // 오류: 배열 패턴 자체를 감싼 괄호

공통 구문을 먼저 파싱하고, Validate가 패턴의 사용 조건을 검사합니다.

이제 사용 코드에서 Validate를 호출하는 이유를 구조 분해 예제로 보겠습니다. 다음 두 입력은 같은 {name = 'guest'} 구문을 포함합니다.

({name = 'guest'} = user)   // 구조 분해의 기본값: 허용
({name = 'guest'})          // 객체 리터럴의 속성 표기: 오류

첫 번째 입력의 중괄호는 값을 저장할 대상을 나타내는 객체 패턴입니다. 반면 두 번째 입력의 중괄호는 새 객체를 만드는 객체 리터럴입니다. 객체 리터럴에서 이름과 값을 지정하려면 {name: 'guest'}처럼 콜론을 사용해야 합니다.

파서가 객체 구문을 읽는 동안에는 뒤에 대입 연산자 =가 이어질 수 있습니다. 그래서 EBNF는 두 경우를 공통 구문으로 받아들이며, name = 'guest' 형태에는 CoverInitializedName이라는 생성 규칙을 사용합니다. 이후 Validate는 완성된 구문 트리를 보고, 그 객체가 실제 대입 패턴이면 기본값으로 검사하고 일반 객체 리터럴이면 오류를 반환합니다.

따라서 구조 분해 입력도 파싱 성공 뒤에 Validate를 호출해야 합니다. JavaScriptAssignmentPatterns는 이 검사에서 실제 패턴으로 쓰인 배열·객체와 기본값 위치를 구분합니다. 반환된 구문 트리는 ArrayLiteral·ObjectLiteral 노드와 원문을 그대로 보존하며, 검사는 트리를 바꾸지 않습니다.

기본값·계산된 키·속성 대상의 기반 표현식은 평소대로 검사합니다.

패턴을 사용한다고 해서 그 안의 모든 객체가 패턴이 되는 것은 아닙니다. 예를 들어 다음 입력에서 왼쪽 {name = ...}은 패턴이지만, 기본값으로 쓰인 오른쪽 {key = 1}은 값을 만드는 일반 표현식입니다.

({name = {key = 1}} = user)

따라서 이 입력은 일반 객체 리터럴의 잘못된 속성 표기 때문에 오류가 됩니다. 기본값을 {key: 1}로 쓰면 이 오류를 해결할 수 있습니다.

계산된 속성 이름과 속성 접근의 기반도 값을 계산하는 표현식입니다. 예를 들어 ({[key()]: target} = user)의 key()는 꺼낼 속성의 이름을 계산하고, [getTarget().name] = values의 getTarget()은 대입할 속성을 가진 객체를 구합니다. 두 위치에도 일반 표현식 검사를 계속 적용합니다.

중복 __proto__ 검사도 이 경계를 따릅니다. ({__proto__: a, __proto__: b} = user)는 두 속성을 각각 대입할 패턴이므로 허용합니다. 반면 기본값이나 속성 접근의 기반에서 실제 객체 리터럴을 만들면, 그 객체에는 기존의 중복 __proto__ 제한을 적용합니다.

여기까지가 표현식에서 값을 대입하는 구조 분해입니다. 변수 선언과 함수 매개변수에서 새 이름을 만드는 구조 분해는 별도의 바인딩 패턴을 사용합니다. 두 패턴의 차이와 사용 예제는 선언·매개변수의 구조 분해 문서에서 이어서 설명합니다.

7. 표현식 구조는 EBNF에, 문자 범위는 토큰 규칙에 둡니다.

앞에서 살펴본 표현식·템플릿·구조 분해의 공통 구문은 기준 문법 파일 grammars/javascript/ecmascript-2026-expressions.ebnf에 들어 있습니다. 이 파일은 생성 규칙을 사용해 표현식의 구조와 연산자 우선순위를 정합니다. 예를 들어 덧셈과 뺄셈의 구조는 다음과 같습니다.

AdditiveExpression
    : MultiplicativeExpression
    | AdditiveExpression AdditiveOperator MultiplicativeExpression ;

AdditiveOperator : '+' | '-' ;

덧셈식이 곱셈식을 하위 규칙으로 사용하므로 곱셈을 먼저 묶습니다. 같은 덧셈식이 생성 규칙의 왼쪽에 다시 나오므로, 연속된 덧셈과 뺄셈은 왼쪽부터 묶습니다. 이런 구조적 관계는 EBNF 파일에서 확인하고 수정할 수 있습니다.

식별자의 Unicode 문자 범위처럼 긴 토큰 정규식은 JavaScriptTokenPatterns가 준비합니다. 템플릿 구간의 정규식과 보간 문맥 처리는 JavaScriptTemplateTokens가 담당합니다. 기준 EBNF에는 다음처럼 토큰 정규식이 들어갈 위치를 표시합니다.

IdentifierName := Identifier "{{IdentifierName}}" ;

JavaScriptExpressionGrammar 생성자는 표현식 EBNF에 ecmascript-2026-bindings.ebnf·ecmascript-2026-statements.ebnf·ecmascript-2026-classes.ebnf·ecmascript-2026-modules.ebnf·ecmascript-2026-functions.ebnf를 연결합니다. 이어서 JavaScriptFunctionGrammar로 Await 문맥별 규칙을 연결하고, 위 표시를 실제 정규식으로 바꾼 뒤 EbnfGrammarReader에 전달합니다. 함수·클래스의 본문과 동적 import까지 같은 언어 문법으로 읽기 위해 이 파일들을 함께 준비합니다. language.GrammarText로 치환을 마친 EBNF 전체를 확인할 수 있습니다.
