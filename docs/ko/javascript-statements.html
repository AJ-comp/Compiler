함수와 문장으로 구성된 Script를 파싱하고,
선언과 제어문의 사용 조건을 검사합니다.

JavaScriptScriptGrammar는 JavaScript 코드에서 일반 함수와 화살표 함수, 변수 선언, 조건문과 반복문 등을 읽는 데 필요한 문법과 토큰 규칙을 준비합니다. 개발자는 이 문법으로 파서를 만들고, 코드 전체를 파싱한 뒤 Validate로 정적 문법 오류를 검사합니다.

예를 들어 함수 매개변수의 {name}, 함수 본문의 return name;, 함수 밖의 const result = read(user);를 하나의 구문 트리로 만들 수 있습니다. 같은 함수에서 매개변수 이름을 두 번 선언하거나, 함수 밖에서 return을 사용하면 정적 검사가 그 오류를 알려줍니다.

표현식 하나에는 JavaScriptExpressionGrammar를, 선언과 문장 목록에는 JavaScriptScriptGrammar를 사용합니다. 두 클래스는 같은 JavaScript 토큰 규칙과 표현식 문법을 공유합니다. 아래에서는 Script를 입력하는 방법부터 살펴본 뒤, 선언·함수·문장 처리의 차이를 차례로 설명합니다.

1. 입력은 엄격 모드의 Script입니다.

이 문법은 ECMAScript 2026, 제17판을 기준으로 합니다. 입력 전체에 엄격 모드의 구문 조건을 적용하므로, 입력에 "use strict";를 따로 적지 않아도 선언 이름과 대입 대상 등을 엄격 모드 기준으로 검사합니다.

입력 문자열에는 다음처럼 여러 선언과 문장을 함께 전달합니다. 함수 본문도 같은 입력 안에서 파싱합니다.

function display({name = 'guest'}, [first, ...rest]) {
    if (first > 0) {
        return `${name}: ${rest.length}`;
    }
    return name;
}

const result = display(user, values);
result;

함수는 function으로 정의하는 일반 함수와, value => value + 1처럼 정의하는 화살표 함수를 사용할 수 있습니다. 일반 함수의 본문과 화살표 함수의 블록 본문 안에는 선언과 문장 목록이 들어갑니다. 화살표 함수의 본문을 표현식 하나로 쓰는 형태도 함께 지원합니다.

2. 문법을 준비하고, 코드를 파싱한 뒤 검사합니다.

먼저 Janglim.FrontEnd.Grammars.JavaScript 네임스페이스의 JavaScriptScriptGrammar를 만듭니다. 그리고 Grammar를 LALRParser에 전달해 파싱 테이블을 준비합니다.

using System;
using Janglim.FrontEnd.Grammars.JavaScript;
using Janglim.FrontEnd.Parsers.LR;

var language = new JavaScriptScriptGrammar();
var parser = new LALRParser(language.Grammar);

이제 입력 문자열을 정합니다. 아래 코드는 user에서 이름을 꺼내 반환하는 함수와, 그 함수를 호출하는 선언으로 구성되어 있습니다.

var input = @"
function read({name = 'guest'}) {
    return name;
}
const result = read(user);
";

var source = language.CreateTokenSource(input);
var parsed = parser.Parsing(source);

CreateTokenSource는 원문과 JavaScript 토큰 규칙을 연결한 입력 공급자 source를 만듭니다. 파서는 이 공급자에 다음 토큰을 요청하면서 원문을 파싱합니다. 문법 객체와 파서는 여러 입력에서 다시 사용할 수 있고, 입력마다 새로운 source를 만듭니다.

파싱 결과가 성공이면 구문 트리를 Validate에 전달합니다. 이 검사는 선언 이름의 중복, 함수 밖의 return, 잘못된 구조 분해 대상처럼 구문 트리에서 확인할 수 있는 오류를 반환합니다.

if (!parsed.Success)
{
    Console.WriteLine(parser.FiredException?.Message);
    return;
}

var diagnostics = language.Validate(parsed.ToParseTree);
if (diagnostics.Count > 0)
{
    foreach (var diagnostic in diagnostics)
        Console.WriteLine($"{diagnostic.Code}: {diagnostic.Message} " +
            $"(위치 {diagnostic.SourceOffset}, 길이 {diagnostic.Length})");
    return;
}

var tree = parsed.ToParseTree;
Console.WriteLine(tree.AllInputDatas);

파싱 성공과 Validate의 빈 진단 목록을 함께 확인해야 합니다. 진단의 위치와 길이는 .NET 문자열의 UTF-16 코드 단위입니다. 오류가 가리키는 원문은 input.Substring(diagnostic.SourceOffset, diagnostic.Length)로 확인할 수 있습니다.

공개 API는 두 입력 클래스가 같습니다. Grammar는 파서에 전달할 문법, Policy는 토큰 규칙 묶음을 선택하는 정책, GrammarText는 토큰 정규식 치환을 마친 EBNF입니다. 입력 단위에 맞는 클래스를 고른 뒤 CreateTokenSource → Parsing → Validate 순서로 사용합니다.

3. 선언·매개변수의 구조 분해는 새 이름을 만듭니다.

먼저 변수 선언부터 보겠습니다. 아래 선언은 user.name의 값을 새 변수 displayName에 연결합니다.

const {name: displayName} = user;

이처럼 선언에서 새 이름을 만드는 패턴을 바인딩 패턴이라고 부릅니다. 배열 패턴, 중첩 패턴, 기본값과 rest도 같은 선언 안에서 사용할 수 있습니다.

let [first, second = 0, ...remaining] = values;
const {profile: {name}, scores: [score]} = user;
const {name = 'guest', ...other} = user;

첫 번째 선언은 first·second·remaining을 만듭니다. 두 번째 선언은 중첩된 객체와 배열에서 name·score를 만듭니다. 세 번째 선언은 name에 사용할 기본값을 정하고, 남은 속성을 새 변수 other에 연결합니다.

함수 매개변수에서도 같은 바인딩 패턴을 사용합니다. 다음 함수의 name과 rest는 함수 안에서 사용할 매개변수 이름입니다.

function read({name = 'guest'}, ...rest) {
    return name;
}

새 이름을 만드는 선언과, 기존 대상에 값을 넣는 할당은 검사 조건이 다릅니다.

기존 구조 분해 할당은 객체의 속성을 대입 대상으로 사용할 수 있습니다. 예를 들어 아래 첫 줄은 user.name을 이미 존재하는 target.name 속성에 대입합니다. 반면 변수 선언은 새 이름이 필요하므로 두 번째 줄의 target.name을 바인딩 이름으로 받을 수 없습니다.

({name: target.name} = user);        // 허용: 기존 속성에 대입
const {name: target.name} = user;    // 오류: 속성 접근은 새 변수 이름이 아님

이 차이를 지키기 위해 EBNF는 선언과 일반 함수 매개변수에 BindingIdentifier와 BindingPattern 전용 규칙을 사용합니다. 화살표 함수의 괄호 안은 일반 괄호식과 시작 모양이 같으므로, 공통 모양으로 읽은 뒤 같은 바인딩 조건을 검사합니다. 이 처리 순서는 아래 화살표 함수 절에서 설명합니다.

나머지 요소는 마지막에 오며, 바인딩 대상에도 제한이 있습니다.

배열과 함수 매개변수의 rest에는 식별자 또는 중첩 바인딩 패턴을 사용할 수 있습니다. 객체의 rest에는 새 이름을 만드는 식별자 하나를 사용합니다. 어느 경우든 rest 뒤에 요소·쉼표·rest 자체의 기본값을 추가할 수 없습니다.

const [...[first, second]] = values;   // 허용: 배열 rest의 중첩 패턴
function read(...[first, second]) {}   // 허용: 매개변수 rest의 중첩 패턴
const {name, ...other} = user;         // 허용: 객체 rest의 식별자

const {...{name}} = user;              // 오류: 객체 rest에 중첩 패턴
const [...rest,] = values;             // 오류: rest 뒤의 쉼표
function read(...rest = []) {}        // 오류: rest 자체의 기본값

이 기본값과 계산된 속성 이름 안에는 여전히 일반 표현식이 들어갑니다. 예를 들어 const {[key]: name = fallback()} = user;에서 바인딩 이름은 name입니다. key와 fallback()은 표현식이므로 바인딩 이름 목록에 포함하지 않고, 기존 표현식 검사로 따로 확인합니다.

4. 일반 함수는 매개변수와 본문을 함께 파싱합니다.

앞에서는 함수 매개변수의 패턴을 살펴봤습니다. 이제 함수 전체를 보겠습니다. 함수 선언에는 이름, 매개변수 목록, 중괄호로 감싼 본문이 순서대로 나옵니다.

function sum(first, second = 0) {
    const result = first + second;
    return result;
}

first와 second는 매개변수이고, 본문은 const 선언과 return 문장으로 구성되어 있습니다. 함수 안에서 return result;를 사용하면 값을 반환하는 문장으로 파싱합니다. 반환할 표현식 없이 return;으로 끝낼 수도 있습니다.

함수를 값으로 사용할 때는 함수 표현식을 씁니다. 아래 입력에서는 이름 없는 함수 표현식을 sum에 대입합니다. 함수 표현식은 JavaScriptExpressionGrammar에 표현식 하나로 전달할 때도 사용할 수 있습니다.

const sum = function (first, second) {
    return first + second;
};

함수 본문은 독립적인 제어 문맥입니다. 따라서 바깥에 반복문이 있어도, 그 안에 정의한 함수가 바깥 반복문으로 break하거나 continue할 수는 없습니다. 이 함수 경계는 파싱 후 정적 검사에서 확인합니다. 같은 경계를 갖는 화살표 함수는 매개변수와 본문을 다른 표기로 연결합니다.

5. 화살표 함수는 매개변수와 본문을 =>로 연결합니다.

먼저 value => value + 1을 보겠습니다. => 앞의 value는 매개변수 이름이고, 뒤의 value + 1은 반환할 값을 나타내는 표현식입니다. 이런 함수 표현식을 변수에 대입하거나 다른 함수의 인자로 사용할 수 있습니다.

const increment = value => value + 1;
values.map(value => value + 1);

매개변수가 식별자 하나이면 괄호를 생략할 수 있습니다. 매개변수가 여러 개이거나 하나도 없으면 괄호로 매개변수 목록을 표시합니다. 아래 각 선언은 이 세 형태를 보여 줍니다.

const one = value => value;
const pair = (first, second) => first + second;
const empty = () => 0;

표현식 입력 API에도 (first, second) => first + second처럼 화살표 함수 하나를 전달할 수 있습니다. 여러 선언과 함께 입력할 때는 위 예제처럼 Script API를 사용합니다.

본문이 표현식이면 그 결과를 반환하고, 블록이면 문장들을 읽습니다.

지금까지의 본문은 표현식 하나였습니다. 본문을 중괄호로 감싸면 그 안에는 선언과 문장이 들어갑니다. 이 블록 본문에서 값을 반환할 때는 return 문장을 적습니다.

const expression = value => value + 1;

const block = value => {
    const result = value + 1;
    return result;
};

이 구분 때문에 객체를 바로 반환할 때는 객체 리터럴을 괄호로 감쌉니다. => 바로 뒤의 {는 블록 본문을 시작하기 때문입니다.

const makeObject = value => ({name: value});
const emptyBlock = value => {};

첫 번째 함수의 본문은 괄호 안의 객체 표현식이고, 두 번째 함수의 본문은 비어 있는 블록입니다. 문법은 ArrowExpressionBody 조건으로 이 두 시작 위치를 구분합니다.

기본값·구조 분해·rest도 매개변수로 사용할 수 있습니다.

이제 매개변수 목록을 살펴보겠습니다. 기본값이나 구조 분해, rest를 사용하면 목록 전체를 괄호로 감쌉니다. 각각의 대상에는 새 이름을 만드는 바인딩 조건을 적용합니다.

const withDefault = (value = 0) => value;
const pick = ({name = 'guest'}, [first, ...rest]) => name;
const collect = (first, ...remaining) => remaining;
const nestedRest = (...[first, second]) => first;

따라서 ([target.name]) => 0은 새 이름 대신 속성 접근을 매개변수로 사용한 오류입니다. rest는 마지막에 와야 하며, (...rest,)처럼 뒤에 쉼표를 붙이거나 (...rest = [])처럼 rest 자체에 기본값을 줄 수 없습니다. 객체 패턴 안의 rest는 ({...remaining}) => remaining처럼 식별자 하나를 사용합니다.

파서가 (value)까지 읽었을 때에는 일반 괄호식인지, 뒤에 =>가 붙을 매개변수 목록인지 아직 정해지지 않았습니다. 그래서 EBNF는 공통 모양을 먼저 읽고, JavaScriptArrowFunctions가 실제 화살표 헤드를 바인딩 목록으로 검사합니다. 빈 괄호 ()나 뒤쪽 쉼표가 있는 (value,)는 이 헤드에서 허용하지만, 일반 괄호식으로 사용하면 오류를 반환합니다.

바인딩으로 해석하는 범위는 실제 매개변수 패턴입니다. 기본값과 계산된 속성 이름 안의 식은 일반 표현식으로 계속 검사합니다. 예를 들어 ({name = {key = 1}}) => name은 기본값의 일반 객체 리터럴에 잘못된 축약 초기값을 적었으므로 오류입니다. 검사는 이런 경계를 구분하면서 원래 구문 트리와 원문을 보존합니다.

매개변수 이름과 함수 본문의 선언을 함께 검사합니다.

같은 화살표 함수에서는 매개변수 이름이 중복될 수 없습니다. 구조 분해 안에서 만든 이름도 이 목록에 포함합니다. 또한 매개변수 이름과 같은 함수 본문에 직접 선언한 let·const 이름이 겹치면 오류입니다.

(value, value) => value;          // 오류: 중복 매개변수
([value], {name: value}) => 0;     // 오류: 패턴에서 만든 이름도 중복
value => { let value; };           // 오류: 같은 함수 본문의 선언
value => { { let value; } };       // 허용: 안쪽 블록의 별도 선언

기본값·구조 분해·rest가 있는 매개변수와 함수 자신의 use strict 지시문을 함께 쓰는 형태도 금지합니다. 따라서 (value = 0) => { 'use strict'; }는 오류입니다. 이 API는 입력 전체에 엄격 모드 조건을 적용하므로, 이런 함수에는 그 지시문을 추가하지 않고 매개변수를 사용하면 됩니다.

화살표 함수의 블록 본문 안에서는 return을 사용할 수 있습니다. 반면 함수 바깥의 반복문이나 레이블은 그 본문의 break·continue 목적지가 될 수 없습니다. 이름과 제어문의 범위 검사는 일반 함수와 같은 함수 경계에서 다시 시작합니다.

매개변수와 => 사이에는 줄바꿈을 넣을 수 없습니다.

줄바꿈 제약이 적용되는 구간은 매개변수 목록의 끝과 => 사이입니다. =>를 읽은 뒤 본문을 다음 줄에 적는 형태는 허용합니다.

const allowed = (value) =>
    value + 1;

const rejected = (value)
    => value + 1;                 // 오류: => 앞의 줄바꿈

이 구간의 주석에 줄바꿈이 포함된 경우에도 같은 제약을 적용합니다. 기존 토큰의 HasLineBreakBefore 정보와 NoLineTerminator 조건으로 확인합니다.

화살표 함수의 블록이 끝난 뒤에는 호출 인자를 바로 붙이지 않습니다.

본문의 중괄호가 닫히면 화살표 함수 표현식 하나가 완성됩니다. 다음 예제에서는 뒤의 (other)를 그 함수의 호출 인자로 붙일 수 없으므로, 줄바꿈에서 선언을 끝내고 별도의 괄호식 문장으로 읽습니다.

const transform = value => {}
(other);

반면 화살표 함수 전체를 괄호로 감싸면, 괄호식 뒤에 인자를 붙이는 함수 호출로 사용할 수 있습니다.

(value => {})(other);

이제 블록 대신 표현식 본문을 사용하는 경우를 보겠습니다. 아래 선언의 (other)는 본문의 read에 붙는 호출 인자이므로, 줄바꿈을 지나 read(other)까지 이어 읽습니다.

const invoke = value => read
(other);

따라서 줄바꿈만 보고 두 선언을 똑같이 끊을 수는 없습니다. JavaScript 전용 문맥 추적기는 블록 본문의 끝을 기록합니다. 문장 종료 조건은 이 정보를 사용해 앞의 transform 선언을 끝내고, 표현식 본문을 가진 invoke 선언에서는 호출을 계속 읽습니다. 이 종료 처리의 공통 원리는 아래 줄바꿈과 세미콜론 절에서 설명합니다.

6. 함수 안팎에서 조건·반복·예외 문장을 연결합니다.

함수 본문에서 사용한 선언과 반환문에 이어, 실행 순서를 나타내는 문장도 함께 파싱할 수 있습니다. 먼저 조건문과 반복문을 보겠습니다.

for (const {name} of users) {
    if (name === '') {
        continue;
    }
    display(name);
}

for/of의 선언 패턴은 반복마다 받은 값에서 name을 바인딩하는 구문입니다. 이 구문에서는 값이 반복 구문에서 공급되므로 const {name} = ... 형태의 초기값을 별도로 적지 않습니다. 본문의 continue는 현재 반복을 끝내고 다음 반복으로 넘어가는 문장으로 파싱합니다.

기존 변수나 속성에 값을 대입하는 for/in·for/of도 사용할 수 있습니다. 이때 선언 키워드가 없으면 왼쪽 부분에 바인딩 패턴이 아닌 할당 대상 검사를 적용합니다.

for ([first, second] of pairs) {
    display(first, second);
}

for (target.name in object) {
    display(target.name);
}

다음으로 예외 처리 문장을 보겠습니다. try와 finally의 본문은 블록이고, catch의 매개변수에는 식별자 또는 바인딩 패턴을 사용할 수 있습니다.

try {
    process(value);
} catch ({message}) {
    display(message);
} finally {
    finish();
}

여기서 message는 catch 블록 안에서 사용하는 바인딩 이름입니다. catch 매개변수를 생략한 catch { ... }도 지원합니다. 조건문·반복문·예외 처리의 각 본문을 읽은 뒤에는 다음 문장으로 이어지며, 그 경계를 세미콜론이나 JavaScript의 자동 세미콜론 조건으로 판단합니다.

7. 줄바꿈은 문장이 끝나는 조건 중 하나입니다.

JavaScript의 자동 세미콜론 처리, 즉 ASI는 세미콜론을 생략한 입력에서 문장 경계를 정하는 규칙입니다. 다만 줄이 바뀌었다는 이유만으로 모든 문장을 끝내지는 않습니다. 다음 토큰이 앞의 표현식을 이어 갈 수 있는지, 줄바꿈을 금지한 구문인지도 함께 확인해야 합니다.

호출로 이어지는 괄호 앞에서는 표현식이 계속됩니다.

a
(b)

첫 줄의 a 뒤에 호출 인자 (b)가 올 수 있으므로, 이 입력은 a(b)라는 표현식 문장 하나로 파싱합니다. 두 문장을 의도했다면 a;처럼 세미콜론으로 첫 문장을 끝내야 합니다.

return 바로 뒤의 줄바꿈은 반환문을 끝냅니다.

function read() {
    return
    value;
}

return과 반환할 표현식 사이에는 줄바꿈을 허용하지 않습니다. 따라서 이 함수 본문은 return;과 value;라는 두 문장으로 파싱합니다. value를 반환하려면 return value;처럼 같은 줄에서 표현식을 시작해야 합니다.

throw도 뒤의 표현식 앞에 줄바꿈을 허용하지 않습니다. 하지만 throw에는 표현식 없는 형태가 없으므로, throw 다음 줄에 error;를 적으면 문법 오류입니다.

줄바꿈 뒤의 ++는 앞 토큰의 후위 증감이 되지 않습니다.

value
++other;

이 입력에서는 value와 ++ 사이에 줄바꿈이 있습니다. 따라서 value++로 묶지 않고, value;와 전위 증감 표현식 ++other;라는 두 문장으로 파싱합니다. 주석 안에 줄바꿈이 있어도 같은 줄바꿈 조건을 적용합니다.

일반 for 헤더의 세미콜론 두 개는 직접 적습니다.

for (
    let index = 0;
    index < 3;
    index++
) {
    step(index);
}

일반 for 헤더의 세 구간은 세미콜론 두 개로 구분합니다. 이 두 세미콜론은 문장 끝을 보완하는 ASI 대상이 아니므로, 줄을 나누어 적어도 직접 넣어야 합니다.

장림은 언어 문법의 종료 조건으로 이 경계를 판단합니다.

이 처리는 JavaScript EBNF의 ExpressionEnd·BindingEnd·RestrictedEnd 등의 규칙과, C#에 등록한 검사 함수가 함께 담당합니다. 예를 들어 ExpressionEnd는 다음 토큰이 현재 표현식을 이어 가는지 확인하고, RestrictedEnd는 return 등의 줄바꿈 경계를 확인합니다.

기존 엔진의 토큰 경계 정보와 프레디케이트를 사용해 문장을 끝낼 수 있는지 검사합니다. 원문에 없던 세미콜론 토큰을 공통 엔진에 끼워 넣는 방식은 사용하지 않습니다. 따라서 원래 토큰과 원문 위치를 그대로 유지하면서 JavaScript의 문장 경계를 구문 트리에 반영합니다.

8. Validate는 이름이 속한 범위와 제어문의 목적지를 검사합니다.

지금까지는 각 구문을 어떻게 읽는지 살펴봤습니다. 읽은 구조를 올바르게 사용했는지 확인하는 단계는 Validate입니다. 먼저 선언 이름의 범위를 보겠습니다.

같은 이름이어도 같은 범위에 선언했는지에 따라 결과가 달라집니다.

function read(name) {
    let name;                 // 오류: 매개변수와 같은 함수 본문의 선언
}

function read(name) {
    { let name; }             // 허용: 안쪽 블록의 별도 선언
}

첫 번째 함수는 매개변수 name과 함수 본문의 let name이 충돌합니다. 두 번째 함수의 let name은 안쪽 블록에 속하므로, 바깥 매개변수와 이름이 같아도 별도의 바인딩으로 허용합니다.

var는 안쪽 블록에 적어도 둘러싼 함수나 Script의 변수 범위에 속합니다. 따라서 let name; { var name; }은 충돌하고, var name; { let name; }은 안쪽 블록의 별도 선언으로 허용합니다. 중첩 함수 안의 선언은 다시 그 함수의 범위에 속하므로 바깥 선언과 분리해서 검사합니다.

이름·초기값·함수 문맥에서 확인하는 주요 조건
검사오류 예제와 이유
엄격 모드 바인딩 이름let eval;, function read(arguments) {}는 이 문맥에서 사용할 수 없는 바인딩 이름입니다.
중복 이름let [name, name] = values;와 function read(name, name) {}은 같은 이름을 중복 바인딩합니다. var의 중복 선언은 구분해서 허용합니다.
const 초기값const value;에는 초기값이 필요합니다. 반복 값으로 바인딩하는 for (const value of values)는 별도 구문입니다.
매개변수와 지시문function read(value = 0) { 'use strict'; }는 기본값·구조 분해·rest가 있는 매개변수와 함수 자신의 use strict 지시문을 함께 사용한 오류입니다.
catch·for 이름 충돌catch ({message}) { var message; }처럼 매개변수와 본문 선언이 충돌하는 경우를 검사합니다. for의 lexical 바인딩과 본문의 var 선언도 확인합니다.

기본값·구조 분해·rest가 있는 매개변수와 함수 자신의 use strict 지시문 조합은 ECMAScript가 금지하는 형태입니다. 이 API는 입력 전체를 엄격 모드로 검사하므로, 이런 함수의 본문에는 지시문을 추가하지 않고 매개변수를 그대로 사용하면 됩니다.

지시문 검사는 함수 본문의 맨 앞 문자열 문장들에만 적용합니다. 따라서 ('use strict'); 같은 괄호식, 다른 블록 안의 문자열, 일반 문장 뒤에 나오는 문자열은 함수의 use strict 지시문으로 처리하지 않습니다.

break와 continue의 목적지는 같은 함수 안에 있어야 합니다.

outer: for (const value of values) {
    if (value === 0) continue outer;
    if (value < 0) break outer;
}

outer는 반복문에 붙인 레이블입니다. continue outer는 그 반복문의 다음 반복으로, break outer는 그 레이블이 붙은 문장의 바깥으로 이동하는 구문입니다. 정적 검사는 이 레이블이 현재 함수에서 활성 상태인지 확인합니다.

레이블 없는 continue는 반복문 안에서, 레이블 없는 break는 반복문이나 switch 안에서 사용할 수 있습니다. 레이블이 있는 continue의 목적지는 반복문이어야 합니다. 함수 밖의 return, 중복 활성 레이블, switch의 중복 default도 이 단계에서 검사합니다.

이 검사는 JavaScript 코드를 실행하지 않습니다. 변수의 실제 값이나 함수 호출 결과를 계산하는 대신, 구문 트리에서 선언 범위와 제어문이 연결된 위치를 확인합니다. 기존 표현식의 대입 대상·템플릿 이스케이프·객체 정적 오류 검사도 함께 적용합니다.

9. 정책은 문장 문맥까지 살펴 /를 읽을 규칙 묶음을 선택합니다.

문장을 추가하면 닫는 괄호의 역할도 중요해집니다. 같은 ) 뒤라도 함수 호출이 끝난 자리인지, if 조건이 끝난 자리인지에 따라 다음 슬래시를 읽는 방식이 달라집니다.

call(value) / divisor;

if (ready) /ab/.test(text);

첫 번째 문장의 call(value)는 값을 만드는 호출 표현식입니다. 그 뒤의 /는 나눗셈 연산자로 읽습니다. 두 번째 문장에서는 if 조건의 괄호가 닫힌 뒤 본문 문장이 시작됩니다. 이 자리에 있는 /ab/는 정규식 리터럴로 읽습니다.

이 차이를 판단하는 주체는 JavaScript 정책입니다. 파서가 현재 상태에서 받을 수 있는 토큰과 직전에 소비한 토큰 등의 문맥을 전달하면, 정책은 이 문맥에 맞는 규칙 묶음을 반환합니다. 파서는 그 반환값을 그대로 사용해 source에 다음 토큰을 요청합니다.

// Parser: 문맥을 정책에 전달하고 반환값으로 다음 토큰을 요청합니다.
var goal = policy.Resolve(context);
var read = source.Peek(cursor, goal);

위 코드는 내부 호출 관계를 보여 주는 예시입니다. 사용 코드는 앞에서 본 language.CreateTokenSource(input)과 parser.Parsing(source)면 됩니다. 선택 과정은 준비된 JavaScript 정책에서 수행합니다.

파싱 테이블의 한 행에서 두 슬래시 방식이 함께 후보로 나올 때는, 정책이 JavaScriptSlashContext에 기록된 문맥으로 둘을 구분합니다. 이 언어 전용 보조 코드는 제어문의 조건 괄호와 호출 괄호, 블록과 객체, 함수 선언·함수 표현식·화살표 함수의 본문을 구분합니다. 예를 들어 화살표 함수의 블록 본문이 닫힌 뒤 새 문장이 시작되면 정규식을 읽을 수 있고, 괄호로 감싼 화살표 함수 표현식 뒤에서는 나눗셈을 읽을 수 있습니다.

이 문맥을 얻기 위해 매 요청마다 원문의 처음부터 다시 살펴보지는 않습니다. source가 토큰을 반환할 때, 보조 코드는 직전 토큰의 문맥에서 새 토큰의 문맥을 계산해 보관합니다. 다음 요청에서 정책은 직전 토큰에 연결된 이 정보를 사용하며, 문장 종료 조건도 같은 정보에서 화살표 블록의 끝을 확인합니다. 문자열·정규식 토큰 내부나 건너뛴 주석의 글자는 괄호로 세지 않습니다.

문맥은 변경할 수 없는 값이며, 해당 토큰 객체에만 연결합니다. 같은 원문 위치라도 서로 다른 예측 후보가 만든 토큰을 합치지 않으므로, 한 후보가 살펴본 문맥이 다른 후보의 문맥을 바꾸지 않습니다. 내부 캐시는 약한 참조를 사용해 더 이상 사용하지 않는 토큰을 계속 붙잡아 두지 않습니다. 템플릿의 보간 중괄호 깊이는 각 커서의 LexicalState에 별도로 보관합니다. 공통 호출 구조는 파서 주도 렉싱 문서에서 이어서 볼 수 있습니다.
