정규식의 끝을 찾은 뒤,
본문의 문법까지 검사합니다.

JavaScriptRegExpValidation은 JavaScript 정규식 리터럴의 본문이 ECMAScript 문법에 맞는지 검사합니다. 개발자가 기존 JavaScript 문법으로 입력을 파싱하고 Validate를 호출하면, 그룹·반복·이스케이프·문자 집합의 오류도 함께 확인할 수 있습니다.

예를 들어 /[z-a]/u에는 리터럴을 닫는 슬래시가 있고, u도 올바른 플래그입니다. 하지만 본문의 문자 범위는 z에서 a로 거꾸로 지정되어 있습니다. 이 기능은 그 본문을 살펴 regexp_syntax 진단을 반환합니다.

리터럴 하나를 토큰으로 읽는 검사와, 그 토큰 안의 정규식 문법을 검사하는 일은 서로 다른 단계입니다. 먼저 두 단계를 구분한 뒤, 플래그에 따라 달라지는 문법과 사용 코드를 차례로 살펴보겠습니다.

1. 토큰을 읽을 때에는 경계와 플래그를, 파싱 뒤에는 본문을 검사합니다.

정규식 리터럴 /ab+/gi에서 두 슬래시 사이의 ab+가 본문이고, 닫는 슬래시 뒤의 gi가 플래그입니다. Janglim은 다음 순서로 이 리터럴을 처리합니다.

정규식 리터럴 하나를 처리하는 세 단계
순서담당하는 검사예제
1. 경계 찾기이스케이프와 문자 클래스를 구분하며 닫는 슬래시까지 읽습니다./a\/b/의 \/는 본문의 슬래시입니다.
2. 플래그 검사dgimsuvy 중에서 골랐는지, 중복이나 u·v 동시 사용이 없는지 확인합니다./a/gg, /a/uv는 이 단계에서 오류입니다.
3. 본문 검사최종 구문 트리의 정규식 토큰에 RegExpPattern 문법과 정적 오류 조건을 적용합니다./[z-a]/u는 본문의 범위가 잘못되었습니다.

첫 두 단계는 source가 정규식 토큰을 읽을 때 수행합니다. 이어서 파서가 전체 입력의 구문 트리를 만들면, Validate가 그 트리 안의 정규식 토큰을 찾아 세 번째 검사를 수행합니다.

본문은 실제 파싱 결과에 들어간 토큰만 검사합니다.

JavaScript의 슬래시는 나눗셈과 정규식에 모두 쓰입니다. 파서는 현재 문맥을 정책에 전달하고, 정책이 반환한 규칙 묶음으로 source에 다음 토큰을 요청합니다. 갈림길을 예측하는 중에는 최종 결과에서 버릴 후보도 읽을 수 있습니다.

그런데 버릴 후보가 읽은 정규식 본문까지 즉시 검사하면, 그 후보의 오류 때문에 올바른 나눗셈 경로의 파싱도 중단될 수 있습니다. 따라서 본문 검사는 파싱을 마친 구문 트리에서 수행합니다. 이렇게 하면 최종 결과에 들어간 정규식 리터럴만 검사할 수 있습니다. 이 검사 순서는 기존의 플래그 검사와 JavaScript 정책의 규칙 묶음 선택을 그대로 사용합니다.

2. 플래그가 일반·u·v 모드의 본문 문법을 정합니다.

본문이 같아도 플래그에 따라 허용되는 표기가 달라집니다. u와 v는 단순한 표시가 아니라, 정규식을 읽는 문자 단위와 적용할 문법을 바꾸는 플래그입니다.

모드문자와 문법의 기준
일반 모드u·v가 없으면 UTF-16 코드 단위로 읽고, Annex B.1.2의 기존 정규식 호환 문법을 함께 적용합니다.
uUnicode 코드 포인트로 읽습니다. Unicode 이스케이프·속성을 지원하며, 잘못된 이스케이프와 범위 조건을 엄격하게 검사합니다.
vu와 같은 Unicode 문자 처리를 사용하고, 중첩 문자 집합·집합 연산·문자열 집합 문법을 적용합니다.

예를 들어 /\8/은 일반 모드의 호환 문법으로 허용합니다. 반면 /\8/u에서 숫자 8은 8번 캡처를 가리키므로, 해당 캡처가 없으면 오류입니다. /[\d-z]/도 일반 모드에서는 허용하지만, u 모드에서는 문자 집합 \d를 범위의 한쪽 끝으로 쓸 수 없어 오류입니다.

이 호환 문법에는 일반 모드의 8진수 이스케이프, 넓은 identity escape, 반복 가능한 전방 탐색 등이 포함됩니다. Script가 엄격 모드인지, 입력이 Module인지와 관계없이 정규식의 일반·u·v 모드는 각 리터럴의 플래그로 정합니다. 엄격 모드 JavaScript 안에서도 일반 모드 정규식에는 Annex B.1.2의 이 호환 규칙을 적용합니다.

문자 단위의 차이는 범위 검사에도 영향을 줍니다. /[😀-😁]/u는 이모지 두 개의 코드 포인트를 비교합니다. \uD83D\uDE00처럼 인접한 고정 길이 이스케이프 두 개가 surrogate 쌍을 이루는 경우도 Unicode 문법에 따라 결합합니다. 이 처리는 실제 코드 포인트 값으로 범위의 순서를 확인하기 위해 필요합니다.

3. 그룹을 구분하고, 역참조가 가리키는 캡처를 확인합니다.

먼저 본문 안의 괄호는 모두 같은 역할을 하지 않습니다. 검사기는 괄호의 시작 표기를 읽어, 입력을 캡처하는 그룹인지 또는 다른 역할의 그룹인지 구분합니다.

본문 표기역할
(ab)괄호 안에 맞는 부분을 번호가 있는 캡처로 만듭니다.
(?<word>ab)번호와 함께 word라는 이름도 가진 캡처입니다.
(?:ab)문법을 묶되 새 캡처 번호는 만들지 않습니다.
(?=ab), (?!ab)현재 위치 뒤쪽을 확인하는 전방 탐색입니다.
(?<=ab), (?<!ab)현재 위치 앞쪽을 확인하는 후방 탐색입니다. 문법 검사에는 고정 길이 조건을 추가하지 않습니다.

그룹 안에서는 ab|cd처럼 여러 대안을 쓸 수 있고, 빈 그룹이나 빈 대안도 허용합니다. 괄호를 열었다면 해당 그룹을 닫는 괄호가 필요합니다.

역참조의 번호와 이름은 본문 전체를 기준으로 검사합니다.

/(a)\1/u의 \1은 1번 캡처를 가리킵니다. 검사기는 본문 전체의 캡처 개수를 먼저 세므로, 선언보다 앞에 적힌 /\1(a)/u도 허용합니다. 하지만 /(a)\2/u에는 2번 캡처가 없어 오류입니다.

이름을 쓰는 /(?<word>ab)\k<word>/u에서는 word 캡처의 존재를 확인합니다. 이름에는 ECMAScript 식별자 문자와 Unicode 이스케이프를 쓸 수 있으며, 이스케이프를 해독한 결과로 이름을 비교합니다. 따라서 word와 같은 이름이 되는 다른 이스케이프 표기도 동일한 캡처 이름입니다.

일반 모드에서도 이름 있는 캡처가 하나라도 있으면, 본문 전체의 \k에 이름 역참조 문법을 적용합니다. 이 때문에 뒤쪽의 이름 있는 캡처가 앞쪽 \k의 해석에도 영향을 줍니다.

같은 캡처 이름은 서로 다른 대안에서 사용할 수 있습니다.

/(?<value>a)|(?<value>b)/u     // 허용: 서로 다른 대안
/(?<value>a)(?<value>b)/u     // 오류: 같은 순서 안에 두 캡처

첫 번째 본문에서는 |의 왼쪽 대안과 오른쪽 대안이 같은 이름을 사용합니다. 두 번째 본문은 한 대안 안에 같은 이름의 캡처 두 개가 이어지므로 오류입니다. 바깥 캡처와 그 안의 캡처가 같은 이름을 쓰는 경우도 오류입니다.

검사기는 두 캡처를 서로 다른 대안으로 나누는 문법 구조가 있는지 확인합니다. 실제 문자열을 넣어 어느 캡처가 성공하는지 시험해서 중복 여부를 정하지 않습니다.

4. 반복의 대상·횟수와 조건 그룹의 표기를 검사합니다.

캡처와 일반 문자가 올바르게 구성되었다면, 그 뒤에 반복 표기를 붙일 수 있습니다. a*·a+·a?와 a{2,5}는 각각 반복 횟수를 정하고, 끝의 ?는 최소 반복을 우선하는 표기입니다. 예를 들어 a+?는 허용하지만, 반복 표기 두 개를 연속해서 붙인 a++는 오류입니다.

중괄호 안의 횟수는 10진수 정수로 비교합니다. 따라서 a{5,2}는 최소 횟수가 최대 횟수보다 커서 오류입니다. 검사기는 숫자가 매우 길어도 유효 자릿수와 숫자 순서로 정확히 비교하므로, C# 정수의 범위를 넘거나 두 값이 무한대로 바뀌는 일이 없습니다.

입력 위치를 확인하는 조건에는 반복 제한이 있습니다.

^·$·\b·\B 뒤에 반복 표기를 붙이면 오류입니다. 전방 탐색 (?=a)·(?!a)의 반복은 일반 모드의 호환 문법에서 허용하고, u·v 모드에서는 거부합니다. 후방 탐색은 세 모드 모두 직접 반복할 수 없습니다.

이 조건을 일반 그룹으로 감싸면 문법상 반복 대상이 달라집니다. 예를 들어 /(?:(?=a))*/u에서 *는 전방 탐색 자체가 아니라 바깥의 일반 그룹 (?:...)에 붙으므로 문법을 만족합니다. 이 구분도 문자열 매칭 없이 표기의 구조로 검사합니다.

그룹 안에서 바꿀 수 있는 수식자는 i·m·s입니다.

/(?i:abc)/u          // 이 그룹에 i 적용
/(?im-s:abc)/u       // 이 그룹에 i·m 적용, s 해제
/(?i-i:abc)/u        // 오류: 같은 수식자를 적용·해제 목록에 함께 사용

수식자 그룹은 (?수식자:본문) 또는 (?적용할 수식자-해제할 수식자:본문) 형태입니다. 검사기는 i·m·s만 허용하고, 각 목록의 중복과 두 목록 사이의 중복을 확인합니다. (?-i:abc)처럼 해제 목록만 쓸 수 있으며, (?i-:abc)처럼 적용 목록만 남길 수도 있습니다. 두 목록이 모두 빈 (?-:abc)는 오류입니다.

5. Unicode 속성은 명세에 정해진 이름과 별칭으로 검사합니다.

u·v 모드에서는 \p{...}로 Unicode 속성을 지정할 수 있습니다. 예를 들어 /\p{Script=Latin}+/u는 Latin 스크립트 속성을 사용하고, /\p{Lu}/u는 대문자 범주를 사용합니다. 이때 본문 검사에 필요한 것은 속성에 속한 문자를 모두 나열하는 일이 아니라, 그 속성과 값의 이름이 ECMAScript에서 허용되는지 확인하는 일입니다.

표기 종류허용 예제
일반 범주와 값\p{General_Category=Uppercase_Letter}, \p{gc=Lu}
스크립트와 확장 스크립트\p{Script=Latin}, \p{sc=Latn}, \p{scx=Latn}
범주 값 또는 이진 속성\p{Lu}, \p{ASCII}, \p{White_Space}
문자열의 이진 속성\p{RGI_Emoji} 등 명세 Table 66의 이름. v 모드에서 사용합니다.

이름은 대소문자까지 정확히 비교합니다. Script=Latin은 허용하지만 script=latin은 오류이며, 공백·하이픈을 제거하거나 Is 접두사를 붙여 이름을 보정하지 않습니다. 이 규칙은 ECMAScript의 속성 표기가 엔진마다 달라지는 일을 막기 위해 필요합니다.

속성 이름은 ECMAScript 2026의 Table 64·65·66으로 한정하고, 일반 범주·스크립트 값의 별칭은 Unicode 17.0.0의 공식 데이터로 고정합니다. 생성된 C# 목록을 저장소에 포함하므로, 일반 빌드와 검사 결과는 네트워크나 .NET 런타임의 Unicode 버전에 의존하지 않습니다.

\P{...}는 속성의 보완 집합을 나타냅니다. 다만 RGI_Emoji처럼 여러 문자로 된 문자열을 포함하는 속성은 \P로 뒤집을 수 없습니다. 문자열이 포함되는 집합의 조건은 다음 절에서 이어서 설명합니다. 데이터의 출처·해시·재생성 방법은 Unicode 데이터 안내에 기록했습니다.

6. v 모드에서는 문자 집합끼리 연산하고 문자열 집합도 표현합니다.

일반 문자 클래스 [a-z]가 범위 안의 문자를 나타낸다면, v 모드의 문자 클래스는 그 안에 다른 문자 집합을 넣을 수 있습니다. 집합 두 개를 적거나 연산자로 연결해 합집합·교집합·차집합을 표현합니다.

/[a-cx-z]/v                // 합집합: 두 범위의 문자
/[[a-z]&&[^aeiou]]/v       // 교집합: a-z 중 모음 집합의 바깥에 있는 문자
/[[a-z]--[aeiou]]/v         // 차집합: a-z에서 모음 집합을 제외한 문자

같은 대괄호 깊이에서 합집합·교집합·차집합을 섞으려면 중첩 대괄호로 묶어야 합니다. 예를 들어 [a&&b--c]는 오류이고, [[a&&b]--c]는 묶는 순서가 명확합니다. 범위의 양 끝에는 문자 하나씩이 필요하므로, 집합이나 문자열을 -의 한쪽 끝으로 쓸 수 없습니다.

또한 v 모드에서는 일반 문자로 쓸 괄호·슬래시·하이픈 등과 예약된 연속 문장 부호를 이스케이프해야 합니다. 검사기는 이 규칙도 적용하므로 [()] 대신 [\(\)]처럼 작성합니다.

문자열 집합을 부정하려면 한 문자로만 구성되어야 합니다.

\q{ab|cd}는 문자열 ab 또는 cd를 집합의 요소로 적는 표기입니다. 따라서 /[\q{ab|cd}]/v를 사용할 수 있습니다. 하지만 이 집합 앞에 ^를 붙인 /[^\q{ab|cd}]/v는 오류입니다. 부정 문자 클래스는 한 문자에 대한 보완 집합을 나타내므로, 여러 문자나 빈 문자열이 들어갈 수 있는 집합에는 그대로 적용할 수 없기 때문입니다.

이 조건을 판단할 때 검사기는 ECMAScript의 MayContainStrings 규칙을 따릅니다. 이 규칙은 실제 집합을 계산하지 않고 문법 구조만으로 다음 가능성을 전달합니다.

문법 구조여러 문자·빈 문자열의 가능성
\q{...}대안 하나라도 빈 문자열이거나 두 문자 이상이면 가능성이 있습니다. 대안이 모두 한 문자이면 없습니다.
합집합어느 피연산자에라도 가능성이 있으면 전달합니다.
교집합양쪽 피연산자에 모두 가능성이 있을 때 전달합니다.
차집합첫 번째 피연산자의 가능성을 그대로 전달합니다.

예를 들어 /[^\q{a|b}]/v는 대안이 각각 한 문자이므로 허용합니다. /[^\q{ab}&&a]/v도 교집합의 한쪽이 한 문자뿐이어서 허용합니다. 반면 /[^\q{ab}--\q{ab}]/v는 차집합의 첫 피연산자가 문자열을 포함하므로 오류입니다. 실제로 차집합을 계산하면 비어 있더라도, 문법 검사는 명세의 가능성 전달 규칙으로 부정 여부를 판단합니다.

7. 기존 Parsing → Validate 순서로 본문 오류를 확인합니다.

표현식·Script·Module의 공개 API는 같은 검사를 사용합니다. 다음 C# 예제는 Script 안에 잘못된 정규식 범위를 넣고, 파싱을 마친 뒤 그 본문 오류를 출력합니다.

using System;
using Janglim.FrontEnd.Grammars.JavaScript;
using Janglim.FrontEnd.Parsers.LR;

var language = new JavaScriptScriptGrammar();
var parser = new LALRParser(language.Grammar);
var input = "const pattern = /[z-a]/u;";

var parsed = parser.Parsing(language.CreateTokenSource(input));
if (!parsed.Success)
{
    Console.WriteLine(parser.FiredException?.Message);
    return;
}

var diagnostics = language.Validate(parsed.ToParseTree);
foreach (var diagnostic in diagnostics)
{
    var original = input.Substring(
        diagnostic.SourceOffset, diagnostic.Length);
    Console.WriteLine($"{diagnostic.Code}: {diagnostic.Message}");
    Console.WriteLine($"원문: {original}");
}

이 입력의 정규식은 토큰 하나로 읽을 수 있으므로, 파싱은 변수 선언의 구문 트리를 만듭니다. 이어서 Validate가 본문의 z-a 범위를 검사해 regexp_syntax 진단을 반환합니다. 입력을 유효하다고 받아들이는 조건은 기존처럼 파싱 성공과 빈 진단 목록입니다.

진단의 위치는 원래 JavaScript 입력을 기준으로 합니다.

SourceOffset은 정규식 본문 안의 상대 위치가 아니라, 전체 input 안에서 오류가 시작되는 위치입니다. Length와 함께 UTF-16 코드 단위로 계산하므로 C# 문자열의 Substring에 그대로 사용할 수 있습니다. 끝에 필요한 문자가 빠진 경우에는 끝 위치를 가리키는 길이 0의 진단이 나올 수 있습니다.

본문에 여러 문제가 있어도 검사기는 정규식 리터럴 하나당 먼저 찾은 오류 하나를 반환합니다. 입력에 정규식 리터럴이 여러 개 있으면 각 리터럴을 따로 검사합니다. 이 과정에서 원문의 문자, 입력 토큰과 구문 트리는 바뀌지 않습니다.

문법 검사기는 JavaScript 언어 지원 계층에 있습니다.

공통 렉서·파서 엔진은 기존 구조를 사용합니다. 새로 추가한 본문 검사는 JavaScript의 최종 구문 트리를 순회하는 기존 JavaScriptExpressionValidation에 연결됩니다.

중첩 그룹과 v 문자 집합은 명시적인 스택으로 읽습니다. 따라서 그룹 깊이가 깊어져도 C# 함수를 재귀 호출하며 검사하지 않습니다. 캡처 이름은 한 대안 안에서 합칠 때 중복을 거부하고, 서로 다른 대안을 합칠 때는 중복을 허용합니다. 이름 집합은 작은 쪽을 큰 쪽에 합쳐 불필요한 복사를 줄입니다.

이 검사의 목적은 ECMAScript 문법의 수락·거부를 판단하고 오류 위치를 알려주는 일입니다. .NET 정규식은 JavaScript와 그룹·이스케이프·v 집합의 문법이 다르므로, 이 목적에는 ECMAScript 규칙을 직접 읽는 C# 검사기를 사용합니다. 문자열 검색과 정규식 매칭을 실행하는 런타임은 애플리케이션에서 별도로 선택할 수 있습니다.

엔진 비교 결과가 다르면 고정한 명세와 원본 데이터를 확인합니다.

테스트는 각 표기의 수락·거부, 모드별 차이, 오류의 UTF-16 위치, 깊은 중첩과 긴 숫자, 기존 함수·클래스·모듈·템플릿과의 조합을 확인합니다. 비교용 Node.js에서도 프로그램이나 정규식 매칭을 실행하지 않고, 정규식 생성과 소스의 구문 컴파일 결과만 확인합니다.

다만 비교 엔진의 결과 자체가 문법의 정의는 아닙니다. Node.js 24.12.0과 대조하면서 다음 차이를 확인했으며, Janglim은 ECMAScript 2026과 고정한 Unicode 17 데이터의 조건을 적용합니다.

  • 매우 긴 반복 횟수: 최소·최대 횟수가 모두 매우 크더라도 정확한 정수로 비교해, 최소가 더 크면 거부합니다.
  • 중첩된 같은 캡처 이름: 바깥 캡처와 그 안의 캡처는 서로 다른 대안으로 분리되지 않으므로 거부합니다.
  • 허용된 속성 별칭: Table 65의 White_Space·space를 허용하며, 목록에 없는 WSpace는 거부합니다.
  • Unicode 값 목록: Unicode 17에서 추가한 스크립트와 공식 별칭을 사용합니다. 공식 목록에 있는 Hrkt·Katakana_Or_Hiragana도 허용합니다. 이 스크립트 값은 역사적으로 사용된 빈 집합 값입니다.
