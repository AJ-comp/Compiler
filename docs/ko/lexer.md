# 렉서 — 글자를 토큰으로, 토큰 사이의 원문도 함께

[문법 읽는 법](grammar-reading.md)에서 `id`, `'+'`, `';'` 같은 재료를 봤죠.
이제 실제 입력에서 그 재료를 찾아내는 **렉서(lexer), 또는 토크나이저(tokenizer)** 를 봅니다.

이 장에서는 특히 **왜 토큰 앞의 공백·주석·줄바꿈도 보존해야 하는지** 설명해요.
그 이유를 이해하면, 렉서가 맡을 일과 파서가 맡을 일도 자연스럽게 구분됩니다.

## ① 왜 렉서가 필요한가요?

입력은 처음에는 글자의 나열입니다.

```text
a + a * a
```

파서가 곱셈과 덧셈의 구조를 판단하려면, 먼저 어디까지가 이름이고 어디가 연산자인지 알아야 합니다.
렉서는 등록된 토큰 규칙으로 입력을 나누고, 각 조각에 종류와 위치를 붙여요.

```text
입력:       a + a * a
파싱 토큰: [a] [+] [a] [*] [a]
종류:      이름 연산자 이름 연산자 이름
```

**왜 두 단계로 나누나요?**
`customerName`이 하나의 이름인지 찾아내는 일과, `a + a * a`를 `a + (a * a)`로 묶는 일은
서로 다른 판단이기 때문이에요. 렉서는 **조각의 경계와 종류**, 파서는 **조각들의 문법적 관계**를 맡습니다.

## ② 토큰 사이의 정보가 필요한 이유

작은 산술식에서는 공백이 있어도 없어도 같은 구조가 나옵니다.

```text
a+a*a
a + a * a
```

하지만 어떤 언어에서는 **토큰 사이에 줄바꿈이 있었는지**가 문법에 영향을 줍니다.
JavaScript 함수 안의 두 `return`을 비교해 봅시다.

```javascript
function first(value) {
    return value;
}

function second(value) {
    return
        value;
}
```

`first`는 `value`를 반환합니다. `second`는 `return`과 `value` 사이의 줄바꿈 때문에
반환 표현식이 없는 `return;`으로 처리되어 `undefined`를 반환합니다. 뒤의 `value;`는 별도의 표현식 문장입니다.
JavaScript 명세는 반환할 표현식이 `return`과 같은 줄에서 시작하도록 정합니다.
둘 사이에 줄바꿈이 있으면 자동 세미콜론 삽입 규칙이 적용됩니다.
([return 규칙](https://tc39.es/ecma262/multipage/ecmascript-language-statements-and-declarations.html#sec-return-statement),
[세미콜론 삽입 예제](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-examples-of-automatic-semicolon-insertion))

두 `return` 문장을 **토큰의 본문만으로** 나타내면 차이가 사라집니다.

```text
첫 번째: [return] [value] [;]
두 번째: [return] [value] [;]
```

**왜 보강이 필요한가요?**
토큰 본문에는 `return`과 `value` 사이가 공백이었는지 줄바꿈이었는지에 관한 정보가 빠져 있어요.
입력에서 실제로 일어난 일을 남겨야, 이후 단계가 언어의 규칙에 따라 판단할 수 있습니다.

기존 Janglim에서도 공백과 주석은 `TokensForView`에 남아 있었습니다.
이번 보강은 **이미 보존하던 원문을 파싱 토큰에서도 바로 조회할 수 있게 연결하는 것**입니다.
원문 전체나 표시용 토큰 목록을 별도로 찾아가서 경계를 복원하는 작업을 공통 렉서에서 처리해요.

## ③ 이제 토큰마다 무엇이 붙나요?

다음 입력을 보세요. `value` 앞에는 들여쓰기 공백이 네 개 있습니다.

```text
return
    value
;
```

렉싱 후 파싱에 전달되는 토큰은 여전히 세 개입니다.
각 토큰에는 다음 정보가 추가됩니다.

```text
토큰: "return"
  앞에 있던 원문: ""
  앞에 줄바꿈이 있었음: 아니오

토큰: "value"
  앞에 있던 원문: "\n    "
  앞에 줄바꿈이 있었음: 예

토큰: ";"
  앞에 있던 원문: "\n"
  앞에 줄바꿈이 있었음: 예
```

여기서 `\n`은 실제 줄바꿈을 눈으로 읽을 수 있게 표시한 것입니다.

| 토큰 | 앞에 있던 원문 | 앞 줄바꿈 | 토큰 시작 위치 |
|---|---|---|---|
| `return` | `""` | 아니오 | 0 |
| `value` | `"\n    "` | 예 | 11 |
| `;` | `"\n"` | 예 | 17 |

**“앞에 있던 원문”의 범위는 어디부터인가요?**
이전 **파싱 토큰**의 끝에서 현재 파싱 토큰의 시작까지입니다.
첫 번째 토큰은 입력의 시작부터 자기 앞까지의 원문을 받습니다.

**왜 다음 토큰의 앞에 붙이나요?**
파서가 다음 토큰을 볼 때 “이 토큰이 앞 토큰과 같은 줄에 이어졌나?”를 함께 확인할 수 있기 때문이에요.
예를 들어 `value`를 볼 때 그 앞의 줄바꿈 여부도 바로 알 수 있습니다.
토큰의 순서와 본문을 유지하면서 경계 정보를 전달할 수 있다는 것도 이 방식의 장점입니다.

## ④ 왜 줄바꿈 여부뿐 아니라 원문도 남기나요?

다음 두 경계에는 모두 줄바꿈이 있습니다.

```text
"\n    "
" /* 설명\n계속 */ "
```

`앞 줄바꿈: 예`라는 요약값에서는 주석 내용과 들여쓰기 형태가 생략됩니다.
원문을 함께 남겨야 다음 질문에도 답할 수 있어요.

- 들여쓰기는 공백 몇 개였나요, 탭이었나요?
- 토큰 앞에 어떤 주석이 있었나요?
- 줄바꿈은 `\n`이었나요, `\r\n`이었나요?
- 편집기에서 정확히 어느 부분을 강조하거나 교체해야 하나요?

그래서 **원문과 위치는 상세 정보**, **줄바꿈 여부는 빠르게 확인할 요약 정보**로 함께 제공합니다.
원문은 주석과 줄바꿈 형식까지 그대로 보관합니다.

이번 요구는 **기존 문법과 파싱 토큰열을 유지하면서, 다음 단계에 경계 정보까지 제공하는 것**이에요.
그 요구를 만족시키기 위해 토큰에 원문 정보를 덧붙이는 방식을 택했습니다.

## ⑤ 주석 안의 줄바꿈도 확인해야 하는 이유

주석을 파싱에서 제외하도록 등록한 문법이라면 다음 주석도 토큰 사이의 원문에 들어갑니다.

```text
return /* 설명 */ value;
```

```text
value 앞 원문: " /* 설명 */ "
앞 줄바꿈: 아니오
```

주석이 두 줄에 걸쳐 있으면 결과가 달라집니다.

```text
return /* 설명
계속 */ value;
```

```text
value 앞 원문: " /* 설명\n계속 */ "
앞 줄바꿈: 예
```

**왜 주석 안의 줄바꿈도 검사하나요?**
문법에서 무시하는 주석 안에도 실제 줄바꿈이 있을 수 있기 때문입니다.
JavaScript는 줄바꿈을 포함한 여러 줄 주석을 문법 판단에 필요한 줄바꿈으로 취급합니다.
공백만 검사하고 주석을 통째로 건너뛰면 그 사실을 놓치게 돼요.
([ECMAScript 주석 규칙](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-comments))

Janglim의 이번 구현은 **파싱에서 제외된 원문 전체**를 기준으로 줄바꿈을 검사합니다.
주석을 인식하는 규칙 자체는 문법에 등록되어 있어야 합니다.

## ⑥ 토큰 내부의 줄바꿈은 구분해야 합니다

문법에 따라 하나의 토큰으로 인식하는 여러 줄 문자열이나 템플릿 안에도 줄바꿈이 있을 수 있죠.
그 줄바꿈은 **그 토큰의 본문**에 속합니다.

```text
[여러 줄 문자열 토큰] [;]
```

문자열 토큰의 끝과 `;` 사이에 공백만 있었다면, `;`의 `앞 줄바꿈`은 **아니오**입니다.

**왜 이 구분이 필요한가요?**
“문자열 내용에 줄바꿈이 있다”와 “두 토큰 사이에 줄바꿈이 있다”는 다른 사실이기 때문이에요.
문법의 토큰 경계 조건을 판단하려면 해당 경계에 속하는 원문만 검사해야 합니다.

경계 정보는 **파싱에서 제외된 원문**으로 구성합니다.
문법이 줄바꿈을 **직접 파싱할 토큰**으로 정의했다면, 그 줄바꿈은 파싱 토큰열에 남습니다.

## ⑦ EBNF 리더, 렉서, 파서는 각각 무엇을 하나요?

서로 읽는 대상부터 다릅니다.

| 부품 | 읽는 것 | 하는 일 | 그 역할이 필요한 이유 |
|---|---|---|---|
| EBNF 리더 | 문법을 적은 EBNF 텍스트 | 문법과 토큰 규칙을 객체로 만듭니다 | 사람이 적은 문법을 엔진이 사용할 형태로 바꿔야 합니다 |
| 렉서 | 실제로 분석할 입력 원문 | 토큰과 위치, 토큰 사이의 원문 정보를 만듭니다 | 실제 입력에 어떤 공백·주석·줄바꿈이 있었는지 여기서 알 수 있습니다 |
| 파서 | 토큰과 조회 가능한 경계 정보 | 문법에 맞는 배열인지 판단하고 트리를 만듭니다 | 같은 줄바꿈이라도 문법에 따라 허용 여부와 의미가 달라집니다 |

```text
문법 텍스트 ── EBNF 리더 ── 문법 객체
                              ├── 렉서에 토큰 규칙 등록
                              └── 파서의 LALR 테이블 생성

실제 입력 ── 렉서 ── 토큰 + 경계 정보 ── 파서 ── 문법 구조
```

**왜 이 정보는 공통 렉서에서 만드나요?**
EBNF 리더는 문법의 정의를 읽고, 렉서는 사용자가 입력한 실제 원문을 읽습니다.
실제 입력과 토큰 분류를 함께 다루는 공통 렉서에서 정보를 만들어야, EBNF로 정의한 문법과
C# 트리 API로 정의한 문법이 같은 기능을 사용할 수 있어요.
여러 언어가 이 공통 입력 처리 기능을 함께 사용할 수 있습니다.

문법에 “여기서는 줄바꿈 금지” 같은 조건을 표현할 기능을 추가할 때에는,
**그 조건을 읽는 부분과 실제 파싱에서 실행하는 부분도 함께 필요합니다.**
보존한 입력 정보는 그 조건을 판단하는 근거가 됩니다.

## ⑧ 왜 줄바꿈의 의미는 문법과 파서가 판단하나요?

줄바꿈의 존재와 줄바꿈의 의미는 다른 단계의 일입니다.
JavaScript의 다음 입력에서는 줄바꿈 때문에 문법 오류가 발생합니다.

```javascript
throw
    error;
```

`throw`와 던질 표현식 사이의 줄바꿈은 문법 오류입니다.
앞에서 본 `return`의 경우와 처리 결과가 다르죠.
([ECMAScript throw 규칙](https://tc39.es/ecma262/multipage/ecmascript-language-statements-and-declarations.html#sec-throw-statement))

**왜 렉서는 사실만 제공하나요?**
공통 렉서가 줄바꿈마다 특정 언어의 규칙을 적용하면 다른 문법에도 그 동작이 강제로 들어가기 때문입니다.
렉서는 “여기에 실제 줄바꿈이 있었다”를 제공하고, 그 정보를 사용하는 문법·파싱 단계가
“허용한다”, “오류다”, “문장을 끝낸다”를 판단해야 합니다.

현재 구현된 것은 **정보의 생성·보존·전달·조회**입니다.

## ⑨ 마지막 토큰 뒤의 원문은 어디로 가나요?

```text
return value; // 마지막 설명
```

마지막 `;` 뒤에도 공백과 주석이 있습니다.
이 끝 경계의 원문은 렉싱 결과의 **`TrailingTrivia`**에 따로 보관합니다.
주석·공백만 있는 입력이라면 제외된 입력 전체가 이곳에 들어갑니다.

**왜 별도 보관이 필요한가요?**
끝부분을 버리면 파일을 온전히 복원하거나 파일 끝의 주석과 줄바꿈을 확인할 수 없기 때문입니다.
파일 끝의 주석과 줄바꿈은 렉싱 결과의 `TrailingTrivia`에서 읽을 수 있습니다.
