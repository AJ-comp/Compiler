Lexer · LRParser 연결 구조 / 엔진 구현 문서
Lexer가 source를 만들고,
파서가 토큰을 받아 파싱합니다.
Lexer에 토큰 규칙을 등록하고, 사용할 규칙 묶음과 선택 방법을 정책으로 준비합니다. CreateTokenSource에 원문과 정책을 전달하면 source 객체가 만들어집니다. 파서는 현재 파싱 문맥을 정책에 전달합니다. 정책이 규칙 묶음을 선택해 반환하면, 파서는 그 묶음으로 source에 다음 토큰을 요청하고 받은 토큰을 직접 파싱합니다.
source를 준비하고 토큰을 처리할 때 각 객체가 맡는 역할
객체 | 하는 일 |
Lexer | 토큰 규칙을 관리하고, 원문과 정책을 연결하는 source를 만듭니다. |
LexicalPolicy | 파서가 전달한 문맥을 등록된 규칙 묶음·선택 로직과 함께 확인하고, 사용할 묶음 하나를 반환합니다. |
source | 원문과 정책을 보관합니다. Peek 요청을 받으면 정규식 규칙으로 렉싱하여 다음 토큰 하나를 반환합니다. |
파서 | 현재 파싱 문맥을 정책에 전달하고, 정책이 반환한 묶음을 그대로 source.Peek에 전달합니다. 받은 토큰으로 파싱 테이블을 조회하고 Shift·Reduce를 수행합니다. |
이 구조가 필요한 이유를 나눗셈과 정규식 리터럴로 살펴보겠습니다. 다음 두 입력에는 모두 / 문자가 있습니다.
result = a / b;
result = /ab/g;
첫 번째 입력의 /는 나눗셈 토큰 하나입니다. 두 번째 입력의 /ab/g는 정규식 리터럴 토큰 하나입니다. source가 각 위치에 맞는 토큰을 만들 수 있도록, 나눗셈을 인식하는 규칙과 정규식 리터럴을 인식하는 규칙을 서로 다른 묶음에 넣습니다.
Lexer가 source를 준비하고, 파서는 source에 토큰을 요청합니다. source가 렉싱하여 반환한 토큰을 파서가 직접 파싱합니다. 먼저 규칙 묶음과 source를 준비한 뒤, 파서가 토큰을 요청하는 과정으로 이어가겠습니다.
1. 공통 규칙은 함께 넣고, 달라지는 규칙만 나누어 묶습니다.
먼저 source가 렉싱할 때 사용할 정규식 규칙들을 준비하겠습니다. 예를 들어 [a-z]+ 규칙은 소문자로 이루어진 식별자를 읽고, [0-9]+ 규칙은 숫자를 읽습니다. 이 문서의 예제에서는 식별자·숫자와 =, +, ; 같은 기호의 규칙을 공통으로 사용하겠습니다.
이 공통 규칙에 나눗셈 규칙을 더한 묶음을 Div라고 부르겠습니다. 같은 공통 규칙에 정규식 리터럴을 인식하는 규칙을 더한 묶음은 RegExp라고 부르겠습니다.
두 묶음에는 공통 규칙이 모두 들어 있고, /를 인식하는 규칙이 다릅니다.
규칙 묶음 | 묶음에 포함할 규칙 |
Div | 식별자·숫자·기호의 공통 규칙
+ 나눗셈 /를 인식하는 규칙 |
RegExp | 식별자·숫자·기호의 공통 규칙
+ /ab/g 같은 정규식 리터럴을 인식하는 규칙 |
두 번째 묶음에 들어갈 예제 규칙을 정규식으로 적으면 /[a-z]+/[a-z]*입니다. 이 규칙은 /ab/g 전체를 토큰 하나로 인식합니다. 반면 Div 묶음의 / 규칙은 문자 하나만 인식합니다.
같은 위치의 원문 /ab/g에서 다음 토큰 하나를 요청하면
선택한 묶음 | source가 반환하는 다음 토큰 |
Div | / |
RegExp | /ab/g |
Div 묶음으로 그 뒤의 토큰도 계속 읽으면 공통 식별자 규칙이 ab를 인식합니다. 이어서 /와 식별자 g가 나옵니다. 이처럼 선택한 정규식 규칙 묶음에 따라, 같은 원문에서 토큰의 종류와 길이가 달라집니다.
이 규칙 묶음을 코드에서는 LexicalGoal로 표현합니다.
먼저 사용할 토큰 규칙들을 Lexer에 등록합니다. 그런 다음 그 규칙들 중 어떤 규칙을 함께 사용할지 LexicalGoal로 묶습니다. 묶음에는 등록한 규칙을 가리키는 Terminal 객체들을 담습니다.
아래 코드에서 commonTokens는 식별자·숫자·기호의 공통 토큰 규칙입니다. divisionToken은 나눗셈 규칙이고, regexToken은 정규식 리터럴을 인식하는 규칙입니다. 공통 규칙을 양쪽 묶음에 넣고, 각 묶음에 필요한 규칙 하나를 덧붙입니다.
Lexer에 등록한 토큰 규칙으로 두 묶음을 준비합니다.
var div = new LexicalGoal(commonTokens.Append(divisionToken));
var regExp = new LexicalGoal(commonTokens.Append(regexToken));
위 코드의 div와 regExp는 렉싱에 사용할 두 규칙 묶음입니다. 이 묶음들을 선택 정책에 등록하면, 정책이 사용할 수 있는 묶음 목록과 선택 방법을 함께 보관합니다.
LexicalPolicy는 규칙 묶음 목록과 선택 로직을 함께 보관합니다.
두 묶음을 다음과 같이 정책에 등록합니다. 이 생성자는 파싱 상태의 기대 단말을 비교해 묶음을 고르는 기본 선택 로직을 사용합니다.
var policy = new LexicalPolicy(div, regExp);
policy.Goals에는 div와 regExp가 순서대로 보관됩니다. 이 목록은 정책을 만든 뒤에는 바뀌지 않습니다. 묶음 구성이 끝났으므로, 이제 원문과 이 정책으로 source를 만들 수 있습니다.
Lexer.CreateTokenSource는 특정 원문을 읽을 source를 만듭니다.
CreateTokenSource는 앞으로 읽을 원문 문자열 input과 그 원문에 사용할 policy를 받습니다. 이 두 정보를 연결해 “이 원문을 나중에 토큰 하나씩 읽을 수 있는 객체”를 만듭니다.
원문과 정책으로 source를 만듭니다.
var input = "result = a / b;";
var source = lexer.CreateTokenSource(input, policy);
source는 원문 "result = a / b;"를 보관하고, 전달받은 정책을 source.Policy로 제공합니다. 정책의 Goals에는 앞에서 등록한 두 규칙 묶음이 있습니다. 실제 토큰 생성은 이후 source.Peek 요청을 받았을 때 수행합니다.
먼저 Peek가 위치를 어떻게 사용하는지 확인하겠습니다. 아래 예제 코드에서는 동작을 살펴보기 위해 div 묶음을 직접 지정합니다. 원문의 시작 위치에서 토큰을 요청하면 result가 나오고, 반환된 다음 위치에서는 =가 나옵니다.
Peek의 동작을 확인하는 예제 코드
// 이 예제에서는 div 묶음을 지정해 토큰을 확인합니다.
// 원문의 시작 위치에서 토큰 하나를 요청합니다.
var first = source.Peek(source.Start, div);
// 반환된 토큰: "result"
// "result" 다음 위치에서 토큰 하나를 요청합니다.
var second = source.Peek(first.Next, div);
// 반환된 토큰: "="
Peek에는 원문 문자열을 다시 전달할 필요가 없습니다. source가 이미 그 원문을 보관하므로, 요청할 때는 읽을 위치와 사용할 규칙 묶음을 전달합니다. 건너뛰도록 등록한 공백·주석 규칙도 source가 두 묶음에서 함께 사용합니다.
이렇게 토큰을 확인해도 source.Start는 원문의 시작 위치를 그대로 가리킵니다. 다음 절의 Parsing 호출은 이 시작 커서에서 원문 처음부터 파싱합니다.
실제 파싱에서는 정책이 사용할 묶음을 선택하고, 파서는 정책이 반환한 묶음으로 Peek를 호출합니다. 이 호출 순서는 다음 절에서 살펴보겠습니다. 그전에, 묶음 하나를 전달받은 source가 여러 토큰 규칙 중 어느 규칙을 적용하는지 먼저 확인하겠습니다.
묶음 안에서는 실제 입력을 가장 길게 읽는 토큰 규칙을 고릅니다.
규칙 묶음을 하나 선택해도, 그 묶음 안의 여러 정규식이 같은 원문 위치에 일치할 수 있습니다. 예를 들어 키워드 규칙 if와 식별자 규칙 [$A-Za-z_][$0-9A-Za-z_]*가 있다고 가정하겠습니다. 입력이 ifx이면 키워드 규칙은 앞의 두 글자 if에 일치하고, 식별자 규칙은 세 글자 ifx 전체에 일치합니다.
묶음을 전달받은 source는 그 묶음의 규칙들 중 실제 원문을 가장 길게 읽은 규칙을 선택합니다. 읽은 길이가 같을 때만 미리 정해진 규칙 우선순위를 사용합니다. 따라서 ifx에서는 세 글자를 읽은 식별자 규칙을 선택합니다. 반면 if에서는 두 규칙이 모두 두 글자를 읽으므로, 식별자 정규식보다 우선하는 리터럴 키워드 규칙을 선택합니다.
키워드 if와 $를 허용하는 식별자 규칙을 함께 사용한 결과
입력 | 각 규칙이 읽는 길이 | 선택한 토큰 |
if | 키워드 2글자 / 식별자 2글자 | 우선순위에 따라 키워드 if |
ifx | 키워드 2글자 / 식별자 3글자 | 더 길게 읽은 식별자 ifx |
if$ | 키워드 2글자 / 식별자 3글자 | 더 길게 읽은 식별자 if$ |
$name | 키워드 불일치 / 식별자 5글자 | 식별자 $name |
name$ | 키워드 불일치 / 식별자 5글자 | 식별자 name$ |
토큰 규칙의 정규식에는 단어 경계 \b가 자동으로 붙지 않습니다. 작성한 정규식이 $를 식별자의 일부로 허용하면, source는 그 정규식대로 $까지 읽습니다. 문법 개발자가 정규식 안에 직접 작성한 \b는 그대로 적용합니다.
기호도 같은 기준으로 선택합니다. = 규칙과 == 규칙을 함께 사용할 때 입력이 ==이면, 두 글자를 읽는 == 규칙이 한 글자를 읽는 = 규칙보다 우선합니다. 비교하는 길이는 정규식 코드의 글자 수가 아니라, 각 정규식이 실제 원문에서 읽은 글자 수입니다. 예를 들어 입력 aaaa에 a+와 [a-z]가 모두 일치하면, 정규식 표기는 더 짧아도 네 글자를 읽는 a+를 선택합니다.
이때 사용할 우선순위는 Lexer가 토큰 규칙을 등록할 때 정합니다. 리터럴 키워드와 정규식 식별자처럼 분류가 다르면 분류별 우선순위를 적용하고, 같은 분류이면 먼저 등록한 규칙을 앞에 둡니다. source는 생성될 때 이 순서를 보관합니다. 이후 읽은 길이가 같은 규칙이 여러 개이면, source는 이 순서에서 앞선 규칙을 선택합니다.
source.Peek는 이번에 선택한 LexicalGoal 안의 토큰 규칙들과, 모든 묶음에 공통으로 적용하는 공백·주석 규칙을 비교합니다. 선택하지 않은 묶음의 토큰 규칙은 비교에 참여하지 않습니다. 공백·주석 규칙이 선택되면 그 원문을 건너뛴 뒤, 다음 위치에서 같은 기준으로 규칙들을 다시 비교합니다.
실제 일치 결과의 길이를 비교하는 코드는 LexicalRuleMatcher에 있습니다. source.Peek와 기존 Lexer.Lexing이 이 비교기를 함께 사용하므로, 두 경로에 같은 최장 일치 기준이 적용됩니다. 각각의 정규식 내부에서는 .NET 정규식의 동작을 유지합니다. 예를 들어 주석 규칙의 .*?는 첫 번째 닫는 기호에서 멈춥니다. 비교기는 각 정규식이 반환한 일치 결과의 길이를 비교하므로, 이 주석 규칙을 마지막 닫는 기호까지 늘려 읽지 않습니다.
지금까지 source를 준비하고, 그 객체가 요청받은 위치에서 토큰 하나를 고르는 기준까지 확인했습니다. 이제 준비한 source를 파서에 전달하고, 파서가 토큰을 받아 파싱하는 순서로 이어가겠습니다.
2. 파서는 source에서 토큰을 받아 직접 파싱합니다.
Lexer가 source를 만들었으면, 파싱할 문법으로 준비한 parser에 그 객체를 전달합니다. 사용할 정책은 이미 source.Policy에 연결되어 있으므로, 다음과 같이 source만 전달하면 파서가 파싱을 시작합니다.
var result = parser.Parsing(source);
LexicalGoal은 사용할 정규식 규칙 묶음입니다. LexicalPolicy는 이 묶음들의 불변 목록과, 현재 문법 문맥에 맞는 묶음을 고르는 로직을 함께 보관합니다. 파서는 source.Policy를 통해 이 정책을 사용합니다.
파서는 다음 토큰이 무엇인지 아직 몰라도, 지금까지 소비한 입력과 현재 파싱 상태를 알고 있습니다. 파서는 현재 입력 위치와 이 파싱 정보를 LexicalContext에 담아 source.Policy에 전달합니다. 정책은 전달받은 문맥을 등록된 규칙 묶음·선택 로직과 함께 확인하고, 사용할 LexicalGoal 객체 하나를 반환합니다.
예제 문법에서 대입할 값이 시작하는 문맥이면 정책은 RegExp 묶음을 반환합니다. 이미 읽은 값 뒤에서 연산을 받을 문맥이면 정책은 Div 묶음을 반환합니다. 규칙 묶음을 판단하는 주체는 정책입니다. 파서는 정책이 반환한 묶음을 그대로 source에 전달합니다.
source를 준비한 뒤, 파서 내부에서 반복하는 순서
① 파서가 문맥을 전달하면 정책이 규칙 묶음을 반환합니다.
파서는 LexicalContext를 source.Policy.Resolve에 전달합니다. 정책은 등록된 선택 로직으로 묶음을 고르고 반환합니다.
② 파서가 반환받은 묶음으로 토큰 하나를 요청합니다.
파서는 현재 원문 위치와 정책이 반환한 묶음을 인자로 source.Peek를 호출합니다.
③ source가 렉싱하여 토큰 하나를 반환합니다.
source는 선택된 묶음의 정규식 규칙을 원문에 적용하고, 만든 토큰과 다음 위치를 반환합니다.
④ 파서가 받은 토큰을 직접 파싱합니다.
파서는 토큰으로 ACTION을 조회하고, 필요한 Reduce·Goto를 처리합니다. Shift하면 입력 위치를 이동하고 다음 토큰을 요청할 준비를 합니다.
파서 내부에서 정책과 source를 호출하는 코드
// 파서는 현재 파싱 문맥을 정책에 전달합니다.
// 정책이 사용할 규칙 묶음을 판단하고 반환합니다.
LexicalGoal goal = source.Policy.Resolve(context);
// 파서는 반환받은 묶음을 그대로 source에 전달합니다.
// source가 그 묶음으로 다음 토큰 하나를 만듭니다.
TokenRead read = source.Peek(cursor, goal);
source의 역할은 렉싱하여 토큰을 만드는 것입니다. 파싱 테이블 조회와 Shift·Reduce는 그 토큰을 받은 파서가 수행합니다.
실제 토큰을 Shift한 뒤에는, 파서가 갱신된 문맥을 정책에 전달합니다. 정책은 새 문맥을 보고 다음 토큰에 사용할 묶음을 반환합니다. 문맥에 따라 이전과 다른 묶음이 반환될 수도 있고, 같은 묶음이 반환될 수도 있습니다.
이제 이 순서를 나눗셈 입력 하나에 적용해 보겠습니다. 먼저 Div 묶음으로 /를 읽고, 다음 값의 시작에서는 묶음을 다시 고르는 과정까지 따라가겠습니다.
3. result = a / b;를 처리해 보겠습니다.
앞에서 준비한 토큰 규칙으로 다음 문법을 사용하겠습니다. id는 식별자 토큰, num은 숫자 토큰, rx는 정규식 리터럴 토큰입니다. 이 문법은 대입할 값에 식별자·숫자·정규식 리터럴을 사용할 수 있고, 값 사이에 덧셈과 나눗셈을 사용할 수 있습니다.
두 입력 예제에서 함께 사용할 문법
S    : id '=' Expr ';' ;
Expr : Expr '+' Term | Term ;
Term : Term '/' Atom | Atom ;
Atom : id | num | rx ;
id  := Identifier "[a-z]+" ;
num := NumberLiteral "[0-9]+" ;
rx  := StringLiteral "/[a-z]+/[a-z]*" ;
이 문법으로 입력 result = a / b;를 파싱하고 있다고 가정하겠습니다. 파서는 다음 세 토큰을 소비했습니다. 아직 그다음 토큰은 source에서 받지 않았습니다.
파서가 지금까지 소비한 입력
result = a
파서는 다음 원문이 / b;인지, + b;인지, ;인지 아직 모릅니다. 다만 파서는 값 a 뒤에서 나눗셈·덧셈 연산자나 세미콜론을 받을 수 있다는 사실을 현재 파싱 상태에서 알 수 있습니다.
파서는 현재 상태에서 받을 수 있는 토큰 종류와 입력 위치 등을 context에 담아 정책에 전달합니다. 기본 정책은 이 문맥과 등록된 규칙 묶음들을 비교합니다. 이 예제에서는 나눗셈 토큰을 기대할 수 있으므로, 정책이 나눗셈 규칙이 들어 있는 Div 묶음을 반환합니다.
파서가 받은 반환값이 코드의 goal입니다. 파서는 그 묶음을 그대로 source.Peek(cursor, goal)에 전달합니다. 정책이 어떤 묶음을 반환하든, 파서가 다음 토큰을 요청하는 코드는 같습니다. 이 요청을 말로 풀면 다음과 같습니다.
“정책이 반환한 규칙 묶음으로, 현재 위치의 다음 토큰 하나를 만들어줘.”
source는 Div 묶음에 포함된 정규식 규칙을 사용합니다. 이 묶음에는 나눗셈 규칙과 함께 +, ;, 식별자, 숫자 같은 공통 규칙도 들어 있습니다.
같은 Div 묶음으로 요청해도, 반환할 토큰은 실제 원문에 따라 달라집니다.
실제로 뒤에 있는 원문 | source가 반환하는 토큰 |
/ b; | 나눗셈 토큰 / |
+ b; | 덧셈 토큰 + |
; | 세미콜론 토큰 ; |
정책은 Div 규칙 묶음을 반환하고, 파서는 그 묶음을 source에 전달합니다. 실제로 어떤 토큰을 반환할지는 source가 그 묶음의 규칙으로 원문을 읽어 결정합니다.
실제 원문이 result = a / b;라면 다음 순서로 처리합니다.
result = a / b;
파서는 a 토큰까지 소비한 문맥을 정책에 전달합니다. 정책이 Div 묶음을 반환하면, 파서는 그 묶음으로 source에 다음 토큰을 요청합니다.
source는 앞의 공백을 확인하고, / 문자 하나를 나눗셈 토큰으로 만들어 반환합니다. 반환값에는 공백 정보와 / 다음의 입력 위치도 담습니다.
파서는 반환된 나눗셈 토큰으로 ACTION[현재 상태, 나눗셈 토큰]을 조회합니다. 필요한 Reduce·Goto를 처리한 뒤, 해당 토큰을 Shift합니다.
파서는 /를 Shift한 뒤 입력 위치를 옮기고, 갱신된 문맥을 정책에 전달합니다. 이제 나눗셈의 오른쪽 값이 시작하는 위치이므로, 정책은 값을 인식할 수 있는 RegExp 묶음을 반환합니다.
파서는 정책이 반환한 묶음으로 다음 토큰을 요청합니다. 식별자 규칙은 두 묶음에 공통으로 들어 있으므로, source는 식별자 토큰 b를 반환합니다.
파서는 b를 Shift한 뒤 갱신된 문맥을 정책에 전달합니다. 정책이 Div 묶음을 반환하면, 파서는 그 묶음으로 다음 토큰을 요청하고 source는 ;를 반환합니다.
파서는 ;를 Shift한 뒤에도 같은 순서로 정책을 호출하고, 반환받은 묶음으로 다음 토큰을 요청해 EOF를 받습니다. 파서는 필요한 Reduce·Goto를 마치고, Accept로 입력 전체의 파싱을 완료합니다.
이 예제에서 정책은 값 a 뒤의 Div → 오른쪽 값 시작의 RegExp → 값 b 뒤의 Div 순서로 묶음을 반환했습니다. 파서는 매번 현재 문맥을 정책에 전달하고, 정책이 반환한 묶음으로 source에 다음 토큰을 요청했습니다.
이번에는 같은 대입문에서 값 자체가 정규식으로 시작하는 경우를 살펴보겠습니다. 앞의 예제와 달라지는 지점은 파서가 어디까지 소비했는가입니다.
4. 이번에는 result = /ab/g;를 처리해 보겠습니다.
새 입력을 파싱하는 상황으로 바꾸겠습니다. 이번에는 파서가 식별자 result와 대입 연산자 =만 소비했습니다. 파서는 이제 대입할 값의 시작을 처리해야 합니다.
파서가 지금까지 소비한 입력
result =
앞에서 정의한 문법에 따라, 이 위치에는 식별자·숫자·정규식 리터럴이 올 수 있습니다. 파서는 이 기대 토큰 정보와 현재 입력 위치 등을 담은 문맥을 정책에 전달합니다. 기본 정책은 그 문맥을 확인하고, 정규식 리터럴을 인식하는 규칙이 포함된 RegExp 묶음을 반환합니다.
파서는 앞의 나눗셈 예제와 똑같이 source.Peek(cursor, goal)을 호출합니다. 이번에는 정책이 반환한 goal이 RegExp 묶음입니다.
“정책이 반환한 규칙 묶음으로, 현재 위치의 다음 토큰 하나를 만들어줘.”
RegExp 묶음에도 식별자·숫자 같은 공통 규칙이 들어 있습니다. 따라서 source는 실제 원문을 확인한 뒤, 식별자·숫자·정규식 리터럴 중 해당하는 토큰을 반환합니다.
RegExp 묶음은 값의 시작에 올 수 있는 공통 토큰도 읽습니다.
실제로 뒤에 있는 원문 | source가 반환하는 토큰 |
a; | 식별자 토큰 a |
123; | 숫자 토큰 123 |
/ab/g; | 정규식 리터럴 토큰 /ab/g |
실제 원문이 result = /ab/g;라면 다음 순서로 처리합니다.
result = /ab/g;
파서는 = 토큰까지 소비한 문맥을 정책에 전달합니다. 정책이 RegExp 묶음을 반환하면, 파서는 그 묶음으로 source에 다음 토큰을 요청합니다.
source는 앞의 공백을 확인하고, 정규식 본문과 닫는 /, 플래그 g까지 읽습니다. source는 /ab/g 전체를 토큰 하나로 반환합니다.
파서는 반환된 정규식 리터럴 토큰으로 ACTION을 조회합니다. 필요한 Reduce·Goto를 처리한 뒤, 해당 토큰을 Shift합니다.
파서는 정규식 토큰을 Shift한 뒤 입력 위치를 ; 바로 앞으로 옮기고, 갱신된 문맥을 정책에 전달합니다. 값 뒤에서 연산자나 세미콜론을 받을 위치이므로, 정책은 다음 요청에 사용할 Div 묶음을 반환합니다.
파서는 정책이 반환한 묶음으로 다음 토큰을 요청하고, source는 공통 규칙으로 세미콜론을 인식해 반환합니다. 파서는 ;를 Shift합니다.
파서는 세미콜론 Shift 뒤에도 같은 순서로 정책을 호출하고, 반환받은 묶음으로 다음 토큰을 요청해 EOF를 받습니다. 필요한 Reduce·Goto를 마친 뒤 Accept로 입력 전체의 파싱을 완료합니다.
정책은 값의 시작에서 RegExp 묶음을, 정규식 토큰 뒤에서 Div 묶음을 반환했습니다. 파서는 같은 요청 코드에 정책이 반환한 묶음을 전달하여, 정규식 리터럴과 세미콜론을 차례로 받았습니다.
두 예제에서 파서는 정책이 반환한 묶음과 현재 위치를 source에 전달했고, source는 토큰과 다음 위치를 반환했습니다. 이제 이 요청값과 반환값을 실제 API가 어떻게 표현하는지 살펴보겠습니다.
5. 파서는 위치와 규칙 묶음을 보내고, source는 토큰과 다음 위치를 반환합니다.
앞에서 만든 source의 인터페이스가 ITokenSource입니다. 파서는 이 입력 공급자에 아직 소비하지 않은 원문 위치와 정책이 반환한 정규식 규칙 묶음을 전달합니다. 입력 공급자의 Peek 메서드는 토큰 하나와 그 토큰 다음의 위치를 반환합니다.
ITokenSource의 다음 토큰 요청 메서드
TokenRead Peek(TokenCursor start, LexicalGoal goal);
전달 방향 | 정보 | 이 정보가 필요한 이유 |
파서 → source | start
TokenCursor 입력 위치 | 원문의 어느 위치부터 다음 토큰을 만들지 정합니다. |
파서 → source | goal
정책이 반환한 LexicalGoal 규칙 묶음 | 이번 요청에서 적용할 정규식 규칙들을 정합니다. |
source → 파서 | TokenRead.Token
만들어진 토큰 | 파서가 토큰 종류로 ACTION을 조회하고, 내용과 원문 위치를 트리·진단에 사용합니다. |
source → 파서 | TokenRead.Next
토큰 소비 후 사용할 위치와 렉서 상태 | 파서가 Shift했을 때 어디부터 다음 토큰을 요청할지 정합니다. |
파서가 현재 원문 위치를 보관하는 값이 TokenCursor입니다. SourceOffset은 아직 소비하지 않은 위치를 .NET 문자열의 UTF-16 단위로 나타냅니다. TokenIndex는 지금까지 소비한 토큰 수이고, PreviousToken은 마지막으로 소비한 토큰입니다.
source.Start는 원문의 시작 커서를 제공합니다. 파싱 중의 현재 커서는 파싱 호출마다 만드는 ContextualInput 객체의 Cursor 프로퍼티에 보관합니다. 파서는 이 커서를 source.Peek에 전달하고, 토큰을 Shift하면 반환값의 TokenRead.Next로 현재 커서를 교체합니다.
커서에는 어느 입력 공급자에 속하는지 확인하는 SourceIdentity와 렉서 상태를 담는 LexicalState도 있습니다. 따라서 현재 입력 위치의 확정은 파서가 맡고, source는 요청받은 위치에서 토큰과 다음 커서를 계산합니다.
반환되는 TokenData에는 토큰의 내용·종류·원문 위치와 함께 LeadingTrivia가 담깁니다. 이 정보는 현재 커서부터 토큰 시작 위치까지의 공백·주석 원문이며, 줄바꿈 포함 여부도 제공합니다. 따라서 C# 프레디케이트는 요청형 경로에서도 토큰 앞의 줄바꿈을 검사할 수 있습니다.
원문 끝에 도달하면 source는 폭이 0인 EOF 토큰을 만들어 반환합니다. 마지막 토큰 뒤의 공백·주석은 EOF의 LeadingTrivia에 담깁니다. EOF의 Next는 토큰 수와 이전 토큰을 그대로 보존합니다.
source가 EOF로 원문의 끝을 알리면, 파서는 그 EOF로 ACTION을 조회합니다. 파서는 필요한 Reduce·Goto를 처리하고 Accept 액션을 확인했을 때 입력 전체의 파싱 성공을 확정합니다.
여기서 Next를 반환하는 이유를 더 살펴보겠습니다. source가 다음 위치를 계산했더라도, 파서가 바로 그 위치로 이동하면 안 되는 경우가 있기 때문입니다.
6. source가 토큰을 만드는 시점과 파서가 토큰을 소비하는 시점을 구분합니다.
Peek는 “이 위치에서 읽으면 어떤 토큰이 만들어지는가”를 확인하는 호출입니다. source는 토큰을 만들기 위해 원문을 살펴보고 다음 위치를 계산하지만, 실제 파서의 입력 위치는 바꾸지 않습니다.
파서는 반환된 토큰을 아직 소비하지 않은 토큰으로 보관합니다. 이 토큰을 흔히 룩어헤드 토큰이라고 부릅니다. 파서는 이 토큰을 보며 필요한 Reduce·Goto를 처리한 뒤, Shift할 때 해당 토큰을 소비합니다.
정규식 예제에서 같은 토큰을 확인하고 소비하는 순서
파서의 동작 | 보관한 토큰 | 파서가 확정한 입력 위치 |
Peek로 토큰 받기 | /ab/g | = 바로 뒤에 그대로 있습니다. |
Reduce·Goto 처리 | 같은 /ab/g 토큰을 유지합니다. | 같은 위치를 유지합니다. |
정규식 토큰 Shift | 해당 토큰을 소비한 것으로 기록합니다. | 반환받은 Next, 즉 ; 바로 앞으로 이동합니다. |
Reduce·Goto 동안에는 같은 룩어헤드 토큰을 계속 사용합니다. 파서는 실제 입력 토큰을 Shift했을 때 다음 입력 위치를 확정하고, 갱신된 문맥을 정책에 전달합니다. 정책은 그 문맥으로 다음 요청의 묶음을 선택합니다. 예를 들어 RegExp 묶음으로 이미 받은 /ab/g는, Reduce로 파싱 상태가 바뀌어도 같은 정규식 리터럴 토큰으로 유지합니다.
이제 요청과 토큰 소비의 순서까지 확인했습니다. 다음으로 기본 정책이 어떤 정보를 비교해 Div·RegExp 묶음을 선택하는지 조금 더 구체적으로 살펴보겠습니다.
7. 기본 정책은 파싱 테이블의 기대 단말로 규칙 묶음을 고릅니다.
앞의 두 예제에서는 new LexicalPolicy(div, regExp)로 묶음 두 개를 등록하고 기본 선택 로직을 사용했습니다. 이 정책은 source.Policy로 파서에 연결됩니다. 파서는 현재 파싱 상태의 ACTION 행에서 기대 단말을 구해 LexicalContext.ExpectedTerminals에 담습니다. 여기서 기대 단말은 현재 상태에서 유효한 ACTION이 등록된 토큰 종류입니다.
파서가 이 문맥을 Resolve(context)에 전달하면, 정책은 문맥에 담긴 기대 단말과 자신이 보관한 규칙 묶음들을 비교합니다. 이 비교를 통해 사용할 묶음을 선택하고, 해당 LexicalGoal 객체를 파서에 반환합니다.
먼저 파서가 result =까지 소비한 경우를 보겠습니다. 이 위치에서 기대하는 단말은 id, num, rx입니다. 식별자와 숫자는 두 묶음에서 모두 읽을 수 있습니다. 그중 두 묶음의 차이를 만드는 토큰은 정규식 리터럴 rx이므로, 정책은 그 규칙이 들어 있는 RegExp 묶음을 선택합니다.
다음으로 파서가 result = a까지 소비한 경우를 보겠습니다. 이 위치에서 기대하는 단말은 나눗셈 /, 덧셈 +, 세미콜론 ;입니다. 덧셈과 세미콜론은 두 묶음에 공통으로 들어 있고, 나눗셈 규칙은 Div 묶음에 들어 있습니다. 따라서 정책은 Div 묶음을 선택합니다.
이미 소비한 입력 | 묶음의 차이를 만드는 기대 단말 | 선택한 묶음 |
result = 다음의 값 시작 | 정규식 리터럴 | RegExp |
result = a 다음의 연산 | 나눗셈 연산자 | Div |
정책은 묶음의 차이를 만드는 기대 단말을 비교합니다. 선택을 마친 뒤 source는 그 묶음의 공통 규칙과 개별 규칙을 모두 사용합니다. 예를 들어 RegExp 묶음을 선택했어도, 실제 원문이 value라면 공통 식별자 규칙으로 그 토큰을 인식합니다.
기본 정책은 묶음 간 차이를 만드는 기대 단말들을 모두 읽을 수 있는 묶음이 하나이면 그 묶음을 선택합니다. 그런 기대 단말이 없으면 정책의 Goals에서 첫 번째 묶음을 선택합니다. 앞의 등록 코드에서 첫 번째 묶음은 Div이므로, 공통 식별자만 기대하는 입력 시작 위치에서도 Div 묶음으로 식별자를 읽을 수 있습니다.
문법 문맥을 더 살펴봐야 할 때는 C# 선택 함수를 전달합니다.
파싱 테이블의 한 상태에는 여러 문법 위치의 후보가 함께 들어갈 수 있습니다. 예를 들어 같은 상태가 나눗셈 토큰과 정규식 리터럴을 모두 기대하면, 앞에서 등록한 두 묶음 중 어느 묶음을 사용할지 기본 정책만으로 정하기 어렵습니다. 이 경우 기본 정책은 ContextualLexingException으로 현재 상태와 원문 위치를 알립니다.
이런 문법에서는 LexicalPolicy를 만들 때 묶음 목록과 C# 선택 함수를 함께 전달합니다. 파서는 앞과 같이 LexicalContext를 정책에 전달합니다. 그러면 정책은 등록된 C# 선택 함수를 호출해 같은 문맥을 넘깁니다. 선택 함수는 현재 LR 상태, 전체 상태 스택과 이미 소비한 토큰 등을 확인한 뒤, 정책에 등록된 Div 또는 RegExp 묶음 객체를 반환합니다.
규칙 묶음과 사용자 선택 함수를 함께 정책에 등록합니다.
var policy = new LexicalPolicy(
new[] { div, regExp },
context => SelectGoal(context));
var source = lexer.CreateTokenSource(input, policy);
var result = parser.Parsing(source);
여기서 SelectGoal은 문법 문맥을 확인해 div 또는 regExp를 반환하는 사용자 C# 함수입니다. 이 함수를 정책에 등록한 뒤에는 같은 순서로 source를 만들고 파서에 전달합니다. 파서가 호출하는 메서드는 그대로 source.Policy.Resolve(context)입니다. 정책이 내부에서 선택 함수를 호출하고 그 결과를 반환하면, 파서는 반환받은 묶음으로 source.Peek를 호출합니다.
같은 닫는 괄호라도, 어떤 문법 구성을 닫았는지 확인해야 합니다.
소비 이력을 확인해 묶음을 선택하는 예제를 보겠습니다. 이번에는 앞의 대입문 문법을 바꾸어 if 조건문과 함수 호출을 포함하는 작은 예제 문법을 사용합니다. 이 문법의 C# 선택 함수는 이미 소비한 토큰에서 괄호의 짝과 역할을 확인합니다.
if 조건 뒤에 실행할 문장이 오는 입력
if (x) /a/.test(y);
파서가 if (x)까지 소비했다고 가정하겠습니다. C# 선택 함수는 ConsumedTokens에서 방금 소비한 )와 짝을 이루는 (를 찾습니다. 그 여는 괄호 앞에는 if가 있으므로, 선택 함수는 이 괄호가 if 조건을 닫았다고 판단합니다.
예제 문법에서 if 조건 다음에는 실행할 문장이 옵니다. 선택 함수가 RegExp 묶음을 반환하면, 정책은 그 묶음을 파서에 반환합니다. 파서가 이 묶음으로 다음 토큰을 요청하면, source는 원문의 /a/를 정규식 리터럴 토큰 하나로 만듭니다. 파서는 이 토큰을 Shift한 뒤에도 정책 호출과 토큰 요청을 반복해, 이어지는 .test(y);까지 처리합니다.
함수 호출 결과에 연산이 이어지는 입력
f(x) / 2;
이번에는 파서가 f(x)까지 소비했다고 가정하겠습니다. 선택 함수가 여는 괄호의 위치와 앞의 식별자 f를 확인하면, 이 괄호는 함수 호출을 닫은 괄호입니다. 예제 문법에서 함수 호출 결과 뒤에는 나눗셈 연산이 이어질 수 있으므로, 선택 함수는 Div 묶음을 반환합니다. 파서는 정책을 통해 이 묶음을 반환받아 다음 토큰을 요청하고, source는 / 하나를 나눗셈 토큰으로 만듭니다. 파서는 이 토큰을 Shift한 뒤 정책 호출과 토큰 요청을 반복해, 이어지는 2;까지 처리합니다.
괄호가 중첩된 if (f(x)) /a/.test(y);도 같은 원칙으로 처리합니다. 안쪽 )는 함수 호출을 닫고, 바깥쪽 )는 if 조건을 닫습니다. 선택 함수가 바깥쪽 괄호의 짝을 확인해 RegExp 묶음을 반환하면, 정책은 그 묶음을 파서에 반환합니다. 파서가 이 묶음으로 토큰을 요청하면, source는 그다음 원문의 /a/를 토큰 하나로 만듭니다.
기본 정책으로 고르든 C# 함수로 고르든, 최종 결과는 source가 사용할 규칙 묶음 하나입니다. 파서는 그 묶음을 source에 전달하고, source는 다음 토큰 하나를 반환합니다.
다음 토큰을 처리하기까지의 순서
① 이전 토큰의 Shift 완료
파서는 입력 커서를 확정하고, 소비한 토큰을 이력에 추가합니다.
② 파서가 갱신된 문맥을 정책에 전달
LexicalPolicy는 기본 로직 또는 등록된 C# 선택 함수로 묶음을 선택하고, 파서에 반환합니다.
③ 파서가 반환받은 묶음으로 다음 토큰 요청
파서는 묶음을 그대로 source.Peek에 전달합니다. source는 그 묶음의 정규식 규칙으로 원문을 읽고 토큰 하나를 반환합니다.
④ 반환된 토큰으로 ACTION 조회
파서는 그 토큰을 보관하고 필요한 파싱 동작을 수행합니다.
C# 선택 함수는 전달받은 정보를 읽고, 같은 입력 문맥에는 같은 규칙 묶음을 반환하는 순수 함수로 작성합니다. 실제 파싱과 충돌 예측은 이 함수를 같은 계약으로 사용합니다. 선택 함수는 source.Policy.Goals에 등록된 LexicalGoal 객체를 반환합니다.
정책이 반환한 묶음으로 토큰을 받은 뒤에는, 파서가 그 토큰으로 ACTION을 조회합니다. 조건절의 ε Reduce가 있으면 프레디케이트를 검사하고, Reduce·Goto 동안에는 이미 받은 토큰을 유지합니다. 정책이 토큰 인식에 사용할 묶음을 고르는 단계와 파서가 문법 경로의 조건을 검사하는 단계는 이 순서로 연결됩니다.
이제 이 호출 순서가 실제 클래스에 어떻게 연결되어 있는지 정리하겠습니다. 먼저 source를 만드는 API와 파싱을 시작하는 API를 확인한 뒤, 같은 입력을 미리 살펴보는 충돌 예측기의 동작을 설명합니다.
8. Lexer·LRParser와 연결 타입은 다음 역할을 맡습니다.
요청형 경로의 중심은 Lexer가 만든 source에 파서가 다음 토큰을 요청하는 구조입니다. 기존 토큰 목록 API와 요청형 API가 같은 LR 파싱 테이블과 실제 Shift·Reduce 처리를 사용합니다.
Lexer.CreateTokenSource는 원문과 정책을 연결한 source를 만듭니다.
Lexer에 등록한 Terminal 객체들을 LexicalGoal로 묶고, 이 묶음들을 LexicalPolicy에 등록합니다. 이후 CreateTokenSource(input, policy)를 호출하면 원문과 정책이 연결됩니다.
이 메서드가 만드는 실제 객체는 ContextualTokenSource이며, 반환된 source는 ITokenSource 인터페이스로 사용합니다. 이 객체는 원문과 Lexer가 정한 토큰 규칙의 순서를 보관하고, Policy로 선택 정책을 제공합니다. source는 각 묶음에서 사용할 토큰 규칙에 등록된 공백·주석 스킵 규칙을 함께 준비합니다.
Peek는 전달받은 위치에서부터 전달받은 묶음의 규칙을 적용합니다. 건너뛴 공백·주석 원문을 다음 토큰의 LeadingTrivia에 담고, 토큰과 다음 커서를 반환합니다. 해당 위치에서 인식할 토큰 규칙이 없으면 원문 한 UTF-16 단위를 NotDefined 토큰으로 반환해 파서가 오류 위치를 알 수 있게 합니다.
LRParser.Parsing은 source를 받아 그 정책으로 요청형 파싱을 수행합니다.
요청형 파싱 메서드
ParsingResult Parsing(ITokenSource source);
문법으로 만든 parser와 토큰 규칙을 등록한 lexer, 두 규칙 묶음 div·regExp를 준비했다면 다음 순서로 연결합니다. input은 파싱할 원문 문자열입니다.
정책을 만들고, source에 연결한 뒤 파싱합니다.
var policy = new LexicalPolicy(div, regExp);
var source = lexer.CreateTokenSource(input, policy);
var result = parser.Parsing(source);
규칙 묶음은 정책을 구성할 때 등록합니다. 그 뒤 일반적인 파싱 호출에서는 정책으로 source를 만들고, 파서에 그 source를 전달합니다. 파서는 새로운 토큰이 필요할 때 현재 문맥을 source.Policy.Resolve에 전달합니다. 정책이 묶음을 반환하면, 파서는 반환받은 묶음을 그대로 source.Peek에 전달합니다.
파서는 반환된 토큰으로 파싱 테이블을 조회해 직접 파싱하며, Reduce·Goto 동안 같은 토큰을 보관합니다. Shift하면 커서와 소비 이력을 갱신하고, EOF에서 Accept를 확인하면 성공한 ParsingResult를 반환합니다.
요청형 경로는 첫 오류에서 멈춥니다. 반환값의 Success는 false가 되고, AllErrors에는 오류 위치와 설명이 담깁니다. 파서의 FiredException으로 오류의 원인도 확인할 수 있습니다. 규칙 묶음을 하나로 선택할 수 없거나 입력 공급자가 반환한 토큰·다음 커서가 계약을 어기면 ContextualLexingException에 LR 상태, 원문 위치와 토큰 순번을 담습니다.
기존 Lexing(string)과 Parsing(IReadOnlyList<TokenCell>)은 계속 사용할 수 있습니다. 사용자 정의 오류 복구와 일반 backtracking을 사용하는 호출은 이 토큰 목록 경로에서 처리합니다. 해당 설정이 켜진 파서에 요청형 API를 호출하면, 파서는 입력을 읽기 전에 NotSupportedException을 던집니다.
ContextualConflictPredictor는 후보마다 별도의 커서와 소비 이력을 사용합니다.
요청형 파싱에서 파싱 테이블의 원래 ACTION 셀에 Shift 하나와 프레디케이트 ε Reduce 하나가 충돌하면, 두 액션이 모두 허용되는 경우 ContextualConflictPredictor가 다음 입력을 살펴봅니다. 예측기는 각 후보에서 같은 LexicalPolicy와 입력 공급자를 사용합니다.
충돌을 확인한 시점에는 파서가 이미 룩어헤드 토큰 하나를 받은 상태입니다. 예측기는 이 토큰을 포함한 입력 상태를 각 후보에 복사합니다. 각 후보는 충돌 당시의 같은 토큰을 유지하며 ε Reduce·Goto를 처리합니다. 각 후보가 그 토큰을 Shift한 뒤, 다음 토큰이 필요할 때 정책을 다시 호출합니다.
예를 들어 충돌 당시 받은 토큰이 y이고, 그 뒤의 원문이 /a/g라고 가정하겠습니다. 두 후보는 먼저 같은 y 토큰으로 각각 진행합니다. 각 후보가 y를 Shift한 뒤에는, 예측기가 해당 후보의 갱신된 파싱 문맥을 정책에 전달하고 반환받은 묶음으로 다음 토큰을 요청합니다.
이때 정책이 한 후보에는 RegExp 묶음을, 다른 후보에는 계속 Div 묶음을 반환한다고 가정하겠습니다. source는 첫 번째 후보의 요청에 /a/g 토큰 하나를 반환합니다. 두 번째 후보의 요청에는 /, 식별자 a, /, 식별자 g를 차례로 반환합니다. 이처럼 후보별 파싱 문맥에 대해 정책이 반환하는 묶음이 달라지면, 이후 토큰의 길이와 개수도 달라질 수 있습니다.
이때 예측기는 후보마다 원문 위치, 렉서 상태, 이전 토큰, 토큰 순번, 소비 이력과 아직 소비하지 않은 토큰을 보관합니다. 한 후보가 토큰을 읽거나 Shift해도 다른 후보의 입력 위치는 바뀌지 않습니다. 각 후보의 프레디케이트도 그 후보의 이전 토큰과 다음 토큰을 받습니다.
토큰 하나로 읽는 후보는 더 적은 예측 단계만 거쳐 먼저 EOF에서 Accept할 수 있습니다. 예측기는 먼저 Accept한 결과를 보존한 채, 다른 최초 액션에서 나온 후보가 어떻게 끝나는지 계속 확인합니다. 다른 후보가 모두 실패하면 Accept한 경로를 선택하고, 서로 다른 최초 액션의 후보가 모두 Accept하면 모호성 진단을 반환합니다.
예측은 후보가 구별될 때까지 진행하며, 후보가 하나의 최초 액션으로 좁혀지면 그 액션을 실제 파서에 반환합니다. 실제 파서는 원래 충돌 위치에서 선택한 액션을 실행합니다. 예측용 커서·스택으로 실제 입력 위치를 덮어쓰지 않고, 실제 Shift·Reduce 과정에서 트리와 파싱 기록을 만듭니다. 예측 중 진행 가능한 후보가 없어지거나 순환·자원 제한에 도달하면 해당 원인과 위치를 진단합니다.
기존 토큰 목록 경로는 LRConflictPredictor를 사용하고, 요청형 경로는 ContextualConflictPredictor를 사용합니다. 두 경로 모두 이 예측을 원래 셀의 Shift 하나와 프레디케이트 ε Reduce 하나가 충돌하는 경우에 적용합니다.
공개 연결 타입은 입력·요청·선택 정보를 나누어 표현합니다.
각 타입의 역할을 앞에서 설명한 호출 순서에 맞춰 정리하면 다음과 같습니다.
공개 타입 | 맡을 역할 |
ITokenSource | 시작 커서·원문 길이·선택 정책 Policy를 제공하고, Peek로 토큰 하나를 반환합니다. |
TokenCursor | 원문 위치·토큰 순번·이전 토큰·렉서 상태를 보관합니다. |
TokenRead | 이번에 확인한 Token과 Shift 후 사용할 Next 커서를 묶습니다. |
LexicalGoal | 사용할 정규식 규칙 묶음입니다. 포함할 토큰 규칙을 가리키는 Terminal 객체들을 보관합니다. |
LexicalContext | 파서가 정책에 전달하는 읽기 전용 문맥입니다. 현재 상태·전체 상태 스택·기대 단말·소비 이력·커서·규칙 묶음 목록을 담습니다. |
LexicalPolicy | 불변인 Goals 목록과 묶음 선택 로직을 보관합니다. 기본 로직은 기대 단말을 비교하고, C# 선택 함수를 지정하면 그 함수를 호출합니다. |
표의 여섯 연결 타입은 Janglim.FrontEnd.Tokenize 네임스페이스에서 사용합니다. 선택 오류를 나타내는 ContextualLexingException도 같은 네임스페이스에 있습니다.
사용자가 직접 ITokenSource를 구현할 수도 있습니다. 입력 공급자는 Policy로 사용할 정책을 제공하고, 같은 커서와 규칙 묶음에 같은 내용의 토큰을 반환해야 합니다. 실제 토큰을 반환할 때 입력 공급자는 그 토큰 뒤의 원문 위치와 토큰 순번을 담은 새 커서를 만들고, TokenRead.Next로 반환합니다. 새 커서의 PreviousToken에는 방금 만든 토큰 객체를 넣고, SourceIdentity에는 시작 커서와 같은 객체를 넣습니다. 파서는 Shift할 때 이 새 커서를 현재 커서로 채택합니다. 공백·주석 원문은 요청받은 커서부터 토큰 시작 위치까지 정확하게 담습니다.
직접 만든 토큰의 공백·주석은 TokenCell의 여섯 번째 생성자 인자 leadingTriviaText로 전달할 수 있습니다. EOF 토큰은 원문 끝의 빈 문자열로 만들고, 다음 커서의 토큰 순번과 이전 토큰을 유지합니다. 이 계약을 통해 일반 파싱과 예측 후보가 같은 입력 공급자를 안전하게 공유합니다.
참고한 명세와 관련 문서
ECMAScript 어휘 문법은 토큰을 받는 문법 문맥에 따라 여러 lexical goal을 사용한다고 설명합니다. 이 문서는 그 개념을 참고해 구현한 Janglim의 요청형 렉서·LR 파서 연결 구조를 설명합니다.
ECMAScript 어휘 문법 12절 — InputElementDiv·InputElementRegExp
렉서 — 토큰과 경계 원문
렉서 심화 — 경계 정보와 구현 이유
SelectFirstAction — 예측 후 최초 액션을 선택하는 과정
저자의 설계와 이 문서의 역할
Janglim의 핵심 LR 구조는 저자가 설계하고 작성했습니다. 이 문서는 그 구조를 바탕으로, 대화에서 검토하고 구현한 파서 주도 렉싱의 호출 순서와 연결 타입을 정리합니다. Codex는 설계 검토와 설명 문서 작성을 보조했습니다.
관련 클래스는 Lexer, LRParser, LRConflictPredictor, ContextualConflictPredictor입니다. 각 클래스의 summary 주석에서 이 문서의 담당 부분으로 이동할 수 있습니다.
