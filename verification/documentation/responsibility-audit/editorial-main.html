Lexer · LRParser 연결 구조 / 엔진 구현 문서

같은 / 문자도,
문법 문맥에 따라 다르게 읽습니다.

다음 두 입력에서 /를 어디까지 읽어야 하는지 살펴보겠습니다.

result = a / b;
result = /ab/g;

첫 번째 입력에서는 / 하나가 나눗셈 연산자입니다. 두 번째 입력에서는 /ab/g 전체가 정규식 리터럴 하나입니다. 따라서 각 위치에 맞는 규칙으로 원문을 읽어야, 파서가 사용할 토큰도 올바르게 만들어집니다.

이를 위해 장림은 토큰 규칙을 여러 묶음으로 준비하고, LexicalPolicy가 현재 파싱 문맥에 맞는 묶음을 선택하도록 합니다. 파서는 정책이 반환한 묶음으로 source에 다음 토큰을 요청하고, source가 만들어 준 토큰을 직접 파싱합니다.

이 문서에서는 먼저 두 규칙 묶음과 source를 준비합니다. 그런 다음 위의 두 입력을 차례로 따라가며, 파서가 어떤 정보를 정책에 전달하고, 정책의 반환값이 어떻게 다음 토큰으로 이어지는지 살펴보겠습니다.

1. 규칙 묶음을 준비하고, 원문을 읽을 source를 만듭니다.

두 입력 모두 식별자와 =, ; 같은 기호를 사용합니다. 그러므로 이 규칙들은 공통으로 넣고, /를 인식하는 규칙만 다르게 구성하겠습니다.

이 문서에서 사용할 두 규칙 묶음
묶음공통 규칙추가하는 규칙
Div식별자·숫자와 =, +, ; 같은 기호나눗셈 /
RegExpDiv와 같은 공통 규칙/ab/g 같은 정규식 리터럴

예를 들어 식별자 규칙은 [a-z]+, 숫자 규칙은 [0-9]+로 준비할 수 있습니다. 여기에 Div 묶음은 / 하나를 인식하는 규칙을 더하고, RegExp 묶음은 /[a-z]+/[a-z]*처럼 정규식 리터럴 전체를 인식하는 예제 규칙을 더합니다.

이렇게 구성하면 같은 원문 /ab/g에서도 묶음에 따라 결과가 달라집니다. Div 묶음으로 다음 토큰 하나를 요청하면 /만 나오고, RegExp 묶음으로 요청하면 /ab/g 전체가 나옵니다. 즉, 규칙 묶음은 source가 이번 토큰을 어떤 규칙들로 인식할지 정하는 단위입니다.

규칙 묶음은 LexicalGoal 객체로 준비합니다.

먼저 문법 개발자는 사용할 토큰 규칙을 Lexer에 등록합니다. 각 규칙을 나타내는 객체의 타입은 Terminal이며, LexicalGoal에는 함께 사용할 Terminal 객체들을 담습니다.

아래 코드에서 commonTokens는 공통 토큰 규칙 목록입니다. 여기에 나눗셈 규칙인 divisionToken 또는 정규식 리터럴 규칙인 regexToken을 더해 두 묶음을 만듭니다.

var div = new LexicalGoal(commonTokens.Append(divisionToken));

var regExp = new LexicalGoal(commonTokens.Append(regexToken));

이제 두 묶음이 준비됐습니다. 다음으로, 현재 파싱 문맥을 보고 이 중 하나를 골라 줄 정책을 만듭니다.

준비한 묶음들을 LexicalPolicy에 등록합니다.

var policy = new LexicalPolicy(div, regExp);

이 정책은 div와 regExp를 보관하고, 파서가 문맥을 전달하면 사용할 묶음 하나를 반환합니다. 위 생성자는 현재 상태에서 받을 수 있는 토큰 종류를 비교하는 기본 선택 로직을 사용합니다. 구체적인 선택 과정은 뒤의 나눗셈·정규식 예제에서 확인하겠습니다.

등록한 묶음 목록은 policy.Goals에서 확인할 수 있습니다. 이 목록은 등록 순서를 유지하며, 정책을 만든 뒤에는 바뀌지 않습니다.

Lexer는 원문과 정책으로 source를 만듭니다.

규칙 묶음과 선택 정책까지 준비했으므로, 이제 이 규칙들로 읽을 원문을 연결할 차례입니다. Lexer.CreateTokenSource에 원문 문자열과 정책을 전달하면, 그 원문에서 토큰을 하나씩 만들어 줄 source 객체가 생성됩니다.

var input = "result = a / b;";
var source = lexer.CreateTokenSource(input, policy);

여기서 input은 앞으로 토큰으로 읽을 원문이고, policy는 사용할 규칙 묶음을 고르는 정책입니다. source는 이 둘을 보관하므로, 이후 요청마다 원문 전체를 다시 전달할 필요가 없습니다. 파서는 읽을 위치와 정책이 선택한 묶음만 전달하면 됩니다.

이 시점에는 원문을 읽을 준비가 끝난 상태입니다. 실제 토큰은 파서가 source에 요청할 때 만들어집니다.

2. 파서는 정책이 반환한 묶음으로 다음 토큰을 요청합니다.

준비한 source를 파서에 전달하면 파싱이 시작됩니다. 사용할 정책은 이미 source.Policy에 연결되어 있습니다.

var result = parser.Parsing(source);

파싱 중 다음 토큰이 필요해지면, 파서는 현재 상태와 지금까지 소비한 토큰 이력을 바탕으로 LexicalContext를 만듭니다. 이 문맥에는 현재 입력 위치, 상태 스택, 현재 상태에서 받을 수 있는 토큰 종류 등이 담깁니다.

파서는 이 문맥을 정책의 Resolve에 전달합니다. 그러면 정책이 사용할 규칙 묶음을 선택해 반환하고, 파서는 반환받은 묶음을 그대로 source.Peek에 전달해 토큰을 요청합니다. 파서 내부에서는 이 두 호출이 다음 순서로 이어집니다.

파서 내부의 묶음 요청과 토큰 요청

// 정책이 context를 보고 규칙 묶음 하나를 반환합니다.
LexicalGoal goal = source.Policy.Resolve(context);

// 파서는 반환받은 묶음으로 다음 토큰 하나를 요청합니다.
TokenRead read = source.Peek(cursor, goal);

이 코드의 context는 파싱 문맥이고, cursor는 현재 입력 위치입니다. 정책의 반환값 goal은 LexicalGoal 타입의 규칙 묶음입니다. Div와 RegExp 중 어느 묶음을 사용할지 판단하는 책임은 정책에 있으며, 파서는 그 판단 결과를 source에 전달합니다.

요청을 받은 source는 cursor 위치에서 goal의 규칙들을 적용하고, 만들어진 토큰을 read.Token으로 반환합니다. 이때 source에 전달되는 정보는 위치와 규칙 묶음입니다. 파싱 상태를 살펴보고 묶음을 고르는 과정은 앞의 정책 호출에서 끝난 상태입니다.

파서는 이렇게 받은 토큰으로 ACTION을 조회해 파싱을 진행합니다. 필요한 Reduce·Goto를 처리하고 토큰을 Shift하면, 그다음 토큰을 요청할 때 갱신된 문맥으로 같은 과정을 반복합니다. 이 흐름을 실제 나눗셈 입력에 적용해 보겠습니다.

3. result = a / b;에서 나눗셈 토큰을 받는 과정입니다.

이제 사용할 문법을 정하겠습니다. 아래 문법은 대입할 값으로 식별자·숫자·정규식 리터럴을 허용하고, 값 사이에 덧셈과 나눗셈을 사용할 수 있습니다. id는 식별자 토큰, num은 숫자 토큰, rx는 정규식 리터럴 토큰입니다.

두 입력 예제에서 함께 사용할 문법

S    : id '=' Expr ';' ;
Expr : Expr '+' Term | Term ;
Term : Term '/' Atom | Atom ;
Atom : id | num | rx ;

id  := Identifier "[a-z]+" ;
num := NumberLiteral "[0-9]+" ;
rx  := StringLiteral "/[a-z]+/[a-z]*" ;

이 문법으로 result = a / b;를 파싱하고 있으며, 파서가 다음 세 토큰까지 소비했다고 가정하겠습니다.

지금까지 소비한 입력

result = a

이제 파서는 값 a 뒤에서 다음 토큰을 받아야 합니다. 현재 파싱 상태에서는 나눗셈 /·덧셈 +·세미콜론 ;을 받을 수 있지만, 실제로 어느 토큰이 이어지는지는 아직 source에서 확인하지 않은 상태입니다. 따라서 파서는 받을 수 있는 토큰 종류와 현재 입력 위치를 context에 담아 정책에 전달하고, 이번 요청에 사용할 규칙 묶음을 받습니다.

이 문맥을 받은 기본 정책은 기대하는 토큰 종류를 등록된 두 묶음과 비교합니다. 덧셈과 세미콜론 규칙은 양쪽에 모두 있지만, 나눗셈 규칙은 Div 묶음에 들어 있습니다. 그러므로 정책은 이 위치에서 사용할 묶음으로 Div를 반환합니다.

반환된 묶음이 goal에 담기면, 파서는 앞에서 본 source.Peek(cursor, goal)을 호출합니다. 그러면 source가 현재 위치의 원문을 Div 묶음의 규칙으로 읽습니다. 실제 예제에서 a 다음에는 공백과 / b;가 이어지므로, source는 공백 정보를 담은 나눗셈 토큰 /를 반환합니다.

이렇게 나눗셈 토큰을 받은 뒤에야 파서는 ACTION[현재 상태, 나눗셈 토큰]을 조회합니다. 파서는 필요한 Reduce·Goto를 처리하고 /를 Shift하여, 이 토큰을 소비한 위치로 이동합니다.

Div 묶음으로 요청해도 실제 토큰은 원문에 따라 달라집니다.

방금 요청에서 나눗셈 토큰이 나온 이유는 실제 원문에 /가 있었기 때문입니다. Div 묶음에는 공통 규칙인 +와 ;도 들어 있으므로, 같은 문맥에서 다른 원문을 읽으면 다음과 같이 해당 토큰이 반환됩니다.

정책이 Div 묶음을 반환한 뒤 source가 실제로 읽는 토큰
뒤에 이어지는 원문반환하는 토큰
/ b;나눗셈 토큰 /
+ b;덧셈 토큰 +
;세미콜론 토큰 ;

정책은 토큰을 인식할 규칙 묶음을 정하고, source는 그 묶음으로 실제 원문을 읽어 토큰을 만듭니다. 이 구분 덕분에 파서는 다음 토큰을 미리 알지 못해도 토큰을 요청할 수 있습니다.

나눗셈 토큰 뒤의 b와 세미콜론도 같은 순서로 처리합니다.

원래 입력으로 돌아와, 파서가 /를 Shift한 다음부터 이어 보겠습니다. 이제 현재 상태는 나눗셈의 오른쪽 값을 받아야 하므로, 다음 요청에 전달할 문맥도 달라집니다.

  1. 오른쪽 값 b를 받습니다. 파서가 갱신된 문맥을 전달하면 정책은 RegExp 묶음을 반환합니다. 이 묶음에도 식별자 규칙이 있으므로, source는 식별자 토큰 b를 만듭니다. 파서는 받은 토큰으로 ACTION을 조회하고 Shift까지 진행합니다.
  2. 세미콜론을 받습니다. 값 b 뒤에서는 연산자나 세미콜론을 받을 수 있으므로, 정책은 다시 Div 묶음을 반환합니다. 파서가 이 묶음으로 토큰을 요청하면 source가 ;를 반환하고, 파서는 이를 Shift합니다.
  3. 입력 전체의 끝을 확인합니다. 파서는 다음 요청에서 EOF 토큰을 받고, 필요한 Reduce·Goto를 마친 뒤 Accept 액션을 확인해 파싱을 완료합니다.

이번 입력에서는 값 a 뒤에서 Div, 나눗셈 오른쪽 값의 시작에서 RegExp, 값 b 뒤에서 다시 Div가 사용됐습니다. 같은 정책이라도 파서가 전달하는 문맥이 달라지므로, 각 위치에 맞는 묶음을 반환할 수 있습니다.

이제 같은 문법에서 대입할 값 자체가 정규식 리터럴인 경우를 보겠습니다. 방금은 값 a를 소비한 뒤 토큰을 요청했지만, 이번에는 = 바로 뒤에서 값을 요청합니다.

4. result = /ab/g;에서는 정규식 전체를 토큰 하나로 받습니다.

새 입력 result = /ab/g;를 파싱하며, 다음 두 토큰까지 소비했다고 가정하겠습니다.

지금까지 소비한 입력

result =

앞에서 정한 문법에 따르면 이 위치에는 식별자·숫자·정규식 리터럴이 올 수 있습니다. 파서가 이 기대 토큰 정보를 담은 문맥을 정책에 전달하면, 정책은 두 묶음에서 공통으로 읽을 수 있는 식별자·숫자와, 한쪽에만 들어 있는 정규식 리터럴을 구분합니다. 정규식 리터럴 규칙이 있는 묶음은 RegExp이므로, 이번에는 RegExp 묶음이 반환됩니다.

이후 파서의 요청은 앞의 나눗셈 예제와 같습니다. 파서는 반환된 goal로 source.Peek(cursor, goal)을 호출합니다. 이번 요청을 받은 source는 RegExp 묶음의 규칙을 적용하므로, 앞의 공백을 건너뛴 뒤 /ab/g 전체를 정규식 리터럴 토큰 하나로 반환합니다.

이 묶음에도 식별자와 숫자 규칙이 함께 들어 있습니다. 따라서 같은 위치의 실제 원문이 a;나 123;라면 각각 식별자 또는 숫자가 반환됩니다. 앞 절에서 Div 묶음으로 /·+·;를 모두 읽을 수 있었던 것과 같은 이유입니다.

원래 입력의 /ab/g를 받은 파서는 ACTION을 조회하고 해당 토큰을 Shift합니다. 그러면 현재 위치는 ; 앞으로 옮겨집니다. 이제는 값 뒤의 문맥이므로 정책이 Div 묶음을 반환하고, 파서는 이 묶음으로 세미콜론을 받아 Shift합니다. 이어서 EOF를 받아 필요한 Reduce·Goto를 마치고 Accept를 확인하면, 이 입력의 파싱도 완료됩니다.

두 예제에서 달라진 부분은 정책이 반환한 규칙 묶음과 그 묶음으로 만들어진 토큰입니다. 파서는 두 경우 모두 현재 문맥으로 묶음을 받고, 반환받은 묶음으로 토큰을 요청한 뒤, 그 토큰을 파싱하는 순서를 따릅니다.

여기까지는 입력의 흐름을 따라갔습니다. 다음으로 이 요청에서 전달한 위치와, 반환받은 토큰·다음 위치를 코드가 어떤 타입으로 표현하는지 살펴보겠습니다.

5. Peek는 토큰과 그 토큰 뒤의 위치를 함께 반환합니다.

앞에서 사용한 source의 인터페이스는 ITokenSource입니다. 이 인터페이스의 Peek 메서드는 읽을 위치와 규칙 묶음을 받고, 토큰과 다음 위치를 묶은 TokenRead를 반환합니다.

TokenRead Peek(TokenCursor start, LexicalGoal goal);

방향값의미
파서 → sourcestart
타입: TokenCursor		이번 토큰을 읽기 시작할 원문 위치입니다.
파서 → sourcegoal
타입: LexicalGoal		정책이 반환한 규칙 묶음입니다.
source → 파서TokenRead.Token
타입: TokenData		원문에서 만든 토큰입니다. 파서는 이 토큰의 종류로 ACTION을 조회합니다.
source → 파서TokenRead.Next
타입: TokenCursor		이 토큰을 소비한 뒤 사용할 다음 위치입니다.

이 표의 TokenCursor는 입력 위치를 보관하는 객체입니다. SourceOffset은 원문에서의 위치를 .NET 문자열의 UTF-16 단위로 나타내고, TokenIndex는 그 위치까지 소비한 토큰 수를 나타냅니다. PreviousToken에는 마지막으로 소비한 토큰이 들어 있습니다.

파싱을 시작할 때 파서는 source.Start에서 시작 커서를 받습니다. 이후 현재 커서는 파싱 호출마다 생성되는 ContextualInput 객체의 Cursor 프로퍼티에 보관합니다. source는 이 커서를 받아 토큰과 다음 커서를 계산하고, 파서는 반환된 Next를 토큰 소비 시점에 사용합니다.

커서에는 입력 공급자를 구분하는 SourceIdentity와 렉서 상태를 담는 LexicalState도 들어 있습니다. 따라서 같은 원문을 여러 경로에서 살펴보더라도, 각 경로의 위치와 읽기 상태를 커서로 구분할 수 있습니다.

여기서 다음 위치를 별도로 반환하는 이유가 중요합니다. source가 토큰을 만들었다고 해서 파서가 그 토큰을 바로 소비한 것은 아니기 때문입니다.

6. 파서는 받은 토큰을 보관하다가 Shift할 때 소비합니다.

정규식 예제로 돌아가, 파서가 =까지 소비한 뒤 /ab/g를 받은 순간을 보겠습니다. source는 이미 정규식 토큰의 끝을 알아냈으므로, 다음 위치인 ; 앞을 TokenRead.Next에 담아 반환할 수 있습니다.

하지만 파서는 이 토큰을 보면서 먼저 Reduce·Goto를 처리해야 할 수 있습니다. 이 동작들은 파싱 상태와 스택을 바꾸며, 입력 토큰은 소비하지 않습니다. 그래서 파서는 받은 토큰을 룩어헤드 토큰으로 보관하고, 실제로 Shift할 때 그 토큰을 소비한 것으로 기록합니다.

/ab/g를 받아 확인한 뒤 실제로 소비하는 순서
동작보관한 토큰현재 커서
Peek로 토큰 받기/ab/g= 바로 뒤
필요한 Reduce·Goto 처리같은 /ab/g= 바로 뒤를 유지
/ab/g를 Shift소비 이력에 추가Next가 가리키는 ; 앞으로 이동

source는 다음 커서를 계산하고, 파서는 Shift할 때 그 커서를 현재 위치로 채택합니다. 따라서 Peek 자체는 파서의 현재 위치를 바꾸지 않습니다. Reduce·Goto로 상태가 바뀌는 동안에도 이미 받은 토큰을 그대로 사용합니다.

Shift가 끝나면 파서는 보관하던 룩어헤드를 비우고, 다음 토큰이 필요할 때 갱신된 문맥을 정책에 전달합니다. 정책이 새 문맥에 맞는 묶음을 반환하면, 파서는 새 커서와 그 묶음으로 다음 토큰을 요청합니다.

토큰 앞의 공백·주석도 반환 정보에 함께 담깁니다.

위 예제에서 = 뒤에는 공백이 있고, 그 뒤에 /ab/g가 있습니다. source는 등록된 공백·주석 규칙으로 이 구간을 건너뛰되, 건너뛴 원문을 토큰의 LeadingTrivia에 보관합니다. 이 정보에는 요청받은 커서부터 토큰 시작 위치까지의 원문과 줄바꿈 포함 여부가 담깁니다.

덕분에 파서는 토큰을 요청형으로 받아도 토큰 앞의 줄바꿈을 확인할 수 있습니다. 예를 들어 줄바꿈을 금지하는 C# 프레디케이트는 다음 토큰의 LeadingTrivia를 보고 조건을 검사합니다.

마지막 토큰 뒤의 공백·주석은 EOF에 담깁니다.

같은 방식으로 원문의 끝까지 읽으면, source는 길이가 0인 EOF 토큰을 반환합니다. 마지막 실제 토큰 뒤에 공백이나 주석이 있었다면, 그 원문은 EOF의 LeadingTrivia에 들어갑니다. EOF의 다음 커서는 원문 끝을 가리키며, 토큰 순번과 이전 토큰을 유지합니다.

이 EOF를 받은 파서는 ACTION을 조회해 남은 Reduce·Goto를 처리합니다. 그 결과 Accept 액션에 도달하면 입력 전체의 파싱 성공을 확정합니다. 원문의 끝을 알려 주는 일은 source가, 문법을 끝까지 만족했는지 판단하는 일은 파서가 맡습니다.

이제 묶음을 받은 뒤 토큰을 읽고 소비하는 과정까지 확인했습니다. 다음으로는 기본 정책이 묶음을 고르는 기준을 정리하고, 그 기준만으로 하나를 고르기 어려운 문맥에서는 어떻게 선택하는지 살펴보겠습니다.

7. 기본 정책으로 고르기 어려운 문맥은 C# 선택 함수로 판단합니다.

앞의 예제에서 기본 정책은 값의 시작에 RegExp를, 값 뒤에 Div를 반환했습니다. 이 선택의 출발점은 파서가 현재 ACTION 행에서 구한 기대 단말입니다. 기대 단말은 현재 상태에서 유효한 액션이 등록된 토큰 종류이며, Reduce의 룩어헤드도 포함합니다.

파서는 이 목록을 LexicalContext.ExpectedTerminals에 담아 전달합니다. 기본 정책은 목록 중 일부 묶음에만 들어 있는 단말들을 찾고, 그 단말들을 모두 읽을 수 있는 묶음이 하나이면 해당 묶음을 반환합니다. 앞의 예제에서는 나눗셈과 정규식 리터럴이 각각 Div와 RegExp를 구별하는 기준이 됐습니다.

만약 기대 단말이 모두 공통 규칙에 해당해 묶음을 구별할 단말이 없다면, 정책은 등록된 첫 번째 묶음을 반환합니다. 이 문서의 등록 순서는 div, regExp이므로, 입력 시작에서 공통 식별자만 기대할 때에는 Div 묶음으로 식별자를 읽을 수 있습니다.

현재 상태의 기대 단말만으로는 하나를 고를 수 없는 경우가 있습니다.

파싱 테이블의 한 상태에는 여러 문법 위치의 후보가 함께 들어갈 수 있습니다. 그 결과 같은 상태가 나눗셈 토큰과 정규식 리터럴을 모두 기대한다면, 앞에서 등록한 두 묶음 중 어느 쪽도 두 토큰 규칙을 모두 포함하지 않습니다. 이 경우 기본 정책은 ContextualLexingException으로 선택할 수 없는 상태와 원문 위치를 알립니다. 조건에 맞는 묶음이 여러 개 남는 경우에도 같은 진단을 반환합니다.

이처럼 현재 상태의 기대 단말만으로 결정하기 어려울 때에는, 이미 소비한 토큰이나 전체 상태 스택까지 살펴보는 C# 선택 함수를 정책에 등록합니다.

var policy = new LexicalPolicy(
    new[] { div, regExp },
    context => SelectGoal(context));

var source = lexer.CreateTokenSource(input, policy);
var result = parser.Parsing(source);

여기서 SelectGoal은 전달받은 LexicalContext를 읽고 div 또는 regExp를 반환하는 사용자 C# 함수입니다. 파서가 Resolve(context)를 호출하면, 정책이 내부에서 이 선택 함수를 실행하고 결과를 반환합니다. 따라서 선택 로직을 바꾸어도 파서의 토큰 요청 순서는 그대로 유지됩니다.

예를 들어 닫는 괄호의 역할을 소비 이력으로 구분할 수 있습니다.

이번에는 if 조건문과 함수 호출을 추가한 예제 문법을 생각해 보겠습니다. 같은 ) 뒤라도, if 조건을 닫았는지 함수 호출을 닫았는지에 따라 이어서 받을 문법 구성이 달라집니다. 이 예제의 C# 선택 함수는 ConsumedTokens에서 괄호의 짝과 그 앞의 토큰을 확인합니다.

if 조건 뒤에 새 문장이 시작하는 경우

if (x) /a/.test(y);

파서가 if (x)까지 소비했다고 가정하겠습니다. 선택 함수가 소비 이력을 살펴보면, 방금 닫힌 괄호의 여는 괄호 앞에는 if가 있습니다. 따라서 이 괄호는 if 조건을 닫은 괄호이며, 그 뒤에는 실행할 문장이 시작됩니다. 선택 함수가 RegExp 묶음을 반환하면, 파서는 정책에서 받은 이 묶음으로 토큰을 요청하고 /a/를 정규식 리터럴 하나로 받습니다.

함수 호출 결과에 나눗셈이 이어지는 경우

f(x) / 2;

이번에는 파서가 f(x)까지 소비했습니다. 선택 함수가 같은 방식으로 괄호의 짝을 찾으면, 여는 괄호 앞에는 함수 이름 f가 있습니다. 이 괄호는 함수 호출을 닫았으며, 그 결과에 나눗셈을 이어 쓸 수 있으므로 선택 함수는 Div 묶음을 반환합니다. 이어서 파서가 이 묶음으로 토큰을 요청하면 source는 / 하나를 나눗셈 토큰으로 만듭니다.

괄호가 중첩된 if (f(x)) /a/.test(y);에서도 확인할 대상은 방금 닫힌 괄호의 짝입니다. 안쪽 괄호는 함수 호출을 닫고, 바깥쪽 괄호는 if 조건을 닫습니다. 따라서 바깥쪽 괄호까지 소비한 문맥에서는 RegExp 묶음을 반환하도록 작성할 수 있습니다.

이 선택 함수는 같은 문맥에 같은 묶음을 반환하는 순수 함수로 작성합니다. 실제 파싱과 충돌 예측에서 같은 함수가 호출되기 때문입니다. 반환값은 정책에 등록한 LexicalGoal 객체 자체를 사용하며, 정책은 반환된 객체가 자신의 목록에 속하는지도 확인합니다.

이렇게 기본 로직이나 C# 선택 함수로 묶음을 하나 고르면, 다음 처리는 source가 맡습니다. 그런데 한 묶음 안에서도 같은 원문에 여러 토큰 규칙이 일치할 수 있습니다. 이때 어떤 규칙을 적용하는지가 다음 절의 내용입니다.

8. source는 묶음 안에서 실제 원문을 가장 길게 읽는 규칙을 선택합니다.

지금까지는 Div와 RegExp 중 어떤 묶음을 사용할지 살펴봤습니다. 묶음이 정해진 뒤에는, 그 안의 토큰 규칙들을 현재 원문에 적용해 다음 토큰을 만들어야 합니다.

예를 들어 한 묶음에 키워드 if 규칙과 식별자 규칙 [$A-Za-z_][$0-9A-Za-z_]*가 함께 있다고 가정하겠습니다. 원문이 ifx이면 키워드 규칙은 앞의 두 글자 if에 일치하고, 식별자 규칙은 세 글자 ifx 전체에 일치합니다. 이 경우 source는 더 길게 읽은 식별자 규칙을 선택합니다.

반면 원문이 if라면 두 규칙 모두 두 글자에 일치합니다. 이때에는 Lexer가 미리 정해 둔 우선순위를 사용하므로, 식별자 정규식보다 우선하는 리터럴 키워드 규칙이 선택됩니다.

키워드 규칙과 식별자 규칙이 함께 있을 때의 선택
입력규칙별 일치 길이반환하는 토큰
if키워드 2 / 식별자 2동률 우선순위에 따라 키워드 if
ifx키워드 2 / 식별자 3식별자 ifx
if$키워드 2 / 식별자 3식별자 if$
$name키워드 불일치 / 식별자 5식별자 $name

이 비교에서 사용하는 길이는 각 정규식이 실제 원문에서 읽은 길이입니다. 따라서 ==에서는 두 글자를 읽는 == 규칙이 = 규칙보다 우선합니다. 원문 aaaa에 a+와 [a-z]가 함께 일치하면, 정규식 표기가 더 짧더라도 네 글자를 읽은 a+가 선택됩니다.

동률일 때 사용할 순서는 Lexer가 규칙을 등록할 때 토큰 분류의 우선순위와 등록 순서로 정합니다. source는 생성될 때 이 순서를 보관하고, 일치 길이가 같은 규칙 중 그 순서에서 앞선 규칙을 사용합니다.

공백·주석을 건너뛸 때도 같은 비교 기준을 사용합니다.

source가 비교하는 대상은 선택된 묶음의 토큰 규칙과, 모든 묶음에 공통으로 적용하는 공백·주석 스킵 규칙입니다. 스킵 규칙이 선택되면 그 원문을 건너뛰고, 이어지는 위치에서 같은 묶음의 규칙들을 다시 비교합니다. 이 과정을 거쳐 다음 토큰 하나가 만들어집니다.

정책의 선택 기준은 묶음 전체를 고르는 데 사용됩니다. 묶음이 정해지고 나면 source는 그 묶음의 공통 규칙과 개별 규칙을 모두 사용합니다. 그래서 앞의 예제에서도 Div 묶음으로 덧셈이나 세미콜론을 읽고, RegExp 묶음으로 식별자를 읽을 수 있었습니다.

각 정규식은 작성한 패턴의 의미대로 동작합니다.

토큰 정규식에 단어 경계 \b를 자동으로 붙이는 처리는 없습니다. 따라서 식별자 규칙이 $를 허용하면 if$ 전체를 식별자로 읽습니다. 문법 개발자가 패턴에 직접 작성한 \b는 그대로 적용됩니다.

또한 주석 규칙에 .*?를 사용했다면, 그 정규식은 첫 번째 닫는 기호에서 멈춥니다. 다른 규칙과 비교할 때에는 이 정규식이 반환한 결과의 길이를 사용하므로, 주석을 마지막 닫는 기호까지 늘려 읽지 않습니다. 정규식 내부의 대안 순서도 .NET 정규식의 동작을 따릅니다.

활성 규칙이 빈 문자열에 일치하면 EmptyTokenMatchException을 발생시킵니다. 토큰 규칙은 입력에서 실제 문자를 읽어 다음 위치로 진행해야 하므로, 길이가 0인 일치를 토큰으로 반복해서 반환하는 상황은 오류로 처리합니다.

실제 길이 비교는 공통 코드인 LexicalRuleMatcher가 수행합니다. 요청형 source.Peek와 기존 Lexer.Lexing이 이 코드를 함께 사용하므로 두 경로에 같은 선택 기준이 적용됩니다. 다음 절에서는 지금까지의 동작이 어떤 클래스에 배치되어 있는지 정리하겠습니다.

9. 실제 클래스와 예측기에서도 같은 책임 구분을 사용합니다.

앞에서는 토큰 하나를 요청하고 소비하는 과정을 따라갔습니다. 이 과정을 구현하는 주요 클래스는 다음과 같으며, 아래의 설명에서는 아직 다루지 않은 예측 후보와 입력 공급자 구현 계약까지 이어서 살펴봅니다.

Lexer는 source를 만들고, ContextualTokenSource가 원문을 읽습니다.

Lexer.CreateTokenSource가 만드는 실제 객체는 내부 클래스인 ContextualTokenSource입니다. 사용자는 이 객체를 공개 인터페이스인 ITokenSource로 사용합니다.

이 객체는 원문, 정책, Lexer가 준비한 규칙 순서를 보관합니다. 또한 각 묶음에서 사용할 토큰 규칙에 공통 스킵 규칙을 합쳐 준비해 둡니다. 이후 Peek 요청이 들어오면 해당 위치에서 규칙을 적용해 토큰과 다음 커서를 계산합니다.

어느 토큰 규칙도 해당 위치의 문자를 인식하지 못하면, source는 원문 한 UTF-16 단위를 NotDefined 토큰으로 반환합니다. 파서는 이 토큰의 원문 위치를 이용해 인식하지 못한 입력을 진단할 수 있습니다.

LRParser는 문맥 전달과 파싱을 맡고, ContextualInput에 입력 상태를 보관합니다.

요청형 파싱의 공개 메서드

ParsingResult Parsing(ITokenSource source);

파싱 호출마다 생성되는 ContextualInput은 현재 커서, 소비 이력, 아직 소비하지 않은 룩어헤드 토큰을 보관합니다. 다음 토큰이 필요하면 현재 ACTION 행에서 기대 단말을 구해 문맥에 담고, 정책의 반환값으로 source.Peek를 호출합니다. 이 내부 객체가 요청 과정을 관리하므로, source가 파서의 상태 스택을 직접 참조할 필요는 없습니다.

파서는 반환된 토큰으로 실제 파싱 테이블과 스택을 처리합니다. Shift가 성공하면 ContextualInput의 현재 커서와 소비 이력이 갱신되고, EOF에서 Accept가 확인되면 성공한 ParsingResult가 반환됩니다.

요청형 경로는 첫 오류에서 멈춥니다. 오류가 나면 Success는 false이며, AllErrors에서 위치와 설명을 확인하고 FiredException에서 원인 예외를 확인할 수 있습니다. 묶음 선택 실패나 입력 공급자의 반환값 계약 위반은 ContextualLexingException에 LR 상태·원문 위치·토큰 순번을 담아 알립니다.

기존 Lexing(string)과 Parsing(IReadOnlyList<TokenCell>)도 계속 사용할 수 있습니다. 사용자 정의 오류 복구나 일반 backtracking을 사용하는 호출은 이 목록 입력 경로로 처리합니다. 해당 설정을 켠 채 요청형 메서드를 호출하면, 파서는 입력을 읽기 전에 NotSupportedException을 던집니다.

연결 타입은 문맥·규칙 묶음·읽기 결과를 각각 담습니다.

지금까지 나온 공개 연결 타입은 모두 Janglim.FrontEnd.Tokenize 네임스페이스에 있습니다. 각 타입은 다음 정보를 나타냅니다.

타입담거나 제공하는 정보
LexicalGoal함께 사용할 Terminal 객체들의 규칙 묶음
LexicalPolicy읽기 전용 Goals 목록과, 문맥으로 묶음을 선택하는 로직
LexicalContext파서가 정책에 전달하는 상태·상태 스택·기대 단말·소비 이력·커서·묶음 목록
ITokenSource시작 커서·원문 길이·정책과, 토큰을 요청하는 Peek 메서드
TokenCursor원문 위치·토큰 순번·이전 토큰·렉서 상태
TokenRead만들어진 Token과 소비 후 사용할 Next 커서

이 중 LexicalContext의 생성자와 LexicalPolicy.Resolve는 내부 API입니다. 앞에서 두 메서드의 호출을 설명한 코드는 파서 내부 흐름을 보여 줍니다. 일반 사용자 코드는 규칙 묶음으로 정책을 만들고, 원문과 정책으로 source를 만든 뒤 parser.Parsing(source)를 호출하면 됩니다.

충돌을 예측할 때에는 후보마다 별도의 입력 상태를 사용합니다.

실제 파싱 중 같은 ACTION 셀에 Shift 하나와 프레디케이트의 ε Reduce 하나가 함께 나올 수 있습니다. 파서가 조건을 검사한 뒤 두 액션을 모두 진행할 수 있다고 판단하면, ContextualConflictPredictor가 뒤의 입력을 미리 살펴보고 실행할 최초 액션을 고릅니다. 이때 예측 후보들도 같은 정책과 source를 사용합니다.

다만 충돌을 확인한 시점에는 이미 룩어헤드 토큰 하나를 받은 상태입니다. 예측기는 그 토큰을 포함한 입력 상태를 각 후보에 복사하고, 후보가 ε Reduce·Goto를 처리하는 동안 같은 토큰을 유지합니다. 후보가 그 토큰을 Shift한 뒤 다음 토큰을 요청할 때부터, 정책에는 해당 후보의 갱신된 문맥이 전달됩니다.

예를 들어 충돌 당시 토큰이 y이고, 그 뒤의 원문이 /a/g라고 가정하겠습니다. 두 후보가 각각 y를 Shift한 뒤, 정책이 첫 번째 후보에는 RegExp 묶음을, 두 번째 후보에는 계속 Div 묶음을 반환한다면 이후의 읽기 결과는 다음과 같습니다.

예측 후보정책이 반환하는 묶음source에서 받는 토큰
첫 번째 후보RegExp/a/g 하나
두 번째 후보Div/, a, /, g 네 개

같은 원문을 서로 다른 개수의 토큰으로 읽으므로, 한 후보가 다른 후보보다 먼저 EOF에서 Accept할 수 있습니다. 그래서 예측기는 먼저 Accept한 결과를 보존한 채 다른 최초 액션의 후보들도 확인합니다. 다른 후보들이 모두 실패하면 살아남은 경로를 선택하고, 서로 다른 최초 액션이 모두 Accept하면 모호성 진단을 반환합니다.

이 과정에서 후보마다 보관하는 정보는 상태 스택, 커서, 소비 이력과 아직 소비하지 않은 토큰입니다. 각 후보의 프레디케이트도 해당 후보의 이전·다음 토큰을 받습니다. 따라서 한 후보가 Shift하더라도 다른 후보나 실제 파서의 입력 위치는 바뀌지 않습니다.

최초 액션이 하나로 좁혀지면, 예측기는 그 액션을 실제 파서에 반환합니다. 실제 파서는 원래 충돌 위치에서 그 액션을 실행하고, 자신의 Shift·Reduce 과정으로 트리와 파싱 기록을 만듭니다. 예측용 스택과 커서는 실제 상태에 덮어쓰지 않습니다. 진행 가능한 후보가 없거나 순환·자원 제한에 도달하면 예측기는 해당 원인과 위치를 진단합니다.

이 예측의 적용 범위는 원래 ACTION 셀의 Shift 하나와 프레디케이트 ε Reduce 하나가 충돌하는 경우입니다. 요청형 경로는 ContextualConflictPredictor를, 기존 토큰 목록 경로는 LRConflictPredictor를 사용합니다.

직접 만든 입력 공급자도 같은 요청·반환 계약을 따릅니다.

이 구조에서는 사용자가 직접 ITokenSource를 구현할 수도 있습니다. 파서와 예측기가 같은 입력 공급자를 사용하므로, 같은 커서와 같은 묶음으로 요청하면 같은 내용의 토큰을 반환해야 합니다. 정책에 등록한 묶음들은 모두 Peek에서 사용할 수 있어야 합니다.

실제 토큰을 반환할 때에는 토큰 끝 바로 뒤를 가리키고, 요청받은 커서보다 토큰 순번이 1 증가한 새 커서를 만듭니다. 이 커서의 PreviousToken에는 방금 만든 토큰을, SourceIdentity에는 시작 커서와 같은 객체를 넣고 TokenRead.Next로 반환합니다. 파서는 Shift할 때 이 새 커서를 현재 커서로 채택합니다.

공백·주석 원문은 요청받은 커서부터 토큰 시작까지 정확하게 담습니다. 직접 만든 TokenCell에는 여섯 번째 생성자 인자 leadingTriviaText로 전달할 수 있습니다. EOF는 원문 끝의 빈 문자열로 만들고, 다음 커서의 토큰 순번과 이전 토큰을 유지합니다.

토큰 규칙을 연결할 때에는 문법·렉서·묶음에 같은 Terminal 객체를 사용합니다. 또한 서로 독립된 파싱에서 수정 가능한 토큰 객체가 공유되지 않도록 반환해야 합니다. 이러한 계약을 지키면 실제 파싱과 예측 후보가 같은 입력 공급자에서 각자의 위치를 유지하며 토큰을 받을 수 있습니다.

참고한 명세와 관련 문서

ECMAScript 어휘 문법은 토큰을 받는 문법 문맥에 따라 여러 lexical goal을 사용한다고 설명합니다. 이 문서는 그 개념을 참고해 구현한 Janglim의 요청형 렉서·LR 파서 연결 구조를 설명합니다.

  • 렉서 심화 — 경계 정보와 구현 이유
  • SelectFirstAction — 예측 후 최초 액션을 선택하는 과정
